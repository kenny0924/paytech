# Client Console 团队成员与邀请 — 需求

> 状态：2026-10-17 阶段 1 用户确认（“按建议”：Q1—Q7 均按建议），进入阶段 2。确认记录见 [delivery.md](./delivery.md)。

## 1. 来源与背景

- 来源：用户 2026-10-17 选择“先做 B：团队成员与邀请”。目前每个 Client 工作区只有入驻申请人一名 OWNER 成员（[租户与工作区](../../20261016/client-console-租户与工作区/requirement.md)第 6 节的假设），客户无法让同事进入工作区，API 凭证、Webhook 等能力也只能由申请人本人操作。
- 已有权威约定（本需求不重新定义，只落地）：
  - [统一人类认证设计](../../../docs/superpowers/specs/2026-08-30-platform-unified-human-authentication-design.md)第 10、12.2—12.4、15.2、17.5 节：Platform 拥有 Member、Role、Invitation 事实。邀请冻结邮箱 Vault Token、成员类型和一个初始角色；同一 Tenant + 邮箱只有一条活跃邀请；接受链接使用独立的 `TENANT_INVITATION_ACCEPT` 认证挑战，Invitation 本身不保存 Secret；接受时账号邮箱必须等于邀请邮箱、Channel 必须匹配 Tenant 类型；一个事务完成“创建或恢复 Member + 授予初始角色 + 消费挑战 + 完成邀请”；已有 Member 时幂等返回或明确拒绝，不能创建重复 Member。账号上下文允许“邀请接受”。
  - 需求目录 PLT-15（管理 Tenant Member、Role 与 Invitation）、PLT-I18（创建、撤销和接受 Tenant Invitation：接受时绑定当前 CUSTOMER Account 并校验目标 Tenant 当前状态）。
  - PLT-15 已确认的展示约束：成员显示与筛选使用已有的脱敏邮箱和账号 ID，不新增姓名字段。
- 已确认（代码与表结构）：`t_tenant_member`（`member_type` 为 OWNER/ADMIN/MEMBER，状态为 ACTIVE/SUSPENDED/REVOKED，已有 `invited_by`）、`t_role`（租户级角色，`scope_key` = tenantId）、`t_tenant_member_role`、`t_role_permission` 已存在；每个 CLIENT 工作区在首次 ACTIVE 投影时获得系统角色 `TENANT_OWNER`，带 4 个开发者权限（API 凭证、Webhook 的读与管理）。`t_authentication_challenge` 已有 `tenant_invitation_id` 列和 `TENANT_INVITATION_ACCEPT` 用途，但**没有 `t_tenant_invitation` 表**，也没有邀请相关代码。认证邮件已经通过 Platform Delivery 发送（注册验证、重置密码）。

## 2. 使用者与目标

| 使用者 | 目标 |
|---|---|
| 工作区 OWNER（入驻申请人） | 邀请同事加入工作区并指定角色；查看成员和邀请；撤销邀请；调整成员角色；移除成员 |
| 工作区管理员（被授予管理员角色的成员） | 协助 OWNER 管理团队，但不能动 OWNER |
| 被邀请人（已有或尚未注册 CUSTOMER 账号） | 通过邀请邮件注册或登录，接受邀请后在“我的工作区”看到并进入该工作区 |
| 后续 Client Console 功能 | 有可按角色授予的权限，新页面按权限决定显示和操作 |

## 3. 本期范围

| 编号 | 功能 | 说明 |
|---|---|---|
| F-01 | 工作区角色 | 每个 CLIENT 工作区提供固定的系统角色（见 Q1），每个角色绑定确定的权限；现有 `TENANT_OWNER` 保持不变 |
| F-02 | 团队页面 | 工作区导航新增“团队”：成员列表（脱敏邮箱、成员类型、角色、状态、加入时间）与邀请列表（脱敏邮箱、初始角色、状态、到期时间、邀请人） |
| F-03 | 发起邀请 | 有团队管理权限的成员输入邮箱并选择一个角色发起邀请；Platform 冻结邮箱 Token、成员类型和初始角色，发送带接受链接的邀请邮件；同一工作区同一邮箱只有一条有效邀请 |
| F-04 | 重发与撤销邀请 | 重发会生成新链接并使旧链接失效（到期时间按 Q4）；撤销后链接不可用 |
| F-05 | 接受邀请 | 被邀请人打开链接：未登录时先登录或注册（注册沿用现有邮箱验证流程）；登录账号的邮箱必须与邀请邮箱相同；接受后成为该工作区 ACTIVE 成员并获得初始角色，回到“我的工作区”可直接进入 |
| F-06 | 调整角色 | 管理者为成员更换角色（每名成员本期只有一个工作区角色，见 Q1）；不能修改 OWNER |
| F-07 | 移除成员 | 管理者移除成员（成员状态 REVOKED）；被移除成员在该工作区内的访问失败关闭，下次刷新回到“我的工作区”并显示原因（沿用租户与工作区 F-07） |
| F-08 | 按权限显示与拦截 | 团队页面和操作只对有权限的成员显示；无权限的请求在 BFF/Platform 被拒绝；现有 API 凭证、Webhook 页面按新角色的权限显示 |
| F-09 | 审计 | 邀请的创建、重发、撤销、接受，成员角色变更与移除写入 Platform 审计，不记录邮箱原值和链接 Secret |

## 4. 本期不做

- Partner Console 的团队管理（PARTNER 租户）；Operations 侧对成员的写操作（Operations 继续只读查询）。
- 自定义角色、按单个权限点自由组合角色、成员同时持有多个角色。
- OWNER 转让、多个 OWNER、OWNER 主动退出工作区。
- 成员暂停（SUSPENDED）与恢复；本期只有移除，移除后可重新邀请（见 Q5）。
- 成员姓名、头像等资料；Google 登录、OTP。
- Platform 驱动的 CLIENT 菜单（PLT-I21）与 Console Resource 注册（见 Q6）。
- 交易、退款等业务页面及其权限。

## 5. 验收标准

### 功能验收

| 编号 | 场景 | 期望 |
|---|---|---|
| AC-01 | OWNER 发起邀请 | 创建 PENDING 邀请并发出邮件；邮件含一次性接受链接；邀请列表显示脱敏邮箱、角色、到期时间 |
| AC-02 | 同一邮箱重复邀请 | 已有有效邀请时提示改用重发，不产生第二条有效邀请；邮箱已是 ACTIVE 成员时拒绝 |
| AC-03 | 重发邀请 | 旧链接失效，新链接可用 |
| AC-04 | 撤销邀请 | 邀请变为 REVOKED，链接打开后提示邀请已失效，且不泄露工作区信息 |
| AC-05 | 已有账号接受 | 登录后接受，成为 ACTIVE 成员并获得初始角色；“我的工作区”显示该工作区且可进入；进入后只拥有该角色的权限 |
| AC-06 | 新用户接受 | 用邀请邮箱注册并完成邮箱验证后接受，结果同 AC-05 |
| AC-07 | 邮箱不匹配 | 登录账号邮箱与邀请邮箱不同：拒绝接受，提示用受邀邮箱登录，不显示受邀邮箱原值 |
| AC-08 | 过期、已撤销、已接受的链接 | 均拒绝接受；已接受的链接被同一账号再次打开时返回已加入的结果（幂等） |
| AC-09 | 工作区不可用 | 工作区被暂停或终止时，不能发起邀请，也不能接受邀请 |
| AC-10 | 调整角色 | 成员下次请求即按新角色判断权限（不需要重新登录）；不能修改 OWNER；管理员不能把别人提升到高于自己的角色（见 Q2） |
| AC-11 | 移除成员 | 成员 REVOKED；被移除成员在工作区内的下次刷新失败并回到“我的工作区”，列表中不再显示该工作区；不能移除 OWNER、不能移除自己（见 Q2） |
| AC-12 | 重新邀请已移除成员 | 接受后恢复为 ACTIVE 成员，获得新邀请的角色，不产生重复成员 |
| AC-13 | 权限 | 无团队管理权限的成员看不到“团队”的管理操作，直接调用接口返回 403；无开发者权限的成员看不到 API 凭证、Webhook 的管理操作 |
| AC-14 | 跨工作区 | 不能查看或操作其他工作区的成员和邀请（返回 404，不泄露存在性） |
| AC-15 | 并发 | 同一邀请被两次同时接受，只产生一个成员和一份角色授权 |
| AC-16 | 安全 | 链接 Secret 只出现在邮件中，数据库只存 HMAC；日志、审计、接口响应不含邮箱原值和 Secret；Token 仍不携带角色和权限 |

### 视觉 / 交互验收

| 编号 | 期望 |
|---|---|
| UI-01 | 工作区导航有“团队”；团队页分“成员”和“邀请”两部分，状态用文字和颜色区分；空状态有说明 |
| UI-02 | 邀请弹窗：邮箱、角色选择（附角色说明），提交中有处理中状态，错误就地提示 |
| UI-03 | 移除成员、撤销邀请需二次确认；调整角色就地完成并反馈 |
| UI-04 | 接受邀请页：显示要加入的工作区名称和角色、当前登录账号（脱敏）；未登录时提供登录 / 注册入口，完成后回到接受页 |
| UI-05 | 无权限成员看到的团队页为只读或不显示菜单项（按 Q3） |
| UI-06 | 桌面与 390px 宽度下布局可用，无横向滚动 |

## 6. 已确认事实与假设

- 已确认（文档）：见第 1 节权威约定。
- 已确认（代码）：见第 1 节最后一条；邀请需要新建 `t_tenant_invitation`（按设计 12.4 节字段）以及新角色和角色权限的初始化数据，**本需求有 DDL 和 DML**。
- 假设：被邀请人邮箱只做格式校验，不做企业域名限制；邀请邮件经现有 Platform Delivery 认证邮件通道发送，test 上经 Mailpit 验证。

## 7. 待决问题

| 编号 | 问题 | 建议 |
|---|---|---|
| Q1 | 提供哪些角色？是否支持自定义？ | 本期每个 CLIENT 工作区固定三个系统角色，成员只持有一个：**管理员**（团队管理 + 全部开发者权限）、**开发者**（API 凭证、Webhook 的读与管理）、**只读成员**（API 凭证、Webhook 只读）。OWNER 保持 `TENANT_OWNER`（全部权限，含团队管理）。不做自定义角色 |
| Q2 | 管理员能做到什么程度？ | OWNER 和管理员都能邀请、撤销邀请、调整角色、移除成员；管理员不能修改或移除 OWNER，不能移除自己；可以邀请或授予“管理员” |
| Q3 | 没有团队管理权限的成员能否看到团队页？ | 能看到只读的成员列表（脱敏邮箱、角色），看不到邀请列表和任何操作；方便成员知道谁是管理员 |
| Q4 | 邀请有效期多长？ | 7 天；重发时重新计算 7 天。接受链接的挑战有效期与邀请一致（设计要求挑战不晚于邀请到期） |
| Q5 | 移除后的成员能否回来？是否需要暂停 / 恢复？ | 本期只做移除（REVOKED）；需要回来时重新邀请，接受时恢复原 Member 记录（设计 12.4“创建或恢复 Member”），不做暂停 / 恢复 |
| Q6 | 菜单与按钮按权限显示：接入 Platform 菜单查询（PLT-I21）还是沿用接入自助的做法？ | 沿用接入自助：BFF 向 Platform 查询当前成员的能力列表，Web 据此显示菜单和按钮；PLT-I21 与 Console Resource 注册另行立项 |
| Q7 | 移除成员或降低角色后，对方已签发的 Access Token 怎么处理？ | 权限每次请求实时判断，降级立即生效；移除后对方的工作区会话在下次刷新时失败（Access Token 最长残余 15 分钟，但每次请求的权限判断会因成员已 REVOKED 而拒绝） |

## 8. 适用阶段

建议走完整 8 个阶段：本需求有 DDL（`t_tenant_invitation`）、DML（新角色与权限）、Gateway 路由登记和邀请邮件，需要阶段 3 设计确认、阶段 6 test 发布清单确认。
