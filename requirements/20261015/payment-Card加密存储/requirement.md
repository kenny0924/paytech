# Payment Card 加密存储需求

> 状态：阶段 1 第 2 版、阶段 2+3 方案第 3 版已确认，阶段 4 已确认，阶段 5 完成待确认（2026-10-15）。卡模型由“每个支付工具一条卡记录”改为“卡 / 卡凭证 / 交易工具”分层，卡按卡号唯一并可按明文卡号定位。[technique.md](./technique.md) 第 2 版和阶段 4 实现基于旧模型，本版确认后重做。领域模型图见评审页 <https://claude.ai/artifact/HmWCN4KQqkXCzzFbpztiCN>。确认记录见 [delivery.md](./delivery.md)。

## 1. 背景与来源

Payment 的 Card 模块原先只有本地合成替身（`CardServiceImpl`）：只接受配置的测试卡号，卡数据保存在本进程内存的 `ConcurrentHashMap` 中，CVV 领取一次后清除。它有三个问题：

| 问题 | 证据 |
|---|---|
| 进程重启后卡数据丢失，多实例下工具申请和 Platform 读卡可能落在不同实例，导致读卡失败 | `CardServiceImpl.materials` 为进程内 Map |
| 没有持久化卡记录，也没有加密 | Schema 中没有 Card 表；`applyInstrument` 留有 `TODO Card：保存已准备的加密卡记录` |
| 只接受配置的测试卡，必须显式开启 Mock，否则 Card 能力不可用 | `PaymentCardProperties.mockEnabled`、`mockPans` |

外部合同已经确定，本需求不改：

- 工具申请 `POST /payment-instrument/v1/card-tokens` 返回支付工具 Token（[申请工具修订](../../20260913/payment-Execution设计/apply-card-instrument-amendment.md)）。
- Platform 凭 Token 调用 `POST /payment-card/v1/channel-card-materials/reveal` 读卡，卡值只在内存中（[卡数据经 Platform 渠道执行决定](../../../agent-docs/decisions/2026-10-14-card-data-platform-execution.md)）。
- Risk 评估使用卡 BIN 和卡指纹（[接入 Risk 统一评估](../payment-接入Risk统一评估/requirement.md)）。

原 [自建 Card Vault 需求](../../20260912/payment-自建CardVault/requirement.md) 的 CVV 不持久化、日志不含卡值、事务内不调外部服务等约束继续有效；其中 `t_payment_submission` 和读卡审计表 `t_card_access_event` 的设计已被后续决定取代或由本需求取消（见 §5）。

## 2. 用户决定（2026-10-15）

1. **卡数据长期保存在 Payment 数据库，不放 Redis。** CVV 可以放 Redis。
2. **读卡不需要审计。** 不建 `t_card_access_event`。
3. **暂不收紧访问控制。** 读卡接口不加调用方认证，保持私网访问。
4. **卡按卡号唯一，能通过明文卡号定位到卡。** 用户：“卡信息应该要是唯一的，不然这样重复的数据太多了”“我想做的是能通过明文卡号定位到这条卡信息”。
5. **分层，不用三要素组合唯一。** 卡的身份只由卡号决定；有效期和持卡人是每次提交的事实，放在卡凭证上，录错只会多一条凭证。
6. **`card_bin` 为 6～8 位：** 卡号不少于 16 位时存前 8 位，少于 16 位时存前 6 位（Q-06）。不存卡组、卡类型、发卡国，以后用 `card_bin` 查 BIN 库。
7. **长期目标（不在本需求实现）：** 用户可以存卡；有一种支付方式用已存卡支付、不必每次输入卡信息；对外商户暴露卡 Token 及前六后四等基础要素；定价使用这些卡要素。本需求的模型要能平滑接上这些能力。

## 3. 使用者与目标

| 使用者 | 目标 |
|---|---|
| Payment 工具申请 | 同一卡号只保存一份加密卡号；每组有效期和持卡人只保存一份；每笔交易记一条工具记录；CVV 暂存 Redis |
| Payment 内部 | 用明文卡号定位到唯一的卡记录 |
| Platform 渠道执行 | 任一 Payment 实例、进程重启后，都能凭 Token 读到这笔交易的卡号、有效期、持卡人和一次性 CVV |
| Risk 评估 | 从卡记录取得 BIN 和跨交易稳定的卡指纹 |
| 运维 | 数据库和日志中看不到卡号、有效期、持卡人明文 |

## 4. 本期范围

### 4.1 数据模型

| 层 | 粒度与唯一性 | 内容 |
|---|---|---|
| **卡** | 每个卡号一条；卡指纹唯一 | 加密卡号、本卡 DEK 的 Vault Token、`card_bin`（6～8 位，见 Q-06）、`pan_last4`、卡指纹 |
| **卡凭证** | 同一张卡下每组“有效期 + 规范化持卡人”一条；（卡、凭证摘要）唯一 | 用本卡 DEK 加密的有效期和持卡人；凭证摘要是对规范化后的有效期和持卡人做的 HMAC |
| **交易工具** | 每个支付工具一条；主键即 `instrument_ref` | 指向本次使用的卡凭证、所属 Client |

Execution 的 `t_payment_instrument_token` 不变，`instrument_ref` 改为指向交易工具记录。表名和字段在阶段 2+3 确定。

### 4.2 行为

1. **按卡号定位：** 用指纹密钥对卡号做 HMAC-SHA256，按卡指纹唯一索引查卡。Card 模块内部提供按卡号查卡的能力，不新增外部接口。
2. **工具申请：**
   - 按卡号查卡，没有就新建：生成本卡 DEK，在 Vault 中保护，然后加密卡号。
   - 按（卡、凭证摘要）查凭证，没有就新建。
   - 新建交易工具记录，与工具 Token 在同一个本地事务内写入。
   - 卡和凭证是可复用的事实。即使本次申请失败，它们也可以保留。
3. **并发首次使用同一卡号：** 只能留下一条卡记录。插入撞唯一键时改为读取已有记录继续处理；输掉竞争的那次在 Vault 中留下一把无人引用的 DEK，作为已知项记录。
4. **CVV：** 用本卡 DEK 加密后按交易工具暂存 Redis，TTL 不超过工具期限，用原子 `GETDEL` 只领取一次；不进数据库、日志、MQ。同一张卡的并发交易互不覆盖。
5. **原提交重放：** 返回原 Token，不新建任何记录、不覆盖 CVV；比对卡指纹和凭证摘要，不一致按现有规则拒绝。
6. **读卡：** 经交易工具找到凭证和卡，从 Vault 取回 DEK，解密卡号、有效期和持卡人，再领取 CVV。
7. **Risk 属性：** 从卡记录取 `card_bin` 和卡指纹。
8. **卡号校验：** Luhn 校验、长度 12～19 位、有效期未过期；不限制测试卡（Q-03）。
9. **指纹密钥：** 由配置提供，未配置时启动失败；与 DEK 无关；不可轮换（Q-07）。
10. **替换内存 Mock：** 删除 Mock 配置和进程内存储。
11. **测试与文档：** 本机 MySQL + Redis 的 `auto` 测试覆盖 §6；同步 PDManer、Schema、配置文档和 `CURRENT_IMPLEMENTATION.md`。

## 5. 明确不做

| 项 | 说明 |
|---|---|
| 存卡、已存卡支付、对外卡 Token | 后续需求，涉及 Commerce、Payment、Platform、Risk；本期模型只保证能挂接（§2 第 7 条） |
| 凭证验证状态（授权成功后标记已验证） | 唯一的使用方是存卡，随存卡需求一起做 |
| 对外掩码规则（前 8 后 4 或前 6 后 4） | 随对外卡 Token 一起定 |
| BIN 库（卡组、卡类型、发卡国） | 以后用 `card_bin` 查 BIN 库，Card 不存 |
| 定价使用卡要素 | 后续由 CCT 牵头 |
| 指纹密钥轮换 | 卡的唯一性依赖指纹，轮换需逐卡解密重算，属于专门的迁移 |
| KMS / HSM | DEK 由 Vault 托管，Payment 不直接接 KMS（Q-02） |
| 读卡审计、读卡接口调用方认证 | 用户决定暂不需要；保持私网 |
| 卡数据自动销毁、保留期限 | 按项目 MVP 规则默认保留，不做自动销毁 |
| 前端采集页、PCI 合规认定 | 不宣称 PCI 合规 |
| mor-test 部署 | Payment 尚未部署到 mor-test，阶段 6–7 不适用 |

## 6. 验收标准

| 编号 | 验收标准 |
|---|---|
| AC-01 | 新卡首次申请：新增一条卡、一条卡凭证、一条交易工具记录；卡号、有效期、持卡人只以密文存在；`card_bin` 按卡号长度为前 8 位或前 6 位，`pan_last4` 为后 4 位；`instrument_ref` 指向交易工具记录 |
| AC-02 | 同一卡号、同一有效期和持卡人在另一次提交中申请：不新增卡和凭证、不再调用 Vault Protect，只新增交易工具记录 |
| AC-03 | 同一卡号、不同有效期或持卡人：沿用同一张卡，新增一条卡凭证；持卡人只有大小写或空格差异时视为同一凭证 |
| AC-04 | 用明文卡号能定位到对应的卡记录；未保存的卡号返回空 |
| AC-05 | 两次并发首次使用同一卡号，最终只有一条卡记录，两次申请都成功 |
| AC-06 | Payment 进程重启后（或由另一实例处理），Platform 读卡仍能取得本次交易的卡号、有效期、持卡人和 CVV |
| AC-07 | CVV 只存在 Redis，加密保存，TTL 不超过工具期限；读卡领取一次后即删除，再次读卡失败；同一张卡两笔交易的 CVV 互不影响 |
| AC-08 | 原提交重放时返回原 Token，不新建任何记录、不覆盖 CVV；换卡重放仍按现有规则拒绝 |
| AC-09 | Risk 评估取得的 BIN 与卡指纹来自卡记录；同一卡号在不同交易中相同 |
| AC-10 | 未配置指纹密钥时 Payment 启动失败 |
| AC-11 | 卡号 Luhn 校验失败、长度不符或已过期时申请失败，不写任何卡数据和 Redis；不再只接受测试卡 |
| AC-12 | 日志、异常信息、`toString` 中没有卡号明文、CVV、持卡人、有效期和指纹 |
| AC-13 | 数据库事务内不访问 Vault 和 Redis；Vault 或 Redis 不可用时申请失败（503），不返回 Token |
| AC-14 | 现有卡支付 `auto` 测试（卡直付、风控评估）在新存储下全部通过 |

## 7. 问题与决定

| 编号 | 问题 | 决定 |
|---|---|---|
| Q-01 | 卡记录粒度 | **第 2 版修订：** 卡按卡号唯一，有效期和持卡人放在卡凭证上，每个支付工具一条交易工具记录（用户 2026-10-15）。原决定“每个支付工具一条卡记录”作废 |
| Q-02 | 密钥 | 每张卡一把 DEK，存 Vault（用户 2026-10-15 决定，[例外决定](../../../agent-docs/decisions/2026-10-15-vault-payment-card-dek.md)）；卡号、凭证、CVV 都用本卡 DEK 加密；指纹密钥由环境变量提供 |
| Q-03 | 是否只允许测试卡 | 不限制。用户：“不用管，假设我们已经有了 PCI 资质”；本需求不据此宣称已合规 |
| Q-04 | CVV 在 Redis 是否加密 | 加密，用本卡 DEK |
| Q-05 | 阶段安排 | 阶段 1 → 2+3 合并 → 4 → 5；阶段 6–7 不适用；提交另行确认。第 2 版需求确认后从 2+3 重新开始 |
| Q-06 | BIN 位数 | 卡号不少于 16 位存前 8 位，少于 16 位存前 6 位；后 4 位都存（用户 2026-10-15）。这样明文最多为前 8 后 4（16 位以上）或前 6 后 4，符合 PCI 截断上限 |
| Q-07 | 指纹密钥能否轮换 | 不可轮换，卡的唯一性和按卡号定位都依赖它（用户 2026-10-15 认可） |
| Q-08 | 持卡人规范化规则 | 去首尾空格、连续空白合并为一个空格、转大写；有效期规范为两位月加四位年。只用于凭证摘要，加密保存的是原值 |
