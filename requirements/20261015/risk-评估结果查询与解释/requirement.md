## 1. 背景与目标

支付反欺诈一期上线后，每次支付评估都把结论、输入快照、变量（Feature）结果和规则轨迹写进 Risk 库，影子运行也会写出候选发布的评估和差异标记。但目前没有任何接口能读取这些记录：一期验收 AC-7 只能直接查库核对，运营也无法回答“这笔支付为什么被拒”。

**目标：** Risk 提供两个只读接口：一个按评估查结论，一个按评估查“为什么得出这个结论”。运营后台据此排查单笔评估，并在激活新发布前查看影子运行中结论变化的样本。

## 2. 使用者与场景

| 使用者 | 场景 | 成功结果 |
|---|---|---|
| 风控运营、客服 | 商户或玩家询问某笔支付为何被拒或要求 3DS | 用支付尝试 ID（或评估 ID）查到结论、拒绝原因、认证要求、所用发布与流程版本 |
| 风控运营 | 想知道是哪条规则、哪个变量值触发了结论 | 看到流程实际经过的节点、各规则集中执行并命中的规则、实际求值的条件结果、所用变量的取值 |
| 风控运营 | 激活新发布前评估影子运行 | 从正式评估看到对应的影子评估结论，以及结论或认证要求是否变化；从影子评估看到其解释 |
| 排查人员 | 评估失败或超时 | 看到失败码、耗时与已完成部分的轨迹，不出现虚构结论 |

## 3. 本期范围

1. **查询风险决定（RCO-I06）：** 按评估 ID 查询；另支持按 `pointCode + businessKey`（支付为支付尝试 ID）查询该业务身份的正式评估。返回评估身份、风控点、模式（正式/影子）、技术状态、结论、拒绝原因码、附加输出（如认证要求）、发布与流程版本坐标、评估时间与耗时、失败码。
2. **查询评估解释（RCO-I10）：** 按评估 ID 查询。返回：
   - 流程路径：按顺序经过的节点（规则集节点及所引用的规则集版本、结束节点）；
   - 规则轨迹：每个执行过的规则（编码、名称、是否命中、是否终态、动作）及其条件谓词求值结果；
   - 变量取值：本次实际计算的 Feature 结果（变量编码、类型、值、技术状态、耗时）；
   - 输入快照：评估冻结的全部输入字段原值，含 IP、User-Agent、卡指纹、消费者引用（Q1）；
   - 影子比较：正式评估列出以其为基线的影子评估（结论、是否变化、严重程度）；影子评估给出其基线评估 ID。
3. **补全运行期记录（视 Q3）：** 为新产生的评估记录到达的结束节点与原因码、流程经过的节点，使解释可以完整给出“走了哪条路”。
4. **交接：** 给 Operations 会话的接口说明与页面建议。

## 4. 不做项

- 运营页面、BFF 适配、Platform 资源与权限登记（Operations 会话按交接单实施）。
- 按订单、Client、时间范围的评估列表或检索（视 Q2）；统计报表。
- 结账（`CHECKOUT_PREPARE`）运行期评估：当前没有结账评估器，结账点不会产生评估记录；接口按风控点通用设计，但本期只有支付数据。
- 重新执行或回放评估；修改评估记录。
- 授权结果回流、拒付等事件数据。

## 5. 已确认事实

| 事实 | 证据 |
|---|---|
| 评估主表 `t_decision_evaluation` 保存模式（PRIMARY/SHADOW/REPLAY）、技术状态、结论、发布、点版本、耗时、失败码、影子批次与基线评估、决定是否变化、认证要求是否变化 | `risk-compliance-schema.sql` |
| 规则轨迹 `t_evaluation_rule_trace` 保存规则（含所属规则集版本）和谓词两类行：是否命中、是否终态、执行顺序 | 同上；`EngineOutcome.RuleTrace/PredicateTrace` |
| Feature 结果 `t_evaluation_feature_result` 保存类型化取值与技术状态 | 同上 |
| 支付输入快照 `t_transaction_risk_assessment` 按支付尝试唯一，保存 17 个输入字段与认证要求；其中 IP、User-Agent、卡指纹、消费者引用为受限值 | 同上；[一期设计](../../20261014/risk-支付反欺诈一期/design.md) |
| **到达的结束节点与原因码没有落库**：引擎 `EngineOutcome.reasonCode` 只用于响应；`decision_adjustment_reason_code` 未被写入 | `DecisionEngine`、`PaymentAttemptEvaluator` |
| **流程经过的节点没有落库**：只能从规则轨迹的规则集版本间接推断；同一规则集版本被多个节点引用时无法区分 | 同上 |
| 一期不写 `t_evaluation_action_intent` / `t_action_effect`；命中规则的动作可从规则配置读出 | 一期设计第 3.5、16 节 |
| 运行期评估器只有 `PaymentAttemptEvaluator`（`PAYMENT_ATTEMPT_RISK`） | `service/evaluation/` |
| `/risk-decisions` 路径的 Web 日志只记元数据 | 统一评估修订第 2 节 |

## 6. 前提与依赖

- 无阻塞依赖；本机与 mor-test 已有支付评估能力。mor-test 的支付决策点有无生效发布、是否已有评估数据，在阶段 2 核对。
- 本会话只改 risk-compliance-service；Operations 接入另由其会话实施。

## 7. 验收标准

| 编号 | 标准 |
|---|---|
| AC-1 | 按评估 ID 查询返回结论、技术状态、拒绝原因码、附加输出、发布与流程版本坐标、时间与耗时；ALLOW、REVIEW、DENY、FAILED、TIMED_OUT 各自字段正确，失败时不返回结论 |
| AC-2 | 按 `pointCode + businessKey` 查询返回该业务身份的正式评估，与按评估 ID 查询结果一致；不存在返回 404 |
| AC-3 | 解释给出流程经过的节点顺序与到达的结束节点（Q3 采纳后产生的评估）；Q3 之前的旧评估明确标出“路径不可用”，不推断 |
| AC-4 | 解释给出执行过的规则及其命中、终态、谓词结果，与库内轨迹逐条一致；规则编码、名称取自评估所用的冻结规则集版本 |
| AC-5 | 解释给出每个实际计算的变量取值与状态；特征失败的评估能看出是哪个变量失败 |
| AC-6 | 响应返回评估冻结的全部输入原值（含 IP、User-Agent、卡指纹、消费者引用）；Risk 日志只记元数据，不出现这些原值 |
| AC-7 | 正式评估的解释列出其影子评估及变化标记；影子评估可单独查询结论与解释 |
| AC-8 | 未知评估 ID 返回 404；参数格式错误返回 400；接口只读，不改变任何记录 |

## 8. 已决问题（2026-10-15）

| 编号 | 问题 | 结论 |
|---|---|---|
| Q1 | 受限输入如何展示 | **用户决定：原样返回**（“可以展示吧，又不敏感”）。接口只在内部私网提供、经 Operations 鉴权后调用；Risk 日志仍只记元数据，交接单要求 BFF 不在日志中记录响应体 |
| Q2 | 除评估 ID 外支持哪些查询入口 | **采纳建议：评估 ID + `pointCode/businessKey`**。运营常只有订单号：可选加“按订单 ID 列出支付评估”（交易快照已有订单索引），建议本期不做，需要时再加 |
| Q3 | 是否补记结束节点、原因码与流程路径 | **采纳建议：补记**。不补记就无法回答“走了哪条路、为什么拒”；代价是一次 DDL（新增列或一张流程轨迹表，方案在阶段 3 定），只对之后的评估生效，历史评估标“不可用” |
| Q4 | RCO-I06 的内部调用方 | **采纳建议：**本期只服务 Operations BFF。Payment 结果未知时用原请求重放评估接口即可拿回原结果，不需要 I06；Commerce 目前无结账评估。接口按内部合同放入 `risk-api`，以后可直接复用 |
