# operations：明细账运维 · 需求

版本：阶段 1 已确认；2026-10-30 阶段 2 调整 R4（追平定位为"排除原因后重放"） · 登记日期：2026-10-30 · 确认记录见 [delivery.md](./delivery.md)

## 1. 背景

account 是 Client / Local Partner / 银行现金的账户明细账，是 Owner 余额的实时权威来源（[2026-10-18 决定](../../../agent-docs/decisions/2026-10-18-account-ledger-subledger-control-account.md)）。资金事实的流向是：

```text
billing（计费事实）──MQ──▶ account（入账：批次 + 流水 + 余额）──AccountPosted──▶ ledger（控制科目）
```

运营控制台"财务"菜单已经有：

- **余额查询**：Client 的待结算 / 可用 / 锁定 / 保证金 / 追偿应收余额，Partner 同理。
- **明细账**：Owner 账户列表（可按科目筛选）→ 账户流水 → 批次详情。

但这条链路**出了问题时，运营没有任何排查和修复手段**：

- 看不到某个主体 + 币种下，billing 发了多少事实、account 入了多少、ledger 消费到哪里，也就无法回答"这笔钱为什么没到账 / 总账为什么对不上"。
- 只能逐个账户翻流水，不能按入账顺序翻一条过账流的全部批次。
- 余额和流水不一致时，account 已经提供了按流重建余额的接口（`POST /account-postings/v1/streams/rebuild`），但没有入口，只能找开发调用。
- ledger 漏消费 account 批次时，ledger 已经提供了追平接口（`POST /posting-streams/v1/catch-up`，接口注释写明"本期不接控制台"），同样没有入口。

上次盘点中说的"账户运营"，即指这一块。

## 2. 目标

财务运营 / 运维人员能在运营控制台上：

1. 看清一个账簿主体 + 币种在 billing → account → ledger 三段上的进度和差距。
2. 按入账顺序浏览一条过账流的批次，下钻到批次详情。
3. 在有权限且确认后，触发余额重建和 ledger 追平，并看到执行结果。

## 3. 使用者与场景

| 使用者 | 场景 | 期望结果 |
|---|---|---|
| 财务运营 | Client 反馈"钱没到账" | 选 OE + 币种，看到 billing 已发布 / account 已入账的事实数和最大事实号，判断卡在哪一段 |
| 财务运营 | 期间关账时 `CHECK_ACCOUNT_POSTING_PROGRESS` 步骤不通过 | 看到哪条过账流 ledger 落后、落后多少，触发追平 |
| 运维 | 怀疑某主体下余额被异常改写 | 按流翻批次核对，必要时触发余额重建，看到重算的账户数和流水数 |
| 财务运营 | 核对一段时间内的入账顺序 | 按序号翻页浏览过账流批次，点开批次看流水 |

## 4. 本期范围

- **R1 进度总览**：选择账簿主体（OE 或 Finance Entity）和币种后，展示三段进度：
  - billing → account：billing 已发布 / 未发布事实数和最大事实号，对比 account 已应用事实数和最大事实号。
  - account 过账流：每条流（主体、分片）的最大批次序号、最后入账时间。
  - account → ledger：每条流 ledger 已消费到的序号和落后数量（ledger 侧是否有查询接口见 Q-2）。
  - 有差距的段落要醒目标出，没有差距时显示"已一致"。
- **R2 过账流批次浏览**：从进度页的某条流进入，按序号升序翻页（每页最多 200 条，复用 account 的 `fromSequence` 翻页），列出批次的序号、来源事实、生成时间、流水条数；点开复用现有的批次详情抽屉。
- **R3 余额重建**：在进度页对"主体 + 币种"触发重建：
  - 二次确认弹窗说明"只按流水重算余额，不删改流水、不发布事件"。
  - 提交时把操作人传给 account（`operatorId`），展示重算的账户数、流水数和最大批次序号。
  - 与入账并发冲突（409）或没有过账流（`STREAM_NOT_FOUND`）时就地提示。
- **R4 ledger 追平（排除原因后重放）**：ledger 是 account 的下游，进度在 ledger 手里，所以由 ledger 主动按序号从 account 拉取落后的批次补记（ledger 已有的 `catch-up`，原设计中的死信恢复路径）。
  - 落后的流要展示**卡住的那一批**（ledger 已消费序号 + 1 对应的 account 批次：序号、事实号、类型、生成时间），可以点开查看流水。
  - 落后分两类：临时故障（消息丢失、重试用完、依赖短暂不可用）追平即可补上；规则拒绝（缺记账规则、数据不合法）不先排除原因，追平会在同一批次上返回同样的错误。
  - 追平失败时，就地展示 ledger 返回的错误码和说明，提示先排除原因（例如去"记账规则"页补规则）再重放。
  - 每次最多处理 200 个批次；返回本次处理批次数、处理后序号和是否已追平；没追平时按钮变成"继续追平"，并显示剩余落后数量。
  - 调用时带上操作人。
- **R5 权限**：只读查看（R1、R2）一个权限；执行类（R3、R4）一个权限，与查看分开。

## 5. 不做项

- **人工余额桶移动**：account 现有的桶移动来源只有到期转可用、出款锁定 / 释放、缴税锁定 / 释放，都绑定具体业务，没有"人工调整"类型。人工挪钱需要单独的业务设计和审批，本期不做。
- **保证金 / 追偿应收专门视图**：余额页已经展示这两项，明细账页也可以按科目筛出这两类账户；而且 account 目前没有任何写入这两类账户的映射规则（保证金和拒付流程未上线）。本期不做。
- **账户冻结 / 关闭**：account 没有改状态接口。
- **修改或补录流水**：重建只重算余额。
- **billing 事实的重发或补发**：不在 account / ledger 运维范围内。
- **死信事实的可视化**（`account.billing.dlq`，映射失败的事实）：见 Q-3。

## 6. 业务规则

- B1 查看类功能只读，不加锁、不推进任何状态。
- B2 重建和追平都可以安全地重复执行：重建不删改流水、不发布事件；追平每批单独提交，中途失败时已处理的批次保留，按序号连续补记，并有唯一约束防止重复记账。界面上要说明这一点。追平不是"点一下就好"的万能修复：规则拒绝类的落后必须先排除原因。
- B3 执行类操作必须带操作人：重建传 `operatorId`（account 现在只写入 INFO 日志）；追平按 ledger 合同传 `X-Gateway-Actor-Subject` / `X-Gateway-Session-Id`。留痕方式见 Q-1。
- B4 进度数字以各 Owner 服务返回为准，BFF 只做对比和展示，不自行推算业务结论（例如不替 ledger 判断能否关账）。
- B5 某一段的服务不可用时，只有该段显示错误，其余段落正常展示。

## 8. 验收标准

**功能验收**

- AC-01 选择 OE + 币种后，展示 billing 已发布 / 未发布事实数和最大事实号，以及 account 已应用事实数和最大事实号；两者一致时显示"已一致"，不一致时显示差额。
- AC-02 展示该主体 + 币种下全部过账流的最大序号和最后入账时间；Finance Entity 主体同时展示其关联 OE 的流（与 account 进度接口语义一致）。
- AC-03 每条流展示 ledger 已消费序号和落后数量；落后时醒目标出，展示卡住的那一批（可点开流水），并提供"追平"入口。
- AC-04 从某条流进入批次浏览，按序号升序翻页，每页最多 200 条；点开批次显示流水明细（与明细账页的批次抽屉一致）。
- AC-05 有执行权限的账号能触发余额重建；确认后展示重算的账户数、流水数和最大批次序号；account 日志里记录了操作人。
- AC-06 重建时没有过账流，或与入账并发冲突，分别显示明确提示，不显示成功。
- AC-07 有执行权限的账号能对落后的流触发追平，每次最多 200 个批次；展示本次处理批次数、处理后序号和是否已追平；未追平时显示"继续追平"和剩余数量，可以再次执行直到追平。
- AC-08 追平遇到没有 OPEN 期间或并发冲突（409）时，显示"稍后重试"类提示，已处理的部分在进度上可见。
- AC-08a 追平遇到规则拒绝（400）时，就地展示 ledger 返回的错误码和说明，并指出卡住的批次；排除原因后再次追平能够通过（本机验收：先删一条记账规则制造拒绝，补回后重放）。
- AC-09 只有查看权限的账号看不到重建 / 追平按钮，直接调用执行接口返回 403；无查看权限的账号看不到菜单。
- AC-10 billing、account、ledger 任一服务不可用时，只有对应段落显示错误并可重试，其余段落正常。
- AC-11 用合成数据制造"ledger 落后"和"余额被改写"两种情况，分别通过追平和重建恢复到一致。只在本机验收；mor-test 只验证页面，以及在数据一致时执行重建和追平，结果为"无变化 / 已追平"（S-03）。

**视觉 / 交互验收**

- AC-V1 页面顶部是主体 + 币种选择，下面按"billing → account → ledger"从左到右（窄屏从上到下）展示三段，有差距的段落用醒目颜色和差额数字标出。
- AC-V2 执行类按钮放在对应段落旁，不平铺在页面顶部；确认弹窗用一两句话说明影响和可重复执行。
- AC-V3 批次浏览风格与现有明细账页一致，可以返回进度页并保留选择。
- AC-V4 en / zh-CN 两种语言、1440 / 390 两种宽度下，经真实浏览器走查通过，无横向滚动。

## 9. 已确认事实、假设与待确认

**已确认事实（只读核对，2026-10-30）**

- F-1 account 已有 `AccountPostingApi`：`GET /progress`（已应用事实数、最大 factId、各流最大序号和最后入账时间）、`GET /`（按流和起始序号分页，每页 ≤ 200）、`GET /{postingId}`、`POST /streams/rebuild`（请求体含 `operatorId`，只用于日志审计）。其中运营台只接了批次详情。
- F-2 billing 已有 `GET /progress`：未发布 / 已发布事实数和最大事实号，原本供 ledger 关账比对使用。
- F-3 ledger 已有 `POST /posting-streams/v1/catch-up`，操作人通过 `X-Gateway-Actor-Subject` / `X-Gateway-Session-Id` 传入，注释写明"本期不接控制台"。ledger 的 API 模块里**没有**按流查询已消费序号的只读接口（关账步骤在 ledger 内部读取）。
- F-4 余额页已经展示 Client 的保证金和追偿应收；明细账页有科目筛选。account 的入账映射规则里没有写入这两类账户的规则。
- F-5 account 的桶移动来源全部绑定业务（到期、出款、缴税），没有人工类型。

**假设（阶段 2 核对）**

- A-1 account 批次列表的字段足够展示（序号、来源事实、时间、流水数）。
- A-2 运营 BFF 已有 account 和 ledger 的出站客户端，billing 客户端已用于"计费事实"页，可以复用。

**待确认（需要你决定）**

- **Q-1 执行操作的留痕。** account 重建的 `operatorId` 现在只写 INFO 日志。
  - 建议：本期沿用日志留痕，ledger 追平沿用其现有的操作人记录方式，不新增审计表。理由：两个操作都不改流水、可重复执行，风险低。
  - 备选：在 account 新增重建记录表（谁、何时、结果），多一张表和 DDL。
- **Q-2 ledger 已消费序号从哪来。** ledger 没有对外的查询接口（F-3）。
  - 建议：ledger 新增一个只读接口，按主体 + 币种返回各流已消费序号（数据已在 ledger 库中，关账步骤也在用），R1 的第三段和 R4 的入口依赖它。
  - 备选：不展示 ledger 段，只提供"追平"按钮，由追平结果告诉运营是否已追平。改动更少，但运营看不到落后多少。
- **Q-3 死信事实。** 映射失败的计费事实进入 `account.billing.dlq`，现在没有地方能看到。
  - 建议：本期不做，记为遗留。要做的话需要 account 把失败事实落库或读取 RabbitMQ 队列，属于另一类改动。
- **Q-4 页面位置。** 建议放在"财务"菜单下，作为独立页面"明细账运维"，与"明细账""余额查询"并列。备选：作为明细账页的一个页签。

**阶段 2 确认的调整（2026-10-30）**

- S-01：account 重建结果新增"余额有变化的账户数"（可选字段）。
- S-02：追平每次最多 200 个批次，未追平显示"继续追平"。
- S-03：写入式验证（改余额、制造 ledger 落后、制造规则拒绝）只在本机做。
- R4 调整：追平定位为"排除原因后重放"，展示卡住的批次和失败原因（用户质疑"ledger 是下游，追平合理吗"后确认）。ledger 定时自动追平临时故障记为遗留。
