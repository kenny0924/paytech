# platform-support：多语言发布变更记录

状态：阶段 1 已确认（2026-10-30）

## 1. 来源与背景

用户在运营控制台「多语言 → 发布」打开发布弹窗时，`release-precheck` 用时 10 秒（mor-test，2026-10-29）。排查结论（只读测量，未改代码）：

| 现象 | 实测 | 原因 |
|---|---|---|
| 发布预检 `GET …/applications/{app}/release-precheck` | 单独调用 5.6—8 s，与其他请求并发时 10 s | 为算「与线上相比」的变更摘要，逐个读取线上发布（operations-console 第 23 版）的 52 个语言包文件；每读一个都去 Vault 解密一次存储凭据（一次预检 52 次 REVEAL）、新建存储客户端，串行约 75 ms / 个，合计约 3.8 s；另外 key 与翻译被查询两遍（覆盖率一遍、摘要一遍） |
| 版本差异 `GET …/releases/{no}/diff` | 6—9 s，其中一次 Gateway 504 | 读两次发布共 104 个语言包 |
| 发布 `POST …/releases` | 同样先算变更摘要 | 同上，发布也会读一遍线上语言包 |

根因不在读取速度本身，而在数据设计：数据库只保存「当前文案」，不保存「某次发布时的文案」，所以与线上比较只能把已发布的语言包文件读回来展开。已发布版本不可变，却在每次打开弹窗、每次查看差异时被重复读取。

用户 2026-10-29 结论：「这么读是不对的」；不采用全量快照（数据会随发布次数膨胀），确认**方案一 + 方案二都做**。

## 2. 目标

1. 预检、发布、版本差异在请求处理过程中**不再读取语言包文件**，只查数据库。
2. 数据增长只与实际改动量相关，不随发布次数 × key 总数膨胀。
3. 结果与现行算法一致；接口合同、BFF、前端不变。

## 3. 方案要点（已与用户确认的方向，细节在阶段 3 设计）

- **方案一：修订号标记（用于预检与发布的变更摘要）**
  - 应用已有 `content_revision`（每次写入推进一次），发布已记录 `based_on_content_revision`。
  - 在 key 与翻译行上记录「创建 / 最后变化时的修订号」（`t_i18n_key` 两列、`t_i18n_translation` 一列，阶段 3 定名）。
  - 预检：取线上发布的修订号 R，按 `> R` 用 SQL 分出新增、废弃、原文变化、各语言译文变化；回滚后与哪一版比就用哪一版的 R。
  - 不新增表，数据零增长。
- **方案二：发布变更明细（用于版本差异与切回确认）**
  - 新表（阶段 3 定名，暂称 `t_i18n_release_change`）：每次发布只记录相对上一发布号的变化条目——key、语言、变化类型、改前文字、改后文字。
  - 在发布流程中生成，生成过程不读语言包文件（改前文字取自变更明细本身的历史，阶段 3 设计）。
  - 版本差异与「切回此版本」确认弹窗（任意基准版本）改为查询该表。
  - 行数 = 实际改动条数。
- 预检中 key 与翻译只查询一次，覆盖率评估与变更摘要共用。

## 4. 本期范围

- Platform Support 多语言模块：上述两列/三列、新表、写入口打标、预检 / 发布 / 版本差异改造、测试。
- PDManer 模型、DDL、一次性基线脚本（见 Q1）、mor-test 部署。
- 适用于全部多语言应用（operations-console、client-console 等），不按应用区分。

## 5. 不做项

- 不改语言包文件的生成、存储、公开地址与前端加载方式；manifest 与语言包合同不变。
- 不改覆盖率算法与发布门槛（覆盖率计算约 1 s 的耗时不在本期优化范围，若阶段 2 证明是主要剩余耗时再单列）。
- 不改文件服务的存储凭据读取方式（每次读取解密凭据的问题在多语言不再读文件后不再影响本场景；文件服务自身的连接复用另立）。
- 不改 Operations BFF、ops-web、client-console-web、Gateway 注册、语言包内容。

## 7. 验收标准

功能：

- **AC-01** 发布预检过程中不读取语言包文件：一次 `release-precheck` 期间 Vault 的 REVEAL 次数为 0，文件服务读取次数为 0。
- **AC-02** 发布预检耗时：mor-test operations-console 连续 5 次单独调用，中位数 ≤ 2 s（现状 5.6—8 s）。
- **AC-03** 预检变更摘要与现行算法一致：mor-test 现有数据上新旧结果逐项相同（新增 / 废弃 / 原文变化 key 数与示例、各语言译文变化数）；auto 测试覆盖新增 key、废弃 key、恢复 key、改原文、改译文、导入译文、切回旧版本后再预检。
- **AC-04** 发布不再为变更摘要读取线上语言包；发布报告中的变更摘要与现行一致。
- **AC-05** 发布后生成变更明细：行数等于该版本相对上一发布号的实际变化条数；每行含改前、改后文字。
- **AC-06** 版本差异（默认上一版、指定任意 `baseReleaseNo`、发布记录页「切回此版本」确认）不读取语言包文件，结果与现行算法一致；mor-test 单次 ≤ 1 s，不再出现 504。
- **AC-07** 已有发布按 Q1 的结论处理，处理后预检与差异立即可用；脚本人工执行、可重复执行不重复写入，有核对与回滚说明。
- **AC-08** 接口合同不变：Operations BFF、ops-web、client-console-web 不改代码，现有 BFF 与 Web 测试通过；发布弹窗、发布记录页在 mor-test 浏览器中显示正常（1440 / 390）。
- **AC-09** 数据增长：一次发布新增的变更明细行数与改动条数一致；不存在按全量 key 复制的写入。

视觉 / 交互：本需求不改页面；只验证发布弹窗打开明显变快、发布记录页差异与切回确认显示正常（AC-08）。

## 8. 关键决定与待决问题

已确认（2026-10-29 用户）：

- D1 读取已发布语言包来比对的做法不对，改为数据库方案。
- D2 不做全量快照；方案一（修订号标记）+ 方案二（变更明细）都做。

- D3（2026-10-30）Q1 采用建议。
- D4（2026-10-30，阶段 2）调整 D2：只做方案二（发布变更明细，可还原任意版本），不加修订号列；理由见 [technique.md](./technique.md) 2.3—2.4。

待确认：

- ~~Q1 已有发布的处理~~（已定 D3）。原建议：一次性人工脚本把现有发布（mor-test 两个应用共 31 次）的语言包各读一次，按发布号顺序生成变更明细，并把修订号列初始化为当前线上发布的修订号；之后不再读文件。备选：只从下一次发布开始记录，之前的版本差异显示「无变更明细」。
- Q2（阶段 3 技术细节，不需要现在决定）：key 在两次发布之间「先废弃后恢复」等少见序列下的精确分类方式，阶段 3 给出设计并以测试证明与现行算法一致。
