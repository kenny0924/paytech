# platform-support：工作流

状态：**阶段 1 已确认**（2026-10-21，Q1—Q5 按建议，补充启动表单 C12）。确认记录见 [delivery.md](./delivery.md)，技术方案见 [technique.md](./technique.md)（阶段 2 起编写），设计讨论稿见 [design-discuss/workflow](../../../design-discuss/workflow/design.md)。

## 1. 背景

- **跨部门协同没有流水线。** 上线一个新渠道要商务改产品、风控配规则、渠道配账号 / MID / 路由等，各部门在各自页面完成，进度靠口头同步，看不到“走到哪一步、这一步做完了什么、能不能放行”。
- **审批各自为政。** Finance 人工调整、期间关账、记账规则版本、billing、渠道成本方案、commercial 等各自在本服务做 Maker-Checker，部分 Maker / Checker 仍由请求传入。
- **原规划的独立服务只有占位。** [目标架构 V2](../../../agent-docs/decisions/2026-10-17-target-architecture-v2.md) 规划了独立服务 `workflow-approval`（18121、`mor_workflow_approval`），D13 规定“审批引擎只记录人已同意；业务服务执行时重新校验并记录最终决定；审批通过 ≠ 可执行”。目前它只有 `paytech/workflow-approval/README.md` 占位，没有工程和表。

用户 2026-10-21 决定：

- 工作流不做独立服务，作为 Platform Support 的一个模块 `paytech-platform-support-workflow` 存在，表放 `mor_platform`。
- 工作流不只是审批，是“流程 + 节点动作”：最简单的用法是审批流，复杂的用法是给节点挂上可配置的动作。

## 2. 目标

1. Operations 人员能用流程图配置流程：节点、连线、分支判断、并行。
2. 节点可以配置审批人，也可以挂动作。动作有输入、输出和验证，能体现“这个节点要做什么、做完没有”。
3. 动作来自可维护的动作目录，按类型配置，可复用。
4. 一个流程实例把跨部门工作串在一条线上：一眼看到当前节点、每个动作的完成情况与证据、能否放行。
5. 守住 D13：工作流只记录“已完成、已同意”，不替业务 Owner 写数据，不当业务执行开关。

## 3. 概念

| 概念 | 说明 |
|---|---|
| 流程定义 | 用流程图配置的模板（如“新渠道上线”）。草稿可改，发布后成为不可变版本；再修改即生成新版本 |
| 流程版本 | 发布后的不可变快照。实例启动时绑定版本，之后不受新版本影响 |
| 节点 | 开始、结束、任务节点、排他网关、并行分叉、并行汇合 |
| 动作模板 | 动作目录中的一条可复用配置：类型、输入定义、输出定义、验证方式 |
| 节点动作 | 任务节点引用的动作模板，带必选 / 可选、默认执行人、输入参数映射 |
| 流程实例 | 一次具体运行（如“上线 Geidea 沙特”），带标题与启动变量 |
| 实例变量 | 启动变量和各动作输出的集合；分支条件与下游动作输入从这里取 |
| 验证结果 | 动作一次验证的结论（通过 / 未通过）、时间、证据与未通过原因 |

## 4. 本期范围（草案）

- **R1 归属调整：** 新增决定记录，把 `workflow-approval` 并入 Platform Support（D13 的语义保留）。清理 `workflow-approval` 的目录、Reactor 注释、服务目录（`services.yaml`、`ServiceCatalog`、`YamlEventCatalog`）、本地环境端口表，以及 commercial 设计稿 / 决定中的引用。
- **R2 流程定义与流程图：**
  - 流程定义的新建、草稿编辑、发布、停用、版本列表。
  - 流程图编辑器：拖放节点、连线，配置节点属性。
  - 发布时做合法性校验（见 B1）。
- **R3 动作目录：** 有权限的人维护动作模板：新建、编辑、停用。本期动作类型：

  | 类型 | 做什么 | 输出 | 验证 |
  |---|---|---|---|
  | `FORM` 表单 | 按配置的字段填写结构化数据 | 各字段值 | 字段规则（必填、类型、长度、枚举） |
  | `FILE_UPLOAD` 上传文件 | 经 Platform file-document 上传 | 文件 ID | 文件存在且类型 / 数量符合配置 |
  | `PAGE_TASK` 页面任务 | 跳到某系统页面完成操作，按参数映射带上实例变量 | 确认说明 | 本期为人工确认；以后可改为数据查询验证 |
  | `MANUAL_CONFIRM` 人工确认 | 执行人确认已完成 | 确认说明 | 记录确认人与时间 |
  | `DATA_QUERY` 数据查询（**预留**） | — | 查询结果中的指定列 | 调用 data-service 执行其维护的查询，按通过条件判断；本期只预留类型与配置结构，不实现 |

- **R4 节点配置：**
  - 审批人：可配置多个 Platform 用户，审批方式为 `ANY`（任一人同意）或 `ALL`（全部同意）。
  - 节点动作：引用动作模板，标 `MANDATORY` / `OPTIONAL`，配置默认执行人与输入参数映射（来自实例变量或常量）。
  - 排他网关：按顺序配置条件和一条默认分支。
- **R5 实例运行：**
  - 启动表单：流程版本配置启动表单（与 `FORM` 动作共用字段定义：单行 / 多行文本、数字、布尔、枚举、日期、文件；文件可多份），提交后成为 `start.*` 实例变量，之后不可修改。
  - 启动：选择已发布版本，填写标题、业务关联键（可选）与启动表单，可修改各节点的执行人 / 审批人。
  - 节点激活后，执行人完成动作并触发验证。
  - 节点按 B3 规则流转；排他网关按 B4 选择分支；并行分叉同时激活各分支，汇合点等全部分支完成。
  - 发起人或有权限的人可终止实例。终止后实例只读。
- **R6 审批与转交：**
  - 审批人可以同意、退回修改、驳回、转交。
  - 执行人可以转交自己的动作。
  - 驳回规则见 B5。转交和审批都保留历史。
- **R7 我的待办：** 按当前登录用户列出待执行的动作和待审批的节点，带实例标题、节点、停留时长和跳转入口。统一收件箱（mailbox）以后做，见第 5 节。
- **R8 实例列表与详情：**
  - 列表：按流程、状态、发起人、我参与的筛选。
  - 详情：在流程图上高亮已完成 / 进行中 / 未到达的节点；节点面板列出动作、执行人、验证结果与证据、审批记录、驳回与转交历史。
- **R10 节点状态通知与业务回调（2026-10-21 用户新增，回调只走 MQ 已确认）：**
  - 节点和实例状态变化时，按配置的规则执行动作。
  - 节点级触发：节点激活、进入待审批、节点通过、退回修改、被驳回、动作验证未通过、转交。
  - 实例级触发：发起、完成、终止，在“流程设置”中配置。
  - 规则动作一：**通知人员**。对象为执行人、审批人、发起人或指定用户；渠道为我的待办和邮件，邮件走 Platform Delivery。
  - 规则动作二：**业务回调**。按配置的回调编码，向 `topic_platform_workflow_event` 发布可靠事件，订阅系统据此处理。事件只是通知，订阅方执行前须自行校验业务事实（D13）。
  - 每次通知和回调都记录投递状态（已送达、重试中、失败），实例活动记录中可见，失败的可以手动重试。
- **R9 Operations 页面与注册：**
  - 页面：流程定义（列表 + 流程图编辑器）、动作目录、流程实例（列表 + 详情）、我的待办。
  - 注册：新增 Console Resource、权限、Route 注册数据，块号在阶段 3 按 live `mor_platform` 选定。

## 5. 不做

- 动作自动调用业务系统的写接口（自动执行）。工作流不写任何业务 Owner 的数据，数据由人在 Owner 页面录入。
- `DATA_QUERY` 的实现，以及 data-service 的查询能力（SQL 由 data-service 维护，属于 data-service 后续切片）。
- 统一收件箱 mailbox 模块（内部待办事件的统一收纳）。本期由 workflow 提供“我的待办”。
- 子流程、定时器、超时自动处理、复杂会签（如三人中两人同意）、可视化表达式编辑器、脚本条件。
- 按角色或部门分配执行人 / 审批人。只能指定具体的 Operations 用户。
- Client / Partner 端使用。本期只对 Operations 开放。
- 迁移现有各服务的 Maker-Checker。审批能力稳定后逐个单独立项。
- 让业务服务把“实例已完成”作为执行前提的接入。如需要，由 Owner 单独立项，且 Owner 执行时仍须自行校验。

## 6. 业务规则（草案）

- **B1 发布校验：**
  - 恰好一个开始节点、至少一个结束节点，所有节点从开始可达，且都能到达结束。
  - 并行分叉与汇合成对，不能跨分支连线。
  - 排他网关有且只有一条默认分支。
  - 任务节点至少有一个审批人或一个动作。
  - 引用的动作模板都处于启用状态。
  - 条件引用的变量必须在启动变量或上游动作输出中声明。
- **B2 动作与验证：**
  - 执行人提交动作后触发验证，可以重复提交、重复验证，节点放行前以最后一次验证为准。
  - 每次验证保存结论、时间、证据和原因。
  - 验证调用失败或超时算“未通过”，可重试，不会误判为通过。
  - 节点放行后，动作锁定。
- **B3 节点放行：**
  - 必选动作全部验证通过后，节点进入可放行状态，可选动作不阻塞。
  - 无审批人的节点，此时自动放行。
  - 有审批人的节点，此时才开放审批：`ANY` 任一人同意即放行；`ALL` 需全部同意；任一人退回修改或驳回，即按该决定处理。
  - 同一人不能既执行该节点的动作又审批该节点。
- **B4 分支：**
  - 排他网关按配置顺序判断条件，第一个满足的分支生效，都不满足走默认分支。
  - 条件为结构化配置（变量、比较符、值），不支持脚本。
- **B5a 退回修改（2026-10-22 确认）：** 只在节点配有动作时可用。本节点开新一轮，执行人修改后重新提交、重新验证，再重新审批；不触及上一节点，并行分支第一个节点也可以用。不回退任何数据。
- **B5 驳回：** 驳回只退回实例**实际走过**的上一个节点，不回退任何数据。被退回的节点重新激活，再次提交时其必选动作全部重新验证。在并行结构中：

  | 位置 | 能否驳回 | 行为 |
  |---|---|---|
  | 分支内第 2 个及以后的节点 | 可以 | 在本分支内退回上一节点，其他分支不受影响 |
  | 分支第一个节点 | 不能 | 上一节点是并行分叉，退回会牵连其他分支 |
  | 汇合后的第一个节点 | 可以 | 审批人指定退回哪一条分支的最后一个节点；其他分支保持已完成，汇合点重新等待这条分支完成 |
  | 流程第一个任务节点 | 不能 | 没有上一个任务节点；发起人可终止实例 |

- **B6 人员：**
  - 执行人、审批人只能是 Operations Realm 的具体 Platform 用户。
  - 流程版本里配置的是默认人选，启动实例时可以修改。
  - 运行中只能通过转交变更人员。
- **B7 边界（D13）：**
  - 工作流只记录“谁在何时完成了什么动作、谁同意 / 驳回了什么”，以及动作输出和证据。
  - 不复制业务对象，不调用业务写接口，不作为业务执行开关。
  - 页面任务的跳转只带参数，数据由 Owner 页面写入。

## 7. 验收标准（草案）

| 编号 | 验收标准 |
|---|---|
| AC-01 | 能在流程图编辑器中配置包含任务节点、排他网关、并行分叉 / 汇合的流程，保存草稿后再打开时图与配置一致 |
| AC-02 | 违反 B1 任一条的流程不能发布，并指出具体节点和原因 |
| AC-03 | 发布后修改生成新版本；已运行的实例仍按原版本执行 |
| AC-04 | 动作目录可维护 `FORM`、`FILE_UPLOAD`、`PAGE_TASK`、`MANUAL_CONFIRM` 四类模板；`DATA_QUERY` 可见但标为未开放，不能被发布的流程引用 |
| AC-05 | 纯审批流：节点只配审批人，按 `ANY` / `ALL` 正确放行或驳回 |
| AC-06 | 必选动作未全部验证通过时，节点不能放行、不开放审批；可选动作未完成不阻塞 |
| AC-07 | 验证结果（结论、时间、证据、原因）在实例详情中可见；重复验证以最后一次为准 |
| AC-08 | 排他网关按条件选择分支，无条件满足时走默认分支 |
| AC-09 | 并行分支同时激活，汇合点等全部分支完成后才继续 |
| AC-10a | 审批人退回修改后本节点开新一轮，上一轮记录保留，重新验证、重新审批；纯审批节点没有“退回修改”选项 |
| AC-10 | 驳回行为符合 B5 全部情形；被退回节点再次提交时重新验证 |
| AC-11 | 同一人不能审批自己执行过动作的节点；只有被指派的人能执行动作和审批 |
| AC-12 | 转交后待办转移给新人，历史可见 |
| AC-13 | “我的待办”只列出当前用户的待执行动作与待审批节点 |
| AC-14 | 实例终止后只读；终止和完成的实例不出现在待办中 |
| AC-15 | 工作流不调用任何业务服务的写接口，Platform 不写其他系统的库（代码与测试可证） |
| AC-16 | `workflow-approval` 的占位目录、坐标与文档引用已按 R1 清理，决定记录已登记 |
| AC-17 | 节点或实例状态变化时，按规则通知到指定人员（我的待办 + 邮件），并发布带回调编码的业务事件；状态变化提交后才发送，事务回滚时不发送 |
| AC-18 | 回调与通知的投递状态在活动记录中可见；失败后自动重试，超过上限标记失败；有权限者可手动重试 |

**视觉 / 交互：**

- 流程定义与动作目录沿用 Operations 配置列表页样式（筛选行 + 表格 + 抽屉）。
- 流程图编辑器：左侧节点面板、中间画布、右侧属性面板，发布校验错误在画布上标出对应节点。
- 实例详情：上方流程图高亮进度，点节点在右侧展开动作、证据与审批记录。
- 待办：表格加跳转入口。
- 空状态与错误反馈沿用现有组件。页面在阶段 3 出原型评审。

## 9. 已确认问题（2026-10-21 用户“按照建议来”）

| 编号 | 问题 | 结论 |
|---|---|---|
| Q1 | 谁能发起实例、谁能终止？ | 有“发起流程”权限的 Operations 用户都能发起；发起人和有“管理流程实例”权限的人能终止 |
| Q2 | 实例变量支持哪些类型？ | 字符串、数字、布尔、枚举、日期、文件 ID；文件字段可多份（C12），其余单值，不支持嵌套对象和列表 |
| Q3 | 实例要不要关联一个业务对象（如渠道编码）方便检索？ | 加一个可选的“业务关联键”（文本，如 `CHANNEL:GEIDEA-SA`），只用于检索和展示，工作流不解释它的含义 |
| Q4 | 流程定义能否停用？停用后在途实例怎么办？ | 可以停用，停用后不能发起新实例，在途实例照常运行到结束 |
| Q5 | 阶段安排 | 走完整流程。阶段 2（现状差异）与 3（方案）合并评审，因为 workflow 是新模块，现状差异较少；阶段 6—8 按惯例部署 mor-test 后本地提交 |
