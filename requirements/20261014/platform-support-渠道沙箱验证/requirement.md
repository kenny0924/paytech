# 渠道标准 API 实现的沙箱验证与证据留存

- 日期：2026-10-14
- 状态：**已确认**（2026-10-14）
- 主入口 / Owner：Platform Support（外部 API 配置与执行）；Operations Console（页面）
- 技术方案：[technique.md](./technique.md)；确认记录：[delivery.md](./delivery.md)

## 1. 背景与目标

外部 API 配置保存即生效，没有发布版本。用户希望在 **Operations 页面**上，对“接入方 × 标准 API”的实现做**沙箱实测**：维护验证用例和参数，运行后保存结果，证明在某个时间点、某套配置版本下，该实现对渠道沙箱的实际行为符合预期。

PayerMax UAT 联调不再使用本地账号文件和脚本，改为本功能的第一批用例，在页面上完成（[PayerMax 接入阶段 4](../platform-support-PayerMax接入/delivery.md)）。

## 2. 页面上的使用方式

在 Operations “外部接入 → 某接入方”工作区新增 **“验证”** 页签：

1. **验证账号：** 录入渠道沙箱账号（如 PayerMax 的 appId、商户号、密钥版本、商户私钥、PayerMax 公钥），保存后供用例使用。
2. **验证用例：** 选择标准 API、填写输入参数（订单号等可写成每次自动生成）、写期望结果；一个用例可以有多个步骤，后一步可引用前一步的输入或输出（例如“下单 → 用同一订单号查询，应为 PENDING”）。
3. **运行：** 点击运行，系统真实调用渠道沙箱。
4. **验证结果：** 每次运行保存时间、操作人、实际参数、渠道返回（脱敏原文）、经过的节点、每条期望是否满足、最终通过与否，以及当时引用的配置版本。配置之后改过的，页面提示“需要重新验证”。

## 3. 用户决定（2026-10-14）

| 决定 | 内容 |
|---|---|
| 目标 | 沙箱实测并保存验证结果，不做离线回放 |
| 证据 | 保存脱敏后的渠道请求/响应原文 |
| 入口 | 全部在 Operations 页面完成，不使用本地配置文件 |
| 账号材料 | 验证用的沙箱密钥**不是敏感信息**，直接保存在 Platform 数据库，不写入 Vault |
| 排期 | 先做本功能，PayerMax UAT 联调作为第一批用例 |

## 4. 本期范围

- Platform：验证账号、验证用例、验证运行的保存与查询；沙箱验证执行（复用正式执行链路并记录轨迹）；异步运行；出站地址的沙箱标记。
- Operations BFF 与页面：“验证”页签（账号、用例、运行与结果）；出站地址的沙箱标记编辑。
- 新增管理接口的 Gateway 路由与权限注册数据（SQL，执行需单独授权）。
- 本机端到端，并以 PayerMax UAT 作为首批用例。

## 5. 不做

- 离线回放、模拟渠道响应。
- 需要人工操作的步骤（如浏览器付款）；本期用例只包含能自动完成的步骤。
- 定时自动重新验证（数据结构不阻碍以后增加）。
- 保存配置时自动运行或阻止保存。

## 6. 验收标准

1. 能在页面上维护验证账号与多步骤用例，运行后看到每步结果、期望核对、节点轨迹与脱敏报文。
2. 运行记录保存配置版本；任一相关配置变更后，页面显示“需要重新验证”。
3. 只能对标记为沙箱的出站地址运行；正式执行接口的行为、响应与“不持久化报文”的规则不变。
4. 用 PayerMax UAT 跑通“下单 → 查询 PENDING”与“查询不存在的订单”两个用例并保存通过记录。
