## 1. 背景

Vault V1 的数据类型（Data Type）与访问规则（`caller_service + action + data_type + purpose`）写在部署时的静态策略文件里，进程启动时加载一次。新增或调整数据类型、给某个服务开通 Protect/Reveal，都要改文件、重启 Vault，运营无法自助，也没有变更记录。

运营排查问题时，偶尔需要把某个 Token 还原成原值核对（例如核对客户联系方式）。另外，渠道 API 凭据等密钥需要由运营自行加密：把密钥交给 Vault 保护，拿到 Token 后写入业务表（例如 Payment `t_channel_account` 的账号配置 Token），业务系统运行时再按自身权限读取。目前这两件事都只能由研发直接调用内部接口，没有权限控制、理由记录和操作人审计。

## 2. 目标

1. 运营在 Operations Console 中查看、新增、调整 Vault 数据类型及其访问规则，保存即发布新版本并记入审计，Vault 无需重启即生效。
2. 有权限的运营人员在 Operations Console 中对指定数据类型执行手动加密（Protect）与手动解密（Reveal），每次操作必须填写理由并留下可追溯到操作人的审计。

## 3. 现状与约束（已确认事实）

| 事实 | 依据 |
|---|---|
| 策略是部署配置，不是数据库表；缺失策略即拒绝 | Vault V1 三表设计 |
| V1 只承诺三表模型与 Protect/Reveal；新能力需由真实消费者触发窄范围 V2 设计 | D2 决定 |
| 数据类型目录受控：新类型须先完成数据分类审批；禁止卡数据、登录密码、根密钥等 | Vault 架构 §数据范围 |
| Vault 访问审计只记录调用服务，不记录人工操作人 | `t_vault_access_event` 结构 |
| 完整 Token 不得进入外部 API、普通日志、MQ | Vault 架构 Token 规则 |
| 人工查看敏感值须带工单号与理由码并审计（历史设计要求） | Vault 架构 §授权上下文 |
| `CHANNEL_ACCOUNT_CONFIG_V1` 托管渠道 API 凭据，属于 Secret 例外类型 | 2026-09-21 / 2026-10-13 决定 |

## 4. 使用者与场景

| 使用者 | 场景 | 成功结果 |
|---|---|---|
| 安全/平台管理员 | 新增数据类型或调整规则，填写变更理由后保存 | 立即发布新策略版本，Vault 在约定时间内生效；审计记录操作人、时间、变更前后差异与理由 |
| 运营（具备解密权限） | 输入 Token、选择用途、填写理由与工单号后解密 | 看到原值（默认遮罩，点击显示，限时自动隐藏）；审计记录操作人、理由、工单号 |
| 运营（具备加密权限） | 选择允许人工加密的数据类型与用途（如 `CHANNEL_ACCOUNT_CONFIG_V1` / `CHANNEL_ACCOUNT_SETUP`），以密码框输入或粘贴密钥，填写理由与工单号后加密 | 一次性看到 Token 并可复制，用于写入业务表；页面不回显、不保留密钥；审计记录操作人，不含原值与完整 Token |
| 任意运营 | 查看策略版本历史与手动操作审计 | 可按时间、操作人、数据类型筛选；不显示原值与完整 Token |

## 5. 本期范围与不做项（草案）

**包含**

- 数据类型维护：编码、Token 模式、说明、数据级别（普通敏感 / 密钥）、是否允许人工加密、是否允许人工解密、启用/停用。
- 访问规则维护：调用服务 × 动作 × 数据类型 × 用途。
- 策略变更保存即发布新版本（不需要审批），每次变更记入策略审计（操作人、时间、差异、理由）；Vault 热加载最新版本。
- 手动加密、手动解密页面与接口；功能权限（普通敏感与密钥类分开授权）、理由、工单号、操作人审计；结果展示与自动隐藏。
- 策略版本历史、手动操作审计查询。
- Operations Console 菜单、权限点、Gateway 路由注册（Platform 配置数据）。

**不做**

- 卡数据、登录密码、根密钥及任何禁止类型；批量加解密、导出。
- Binding、Retire/Destroy、Blind Index、Masked Value、密钥轮换等 V1 之外的能力。
- 强服务身份（mTLS/Workload Identity）、生产 KMS。
- Client / Partner 控制台。
- 已有数据类型的 Token 模式变更（已有记录时不可改，见 D6）。

## 6. 决策点（已确认）

| 编号 | 问题 | 建议 |
|---|---|---|
| D1 | 维护范围只含数据类型，还是同时含访问规则？ | **已确认：同时维护**。只有数据类型而没有规则，新类型无法被任何服务使用 |
| D2 | 策略存储与生效方式 | **已确认：**策略迁入 Vault 数据库（新增策略表，版本化发布）；Vault 定时检查并热加载已发布版本；原静态文件仅作首次导入 |
| D3 | 策略变更是否需要审批？ | **用户已明确：不需要审批**，保存即生效；每次变更记入审计（操作人、时间、变更前后差异、理由），可按版本追溯 |
| D4 | 手动解密的管控 | **用户已明确：密钥类也可人工解密，由功能权限控制。** 两层控制：① 数据类型开关“允许人工解密”；② 功能权限——“解密普通敏感数据”与“解密密钥类数据”为两个独立权限点，后者单独授予。必填理由码与工单号；结果默认遮罩、显示 30 秒后自动隐藏、不落浏览器存储；按操作人限流；Vault 审计增加操作人、理由码、工单号。密钥类人工解密超出 2026-10-13 渠道账号读取决定的范围，阶段 3 需补一份决定记录 |
| D5 | 手动加密的用途与 Token 展示 | **已明确用途**：运营自行加密渠道凭据等密钥，把 Token 写入业务表。仅“允许人工加密”的类型可用；加密同样分“普通敏感”“密钥类”两个权限点；建议密钥类使用 REFERENCE 模式；密钥以密码框输入、提交后立即清空，不进日志、不存浏览器；Token 只在本次结果中展示一次（可复制），不进入审计、列表或普通日志；每次提交自动生成幂等键，重复点击返回同一 Token |
| D6 | 数据类型的可修改范围 | **已确认：**编码与 Token 模式创建后不可改；说明、数据级别、人工加密/解密开关、启用状态可改；不提供删除，只能停用 |

## 7. 验收标准（草案，阶段 2/3 细化）

| 编号 | 标准 |
|---|---|
| AC-1 | 运营可分页查看数据类型与规则，显示当前生效版本 |
| AC-2 | 有维护权限的运营新增或调整数据类型/规则并填写理由后保存，立即生成新的策略版本；审计可查到操作人、时间、变更前后差异与理由 |
| AC-3 | 新版本发布后，Vault 在约定时间（如 30 秒）内按新版本授权，无需重启；校验失败的变更不保存、不影响当前版本 |
| AC-4 | 发布前校验：编码格式、Token 模式不可变、禁止类型、规则引用的数据类型存在且启用 |
| AC-5 | 有解密权限的运营输入合法 Token、用途、理由码、工单号后看到原值；默认遮罩，30 秒后自动隐藏 |
| AC-6 | 无权限、类型不允许人工解密、用途不匹配、Token 不存在时给出明确错误，且不返回原值 |
| AC-7 | 每次手动加/解密在 Vault 审计中记录操作人、理由码、工单号、结果，不含原值与完整 Token |
| AC-8 | 手动加密只对“允许人工加密”的类型与已授权用途开放；生成的 Token 只在本次结果展示一次，可被业务系统按其自身规则 Reveal（如 Payment / Platform 读取渠道账号配置）；同一次提交重试返回同一 Token |
| AC-11 | 密钥类类型（如 `CHANNEL_ACCOUNT_CONFIG_V1`）的人工加密、人工解密只对持有对应“密钥类”权限点的运营开放；仅有普通敏感权限的运营操作密钥类数据返回无权限且不返回原值 |
| AC-9 | 现有服务（CCT、Platform、Payment）的 Protect/Reveal 行为与合同不变 |
| AC-10 | 页面：入口在“安全/Vault”菜单下；列表、编辑、版本与变更差异、手动加解密表单、空状态、错误提示符合 Operations Console 现有风格 |

## 8. 阶段安排（建议）

八个阶段全部适用：1 需求评审 → 2 现状差异与影响 → 3 方案/接口/数据/页面设计 → 4 研发 → 5 本地验证 → 6 test 发布准备 → 7 test 部署验收 → 8 提交归档。每阶段完成后停下等待确认。
