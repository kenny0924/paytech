# 支付反欺诈一期：自建支付风控最小闭环

- 日期：2026-10-14
- 状态：**评审稿**（阶段 1，待用户确认）
- 主入口 / Owner：Risk & Compliance（支付风控评估）；关联 Payment（支付风控步骤接入）、Commerce（经 Payment 提供消费者与网络输入）
- 技术方案：[technique.md](./technique.md)；确认记录：[delivery.md](./delivery.md)

## 1. 背景与目标

用户希望参考一批外部成熟风控规则，构建我们自己的风控体系。参考材料是本机导出的外部规则、变量和决策流（不入仓库），已整理为本机分析库。分析结论：

- 外部规则约 1300 条启用，几乎全部是**收单反欺诈**；结论分为拦截、要求验证（3DS）和放行三类。
- 支撑规则的能力按覆盖量依次是：输入字段、运营名单、实时累计（按用户/卡/设备/IP/商户在 10 分钟～24 小时窗口计数、求和、去重计数、取上一笔）、业务函数、表达式运算、评分，以及大量离线特征（30～180 天统计）。
- 规则模板集中在：单笔/累计限额、频次、多卡或多账户关联、黑白名单、地理不一致、3DS 兜底等。

Code-MoR 现状：

- Risk 已实现规则、变量、决策流的**配置与发布**，没有**运行期评估**。
- Risk 数据库设计 V1 已包含运行期所需的评估记录、Feature、实时累计事件、名单、影子运行和支付限额占用，但都未实现。
- Payment 的支付风控步骤（`RISK_CHECK`，CARD+PAY 修订后命名 `PAY_RISK`）已设计，执行器目前直接报“支付风控尚未接入 Risk”。按 Payment 已确认的设计，放行时必须同时冻结认证要求 `NOT_REQUIRED / THREE_DS_REQUIRED / CHALLENGE_REQUIRED`。

**一期目标：** 让 Payment 的每次支付尝试经过 Risk 的真实规则评估，得到可追溯的放行（附认证要求）、审核或拒绝结论；规则可基于输入字段、实时累计和运营名单编写，新规则可先影子运行再生效。

## 2. 使用者与场景

| 使用者 | 场景 | 成功结果 |
|---|---|---|
| Payment（系统） | 新支付尝试进入风控步骤，调用 Risk 评估 | 取得原评估的结论；放行时附认证要求，未放行则停止本次支付 |
| Payment（系统） | 调用超时或响应未知，按原尝试重新请求 | 取得同一评估的同一结论，不重复计数、不重复占用 |
| 风控运营 | 配置限额、频次、多卡关联、名单、地理不一致、3DS 兜底规则并发布 | 规则在下一次评估中按发布版本执行 |
| 风控运营 | 维护黑名单、白名单成员 | 命中名单的支付按规则拒绝或放宽 |
| 风控运营 | 新规则先影子运行 | 得到新旧版本结论差异汇总，确认后再正式生效 |
| 风控/排查人员 | 查某笔支付为何被拒或要求 3DS | 查到命中规则、用到的变量取值和最终结论 |

## 3. 本期范围

1. **支付评估入口：** Risk 提供支付尝试评估的内部同步接口，入参为原支付尝试身份和最小输入字段（用户、卡 Token、卡 BIN/国家、IP 与 IP 国家、支付方式、金额与币种、Client、Operating Entity 等，以阶段 3 合同为准）。同一支付尝试只做一次首次评估，重复请求返回原结果。
2. **运行期评估：** 按当前已发布的决策流和规则集执行，记录评估、变量取值、命中规则和结论。
3. **实时累计：** 评估时登记风险事件及其关联主体（用户、卡、设备、IP、Client），按窗口计算计数、求和、去重计数、取上一笔，作为规则可引用的变量。
4. **运营名单：** 黑名单、白名单及成员维护；规则可判断某个值是否在名单中。
5. **结论与认证要求：** 结论为放行、审核、拒绝；放行时给出认证要求，支持规则把结果提升为要求 3DS。附原因码。
6. **影子运行：** 候选版本旁路执行，输出与基线的结论差异汇总，不影响正式结论。
7. **第一批规则模板种子：** 单笔与累计限额、频次、多卡/多账户关联、黑白名单、IP 与卡国家不一致、3DS 兜底。只提供模板与示例规则，**阈值由我们自行设定**，不复制外部阈值。
8. **Payment 接入：** Payment 支付风控步骤调用上述接口并按结论继续或停止。该部分改动属于 Payment，由负责 Payment 的会话实施或用户另行授权（见第 7 节）。

## 4. 不做

- 模型评分、离线特征（数仓统计）、脚本函数。
- 外部设备指纹、IP 情报等供应商接入；一期只用 Commerce 已有的 IP 原值和请求头信息。
- 比值/突变类表达式运算（如“当前金额是近 30 天均值的 N 倍”）、并行决策流。
- 出款反洗钱、账户盗用（ATO）、营销、商户入驻禁限售等其他场景。
- 真实执行冷却、自动拉黑等副作用动作。
- 运营页面（名单维护、影子对比、评估查询）；一期通过内部接口和初始化数据维护。
- 照搬外部规则的阈值、名单内容或原始配置。
- test 以外环境部署与生产上线。

## 5. 用户决定（2026-10-14）

| 决定 | 内容 |
|---|---|
| 一期场景 | 只做支付（收单）反欺诈，其他场景放到后续期 |
| 设备与 IP 情报 | 一期不接供应商 |
| 失败策略 | Risk 不可用、超时或特征计算失败时**拒绝本次支付**（fail-closed），与 Payment 现有设计一致 |
| 生效流程 | 新规则先影子运行再生效；审批沿用现有发布流程，不另加双人审批 |
| 页面 | 一期不做 |
| 外部数据 | 仅作设计参考，提炼模板和能力；原始内容不进入仓库 |
| 文档登记 | 同意在 `requirements/` 下登记本需求 |

## 6. 验收标准

| 编号 | 验收标准 |
|---|---|
| AC-1 | Payment 以原支付尝试调用 Risk，得到放行、审核或拒绝之一；放行时必定带认证要求，审核和拒绝时停止本次支付 |
| AC-2 | 同一支付尝试重复请求（含超时后重试）返回同一评估身份和同一结论，实时累计不重复计入 |
| AC-3 | 实时累计在窗口边界上计算准确：恰好落在窗口起点/终点的事件按约定计入或排除；计数、求和、去重计数、取上一笔各有验证 |
| AC-4 | 主体命中黑名单的规则拒绝支付；命中白名单的规则按配置放宽（如免除部分限额规则）；名单成员失效后不再命中 |
| AC-5 | 至少一条规则把放行提升为要求 3DS，Payment 收到 `THREE_DS_REQUIRED` |
| AC-6 | 候选版本可影子运行，正式结论不受影响，输出结论变化数量等差异汇总 |
| AC-7 | 每次评估可查到所用发布版本、变量取值、命中规则、动作与最终结论 |
| AC-8 | Risk 内部失败、变量计算失败或超时时，结论为技术失败，Payment 不放行 |
| AC-9 | 第一批 7 类规则模板各有至少一条示例规则在自动化测试中通过真实评估链路命中 |

以上为接口与数据能力，不涉及页面，无视觉/交互验收。

## 7. 已知约束与待决事项

- **跨系统改动：** 本会话只负责 Risk。Payment 执行器接入（AC-1 的 Payment 侧）需负责 Payment 的会话实施或用户另行授权；Commerce 输入字段如需补充，同样需要对应授权。
- **已有设计的复核：** Payment 已确认的风控步骤设计（[内部风控 Action 修订](../../20260913/payment-Execution设计/internal-risk-action-amendment.md)、[限额关联修订](../../20260913/payment-Execution设计/risk-limit-correlation-amendment.md)、[字段精简修订](../../20260913/payment-Execution设计/execution-field-simplification-amendment.md)）及 [Risk 数据库设计](../../../agent-docs/database/RISK_COMPLIANCE_DATABASE.md)中支付决策点 `PAYMENT_ATTEMPT_RISK`、交易评估与限额占用组，是本需求的已有依据。阶段 2 逐项核对，有差异时提出调整方案，不另起一套。
- **限额占用：** 已有设计要求支付放行时执行限额占用（`RESERVE_LIMIT_GROUP`），并随支付结果释放或确认。是否纳入一期、还是一期只创建空占用组，在阶段 2 结合差异给出建议并请用户确认。
- **延迟预算：** 暂未指定。阶段 3 给出目标值（含实时累计查询）供确认。
- **数据库：** 涉及 Risk 一个数据库；DDL/DML 在阶段 3 设计，执行需单独授权。
