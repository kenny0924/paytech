# platform-support：多语言管理（前端 UI 文案）· 需求

> 状态：**阶段 1 已确认**（2026-10-22 用户：基准语言英文、暂只支持中英、不需要审核直接发布、其余按建议）。本文为 v2，已按确认结果修订。确认记录见 [delivery.md](./delivery.md)，技术方案见 [technique.md](./technique.md)（阶段 2—3 评审中）。

## 1. 背景

- **系统目前没有任何多语言基础设施。** 2026-10-22 全仓库核对：没有 `Accept-Language` 处理、没有 `MessageSource`、前端没有 i18n 库。`operations-console-web` 把 antd 写死为 `zh_CN`，约 24k 处中文硬编码，165 个"枚举 Code → 中文 label"映射表散落在页面里；`client-console-web` 约 1.4k 处中文硬编码；`checkout-web` 只有设计稿，界面为英文；`partner-console-web` 尚未开始。
- **仅有的 locale 概念在 CCT 和通知。** `consumer_legal_document`、`seller_disclosure` 已按 IETF BCP 47 locale 建模；Platform `t_notification_template_content` 已有 `locale`，`t_notification_request` 有 `default_locale`。两者都没有统一的"系统支持哪些语言"目录。
- **用户决定（2026-10-22）。** 文案分三类治理：① 前端静态 UI 文案；② 服务端产生的人类文案（报错、校验）；③ 运营录入的业务内容文本。本需求只处理第 ① 类，并采用"后端维护、发布后导出语言包"的模式：Platform 新增多语言模块，运营在后台维护各语言文案，发布生成不可变版本，每个版本导出按语言划分的 JSON 语言包，前端按版本拉取。第 ②、③ 类另立需求，但本模块的存储和发布模型要为第 ② 类预留。
- **业界参考。** Crowdin Distribution（发布生成 Hash 与 manifest，语言包按 Hash 路径静态拉取）、Tolgee Content Delivery（按 namespace 导出 `ns/en.json`，只发布已审核文案）、Lokalise OTA（bundle 绑定应用构建号）。共同点：key 和基准文案由代码侧产生，翻译在后台维护，发布为不可变版本，客户端拉静态 JSON，没有一家在运行时逐 key 查库。本需求参照该模式自建，不引入 Tolgee / Weblate 等独立产品（需要独立数据库与 UI，审批和审计脱离 Platform 体系）。

## 2. 目标

1. 运营可以在 Operations Console 维护各前端应用、各语言的 UI 文案，不需要改代码、不需要前端重新构建。
2. 发布是显式动作，生成不可变版本；线上可以回滚到任一历史版本，回滚不重新生成文件。
3. 前端运行时按版本拉取语言包；Platform 不可用或某 key 缺失时回退到构建内置的基准语言，页面永远不出现裸 key 或空白。
4. key 的集合由代码决定：运营只翻译，不能凭空新增或删除 key，避免代码引用不存在的 key 或发布无人使用的 key。
5. 存储与发布模型可以承接后续服务端报错文案（`messageKey`）和共享枚举展示名，不需要推倒重来。

## 3. 概念

| 概念 | 说明 |
|---|---|
| Locale 目录 | Platform 维护的系统支持语言清单：BCP 47 代码（如 `zh-CN`、`en`）、显示名、文字方向（LTR / RTL）、状态。各渠道默认语言也在此配置 |
| 应用（Application） | 语言包的消费方，一个应用一套 key 空间与发布线。首期登记：`operations-console`、`client-console`、`partner-console`、`checkout`，以及各端共享的 `shared`（枚举展示名等） |
| 命名空间（Namespace） | 应用内按页面或功能域划分的 key 分组，是前端懒加载与导出文件的粒度，例如 `common`、`onboarding`、`team` |
| Key | 命名空间内唯一的文案标识（如 `team.invite.submit`），带基准语言文案、开发者说明、占位符清单、状态（在用 / 已废弃） |
| 基准语言 | key 随代码登记时所带的文案语言，全系统固定为 `en`；其他语言的翻译以它为依据 |
| 翻译（Translation） | `key × locale` 的文案，没有审核状态；保存即可发布。每次修改带版本号与操作人 |
| 发布（Release） | 某个应用的一次不可变发布：冻结当时全部在用 key 和各语言已填写的文案，记录 key 数、各语言覆盖率、发布人、时间与说明 |
| 语言包（Artifact） | 每个 `发布 × locale × namespace` 一份 JSON 文件，加一份描述该发布全部文件地址与内容 Hash 的 manifest |
| 当前发布 | 每个应用在当前环境指向的发布；切换指向即上线或回滚 |
| key 导入 | 开发把代码旁的基准语言 JSON 导入 Platform 的动作；导入做差异预览（新增 / 变更 / 删除），确认后生效 |

## 4. 本期范围（草案）

- **R1 Locale 目录。** 维护系统支持的 locale（新增、启用、停用、文字方向），以及每个渠道（OPERATIONS / CLIENT / PARTNER / CHECKOUT）的默认语言。首期只登记并启用 `en`、`zh-CN`（C3）；文字方向字段保留，不登记其他语言。
- **R2 应用与命名空间登记。** 登记应用、必须覆盖的 locale 清单（发布校验用）；基准语言全系统固定为 `en`，不按应用配置。命名空间在后台创建、查看并维护名称与说明（C9）；导入只接受已创建命名空间下的 key。
- **R3 key 导入（代码 → Platform）。** 运营或开发在控制台上传应用的基准语言 JSON（按命名空间分文件或一个合并文件），系统给出差异预览：新增 key、基准文案变更的 key、代码已不再使用的 key。确认后新增 key 进入待翻译，基准文案变更的 key 把其他语言的翻译标记为"基准已变更"（翻译保留，列表可筛），删除的 key 标为已废弃（不物理删除，发布时不再包含）。首期不做 CLI 推送（C6）。
- **R4 翻译维护。** 按应用、命名空间、locale、填写状态（未翻译 / 已翻译 / 基准已变更）、关键字筛选；逐条编辑、批量粘贴；显示基准文案、开发者说明、占位符；保存时校验 ICU MessageFormat 语法可解析、占位符与基准一致。没有审核环节（C4）。导出 / 导入 XLIFF 或 JSON 供外部翻译（导入仍走同样校验）。
- **R5 发布。** 发布前校验：应用必须覆盖的 locale 翻译覆盖率达到阈值（默认 100%，可按应用配置，C8），所有翻译 ICU 可解析。通过后生成发布记录、导出语言包与 manifest（存现有文件服务），并给出发布报告（未翻译而回退基准语言的 key 清单、基准已变更仍沿用旧翻译的 key 清单）。发布需要独立权限。
- **R6 当前发布与回滚。** 查看发布历史与 diff（相对上一发布新增 / 变更 / 删除的 key 与文案）；把当前发布指向任一历史发布即回滚。
- **R7 语言包交付接口。** 为前端提供：读取某应用当前发布的 manifest（含发布号、各 locale × namespace 的文件地址与 Hash）；按地址读取语言包文件。文件地址随发布号变化，响应可长期缓存。各 Console 经自己的 BFF 匿名读取；Checkout 首期只用构建内置（C5）。
- **R8 前端接入基线。** 定义各 `*-web` 的统一接入方式：代码旁维护基准语言 JSON；构建时把基准语言包内置；启动时读取 manifest 并按 namespace 懒加载；语言切换同步 antd、dayjs locale 与 `<html lang/dir>`；缺 key 回退内置基准文案；ESLint 规则禁止 tsx 内硬编码中文。
- **R9 首期接入范围。** `client-console-web` 全量接入并提供 `en` + `zh-CN`；`operations-console-web` 新增本需求的页面（R1—R6）自身按新基线编写，其余既有页面不迁移（另立需求）。`checkout-web`、`partner-console-web` 只登记应用，不接入。
- **R10 决定记录。** 新增 `agent-docs/decisions/` 决定：三类文案的治理边界、Locale 目录归 Platform、UI 文案"后端维护、发布导出语言包"模式、key 来源于代码；更新 `DEVELOPMENT_CONVENTIONS.md` 增加前端文案与 locale 约定；`AGENTS.md` 增加路由。

## 5. 明确不做

- 不做服务端报错 / 校验文案的多语言（第 ② 类），不改 Problem 合同；本需求只预留存储模型。
- 不做运营录入业务内容（产品名、模板名、法律文档等）的多语言（第 ③ 类）。
- 不做机器翻译、术语库、翻译记忆、翻译工作量统计。
- 不做在页面内就地编辑翻译（in-context editing）。
- 不做账号偏好语言字段与登录态 locale 解析链；首期前端语言来源见 B6。
- 不做翻译审核 / Maker-Checker；不做多条发布线。
- 不迁移 `operations-console-web` 既有页面的 24k 处中文。
- 不接入独立 TMS 产品。
- 不做中英以外的语言，不做 RTL 布局实现，只在 Locale 目录预留文字方向字段。

## 6. 业务规则

- **B1 key 只来自导入。** 控制台不提供"新建 key"，但命名空间在控制台创建，key 必须属于已创建的命名空间；废弃 key 可以在发布中排除但保留历史翻译；重新导入同名 key 恢复在用状态并保留原翻译。
- **B2 基准文案变更要可见。** 基准文案变化时，该 key 其他 locale 的翻译标记为"基准已变更"并保留原文；发布仍包含它（不回退），但进入发布报告，提醒复核。
- **B3 发布内容为已填写翻译。** 未翻译的 key 不出现在该 locale 的语言包中，由前端回退到内置基准语言；发布报告列出这些 key。
- **B4 发布不可变。** 发布后的 key 集合、文案、语言包文件与 Hash 不再改变；修正文案必须新建发布。
- **B5 校验规则。** ICU MessageFormat 语法必须可解析；占位符名称集合必须与基准文案一致；`select`/`plural` 分支至少包含 `other`。校验失败不能保存。
- **B6 首期前端语言来源。** 顺序为：URL 参数 `?lang=`（仅本次会话）> 浏览器本地记忆（localStorage）> 浏览器 `navigator.language` 与启用 locale 的匹配 > 渠道默认语言。账号偏好语言与登录态解析在后续"Locale 模型"需求中接入，届时插在 URL 参数之后。
- **B7 回退顺序。** 运行时语言包缺 key → 构建内置基准语言 → 显示 key 本身并记录一次控制台告警（开发可见，不应出现在生产）。
- **B8 权限。** 维护翻译、导入 key、发布 / 回滚分别为独立权限；发布与回滚写审计事件。
- **B9 跨环境。** 发布记录属于当前环境的 Platform；mor-test 与生产各自发布，不做跨环境同步（翻译内容可用 R4 导出 / 导入搬运）。

## 7. 验收标准（草案）

**功能验收**

- AC-01 Locale 目录可新增 / 启用 / 停用 locale 并设置文字方向；停用的 locale 不能被选为必须覆盖语言，也不出现在前端语言切换中。
- AC-02 导入 client-console 基准语言 JSON：差异预览正确列出新增 / 变更 / 删除；确认后 key 状态、翻译状态按 B1、B2 变化。
- AC-03 翻译编辑：ICU 语法错误、占位符不一致时不能保存，错误提示指出具体位置；合法时保存并记录操作人与版本。
- AC-04 发布：必须覆盖 locale 翻译覆盖率不足阈值时拒绝并列出缺口；达标后生成发布记录、语言包与 manifest；发布报告列出回退基准语言与基准已变更的 key。
- AC-05 当前发布切换到历史发布后，manifest 立即返回旧发布的文件地址；旧语言包文件内容与 Hash 与首次发布一致。
- AC-06 manifest 与语言包接口：发布号变化时地址变化；同一地址重复读取内容与 Hash 不变；响应带长期缓存头。
- AC-07 client-console-web 在 `en` 与 `zh-CN` 下全部页面无裸 key、无硬编码中文（ESLint 规则通过）；切换语言时 antd 组件、日期格式、`<html lang>` 同步。
- AC-08 Platform 不可达或 manifest 读取失败时，client-console-web 以内置基准语言正常渲染。
- AC-09 导出 / 导入 XLIFF 或 JSON：导出再原样导入不产生差异；导入非法文案按 AC-03 拒绝。
- AC-10 发布历史 diff 正确显示相对上一发布的新增 / 变更 / 删除。
- AC-11 本需求新增的 Operations Console 页面自身使用新基线（key 化、`en` + `zh-CN`）。

**视觉 / 交互验收**

- AC-12 Operations Console 新增页面：Locale 目录、应用列表、翻译工作台（左侧命名空间与筛选、中间 key 列表、右侧编辑区含基准文案 / 占位符 / 校验结果）、key 导入差异预览、发布页（校验结果、发布报告、历史与回滚）。空状态、校验失败、发布被拒绝有明确反馈。原型按 [ops 原型质量约定](../../../operations-console-web/docs/operations-console.pen) 在阶段 3 提供。
- AC-13 client-console-web 语言切换入口位置与两种语言下布局不溢出、不截断。

## 8. 已确认事实与假设

- C1 第一类文案采用"后端维护、发布导出语言包"模式，模块放在 Platform Support，不独立部署（用户 2026-10-22）。
- C2 key 由代码侧产生，运营只翻译，控制台不能新建 key（用户 2026-10-22 "其余按建议"）。
- C3 基准语言为 `en`；首期只支持 `en`、`zh-CN` 两种语言（用户 2026-10-22）。
- C4 不需要审核，翻译保存后直接可发布（用户 2026-10-22）。
- C5 各 Console 经自己的 BFF 匿名读取 manifest 与语言包；Checkout 首期只用构建内置；公开桶落地后可改为固定地址（按建议）。
- C6 key 导入首期只做控制台上传 JSON 并预览差异，CLI / CI 推送延后（按建议）。
- C7 只有一条"当前发布"指针；预览指定发布用前端 `?release=` 参数（按建议）。
- C8 覆盖率阈值默认 100%，按应用可调，不足则禁止发布（按建议）。
- C9 命名空间在后台创建和查看（用户 2026-10-22，取代"随导入自动产生"）。
- A1 语言包文件复用现有文件服务存储，地址形如 `/files/v1/{fileId}`。
- A2 发布校验在 Platform 内完成；前端不参与校验。
- A3 ICU MessageFormat 作为唯一文案语法；前端用一个支持 ICU 的轻量运行时（阶段 3 选型，须符合 `TECHNOLOGY_STACK.md` 的依赖规则）。
- A4 基准语言为英文意味着开发在代码旁写英文文案；本需求新增的 Operations Console 页面也按英文基准编写，中文由翻译提供。
