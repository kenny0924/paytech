# platform-support 工作流页面体验优化：技术方案

> 状态：阶段 3 已确认（2026-10-22，用户「继续」；E 组 2026-10-22 定稿：只保留必填、放行 A）。需求见 [requirement.md](./requirement.md)，原型见 `operations-console-web/docs/operations-console.pen`「工作流 V2 · 01—12、14—16」（13 已删除）（[delivery.md](./delivery.md) 第 2 行列出节点 ID）。

## 1. 结论

- **以前端为主**：16 张原型的数据都能由现有接口提供或在前端推导；表结构不变。
- **后端三处改动**：
  - 新增「我发起的」菜单：块 127 追加 1 行 `t_console_resource`，复用现有权限，不新增授权；
  - 动作列表补一个「被引用流程数」字段：Platform 只读查询，BFF 原样透传；
  - 去掉动作验证与提交校验（需求 E 组）：只检查必填，状态改为待处理 / 已完成 / 已取消，同意时兜底检查，删除「重新验证」接口 #20 及其路由，见 4.3。
- 不新增接口，不改请求体。

## 2. 数据来源核对

| 原型元素 | 来源 | 处理 |
|---|---|---|
| 待办列表、类型、停留时长 | `GET /workflow/v1/my-tasks`（`taskType`、`waitingSince`、`definitionName`、`nodeName`） | 已有。超时 = `now - waitingSince ≥ 24h`（前端常量，Q3） |
| 「全部 12 · 填写 5 · 审批 7」 | 同一接口 `taskType=ACTION / APPROVAL`、`size=1` 取 `total` | 每次刷新列表时额外 2 个 GET，串行发出，沿用现有 `DetailQueue` 节流，避免 429 |
| 详情头部进度条 | 实例详情 `graph` + `nodeRuns` | 前端按主路径排序：已完成 / 当前 / 未到；有分支时只显示已走过的分支和当前节点，其余进「查看流程图」 |
| 背景、前序产出、附件预览 | 实例详情 `startForm` + `startValues`、`actionRuns.output`、`files` | 已有；附件预览沿用本次跟进的 INLINE 下载 |
| 「必填 3 项 · 已填 1 项」 | 当前动作模板快照的必填字段 + 表单当前值 | 前端计算 |
| 已办结果 + 实例状态 | `GET /workflow/v1/my-tasks/handled`（`result`、`instanceStatus`） | 已有；结果文案映射为 已提交 / 已同意 / 已退回 / 已驳回 |
| 我发起的：当前步骤 · 等待谁 | `GET /workflow/v1/instances?scope=MINE&startedBy=<我>`，`currentNodes[].nodeName`、`handlers[].displayName` | 已有（现「我发起的」页签就是这样调用的） |
| 我发起的：右侧时间线、小流程图 | 实例详情 + `GET …/instances/{id}/activities` | 已有 |
| 动作列表的类型页签数量 | 动作列表（全部动作一次取回，前端分组计数） | 已有 |
| 动作列表「被引用 N 个流程」 | **缺**。现在只有单个动作的引用接口 6 | **新增字段** `referencedDefinitionCount`：Platform 列表查询按当前已发布版本冻结的模板去重计数，BFF 透传；缺字段时前端显示「—」 |
| 动作抽屉「填写人看到的样子」与引用列表 | 动作详情 `config` + 接口 6 | 已有 |
| 动作编辑页修改人姓名 | 动作详情 `updatedByName` | 已有 |
| 流程卡片状态（四选一） | 列表 `status`、`currentVersionNo`、`draftVersionNo` | 前端推导：已停用 > 有草稿且有发布版本 →「已发布 vN · 有未发布修改」> 只有草稿 →「草稿 · 未发布」> 「已发布 vN」 |
| 流程卡片「本月发起 N 次」「修改人」 | **缺** | **本期不做**：卡片改显示「更新于 10-21」；发起次数要聚合查询，价值低，不为它加接口 |
| 流程卡片缩略图 | 接口 12 读版本全文 | 沿用现有按需读取（进入可视区才读） |
| 编辑器实时问题数 | 保存草稿响应的 `problems` + 前端本地检查 | 前端在 `graphModel` 增加与服务端同口径的本地检查（缺审批人、网关缺默认出口、孤立节点、未连到结束）；保存后以服务端结果为准 |
| 发布确认的变更摘要 | 定义详情的 `draft` 与当前发布版本 `versions[]` | 前端比较两版：节点增删改名、连线条件变化、启动表单字段增删、动作增删 |
| 「已发起的 N 个实例继续按 vN 运行」 | 实例列表 `definitionId` + `status=RUNNING`，`size=1` 取 `total` | 打开发布确认时读一次；需要实例查看权限，没有权限时不显示这句 |
| 就地新建动作 | 现有新建动作接口 + 草稿保存 | 新建成功后把模板加入节点草稿，不另开接口 |

## 3. 前端改动

目录：`operations-console-web/src/pages/Workflow*.tsx`、`src/workflow/*`。

### 3.1 我的待办（原型 01—04）

- `WorkflowMyTasks.tsx` 重写页面骨架：页签「待办 N / 已办」，去掉「我发起的」页签与「超过 1 天」筛选；类型切换、搜索图标、批量审批入口放在列表头部。
- 新增 `TaskInboxItem`（列表项）、`TaskDetailLayout`（头部 + 背景 + 前序产出 + 我的任务 + 底部操作栏）、`TaskStepper`（横向进度）、`TaskActionBar`（固定操作栏，主按钮在右，「更多」收转交和查看流程图）。
- `TaskPanels.tsx` 中的表单与审批内容改为放进 `TaskDetailLayout` 的「我的任务」区，提交 / 同意 / 退回 / 驳回按钮移到操作栏；表单校验改为提交时和字段失焦时显示，打开时不标红（`formModel` 增加 `touched` 状态）。
- 批量审批：新增显式模式状态 `batchMode`，进入后只列可批量的审批（沿用现有可批量判断），右侧为确认清单；退出后恢复原选中项。
- 设置与快捷键：右上 ⚙ 浮层（「处理完自动打开下一条」，仍存 localStorage），? 浮层列出快捷键；快捷键行为不变。
- 已办：列表样式同待办，右侧只读打开实例（复用 `InstanceDetailView` 的只读部分）。

### 3.2 我发起的（原型 05）

- 新页面 `WorkflowStarted.tsx`，componentKey `OPERATIONS_WORKFLOW_STARTED`，路由 `/workflow/started`；`ConsolePage.tsx` 与 `pageCapabilities.ts` 登记。
- 页签「进行中 / 已结束」对应 `status=RUNNING` / 其余；表格列：实例标题、流程、当前步骤 · 等待人、已用时长、状态；右侧时间线 + 小流程图（复用 `WorkflowCanvas` 只读缩略模式）。
- 「发起流程」按钮复用现有 `LaunchModal`。原型里的「撤回」按现有接口语义只对发起人可终止的实例显示（现有终止接口），文案用「撤回（终止实例）」，不新增撤回语义。

### 3.3 动作目录（原型 06—08）

- `WorkflowActionTemplates.tsx` 改为列表页：类型页签带数量、表格（名称、类型、被引用、状态、最近修改）、右侧只读抽屉（填写预览 + 引用流程，底部「编辑」与「⋯ 停用」）。
- 新增 `WorkflowActionTemplateEditor.tsx`，挂在已登记的子路由 `/workflow/action-templates/:templateId`（新建用 `/workflow/action-templates/new?type=FORM`）：左侧步骤导航（基本信息 / 字段设计 / 提交校验 / 引用），页头「未保存的修改」、放弃修改、保存；离开页面有未保存内容时确认。
- `FieldDesigner.tsx` 改为三栏全宽布局（字段类型 | 表单画布 | 字段属性），画布按填写效果渲染；字段类型保持现有七种。
- 新建：「新建动作」先弹类型选择（数据查询置灰，标「即将支持」），确定后进入编辑页。
- 编辑器抽出为可复用组件 `ActionTemplateEditor`，供 3.4 的就地新建抽屉使用。

### 3.4 流程定义与编辑器（原型 09—12）

- `WorkflowDefinitions.tsx`：卡片显示单一状态（第 2 节推导规则）、「更新于」、一个主按钮（已发布 → 发起；只有草稿 → 继续编辑；已停用 → 启用），其余进「⋯」（编辑、版本历史、停用，停用需二次确认）；状态筛选「全部 / 已发布 / 草稿 / 已停用」前端过滤。
- `DefinitionEditor.tsx`：
  - **页头**：状态药丸 + 问题徽标（点开为问题清单，「定位」选中并居中对应节点 / 连线）+ 页签 + 保存草稿 / 发布。
  - **画布**：左侧节点面板改为浮动竖排图标工具条（悬停说明），操作说明收进「?」。
  - **属性面板**：只在选中节点 / 连线时从右侧出现，带关闭按钮。
  - **插入节点**：连线悬停时中点显示「+」，点击弹出节点类型菜单，在该连线上插入节点（原连线拆成两段，条件留在前一段）。
- `EditorPanels.tsx`：节点属性页签「基本 / 动作 / 审批 / 通知与回调」，动作选择下拉末尾「＋ 新建动作…」打开就地新建抽屉（3.3 的 `ActionTemplateEditor`），创建成功后把该模板加入节点并关闭抽屉。
- 发布确认弹窗：变更摘要（第 2 节）+ 问题数（有问题时禁用确认）+ 运行中实例提示；确认后调用现有发布接口。

### 3.5 动作完成（原型 14—16，需求 E 组）

- **原型 13（提交要求页）删除**；动作编辑页步骤为「基本信息 / 字段设计（仅表单）/ 引用」。上传文件动作只有「说明」与「至少上传一个」开关；人工确认、页面任务只有说明（页面任务另有页面地址与参数）。
- **多动作待办（14）**：每个动作一行，状态取 `actionRuns[].status`（`PENDING` 待处理 / `COMPLETED` 已完成 / `CANCELLED` 已取消）。
  - 每行一个「完成」按钮，前端只检查必填（表单必填字段、上传「至少一个」）；扫描中不挡完成，文件旁灰字提示；已确认未通过的文件（实例元数据为隔离 / 拒绝，或 422 报告在该文件路径上）标红「未通过安全检查，请删除后重新上传」，删除前「完成」不可用。发起弹窗的 FILE 字段同一规则，删除前「发起」不可用。
  - 已完成的必选动作在节点仍为 `ACTIVE` 时可「修改」后再次完成；节点进入审批后按钮隐藏（后端同样拒绝）；可选动作在节点放行前可完成。
  - 必选计数按 `required` 统计；可选动作标「不阻塞放行」。
- **审批前查看提交内容（15）**：「动作与提交内容」表每行显示执行人、状态、完成时间（`submittedTime`）与内容摘要（表单 = 字段数，上传 = 文件名与扫描状态，说明 = 说明文字），「查看」展开完整内容，文件可预览（未通过扫描的不可预览 / 下载）。
- **节点动作配置（16）**：必选 / 可选写 `NodeAction.required`；执行人是默认执行人（`executorId`，发起时可改）；动作卡不再显示「提交要求」摘要，只显示类型与说明首行；底部提示「必选动作全部完成后才进入审批」「执行人不能审批本节点」。
- **其他前端清理**：去掉「重新验证」、验证结论 / 证据 / 历史；表单字段属性只保留显示名、字段键、类型、必填、选项（枚举）、帮助文字，去掉最大长度等校验项；通知触发选项去掉「动作验证未通过」；历史活动中的「动作验证未通过」保留文案只读显示。

### 3.6 公共

- 人名一律显示名，不显示账号 ID；技术编码只出现在动作 / 流程的「基本信息」里。
- 新组件样式写在 `workflow.css`，沿用 `$ops-*` 颜色变量对应的 CSS 变量；1280 宽度下三栏不挤压（AC-04）。

## 4. 后端改动

### 4.1 「我发起的」菜单注册（块 127 追加 1 行）

```sql
-- t_console_resource
(900000000000127311, 'OPERATIONS_WORKFLOW_STARTED', 'OPERATIONS', 'MENU', 900000000000127301, '我发起的',
 '/workflow/started', 'OPERATIONS_WORKFLOW_STARTED', 900000000000127105, 15, 'DISABLED', 1, …)
```

- 权限沿用 `900000000000127105`（与「我的待办」相同），角色授权不变，**不新增路由**（实例列表 `scope=MINE` 已在现有路由内）。
- 块 127 合计 417 → 418 行；`platform-support-schema.test.mjs` 计数同步。
- 本机 e2e 与 mor-test 各需 1 条增量 SQL（插入 ACTIVE 行并递增 PLATFORM_ADMIN 角色版本使菜单重算），执行时另行授权。

### 4.2 动作列表补引用数

- Platform 模板列表响应增加 `referencedDefinitionCount`（int）：统计引用该模板的流程定义数，口径与接口 6 一致（当前已发布版本冻结的模板，按 definition 去重）。
- 实现位置：workflow 模块模板列表查询，一条按模板 ID 批量分组的计数 SQL（单次查询，不逐条），无事务、无外部调用。
- BFF 同路径转发，字段原样透传；`workflow-boundary.json` 对应用例加字段。
- 自动化测试：在现有模板列表用例里增加「被 2 个流程引用 / 未被引用」断言。

### 4.3 去掉动作验证与提交校验（需求 E 组）

- **状态**：`ActionRunStatus` 改为 `PENDING / COMPLETED / CANCELLED`（`VERIFIED` → `COMPLETED`，去掉 `UNVERIFIED`）。存量数据一条 DML：`VERIFIED → COMPLETED`、`UNVERIFIED → PENDING`；本机 auto 库由测试自建无需迁移，本机 e2e 与 mor-test 随发布执行（另行授权）。
- **完成动作**（原提交接口 #19，路径与请求体不变）：`ActionOutputVerifier` 改为 `ActionOutputChecker`，只做必填与 E7 技术保护（类型、文件归属与地址格式、长度上限），不检查文件数量 / 类型、说明必填；扫描中不挡完成，已确认未通过（`QUARANTINED / REJECTED`）的文件须删除重传，在该文件路径（`output.files[i]`、`output.<key>[i]`）返回 422「文件未通过安全检查，请删除后重新上传」；发起时启动表单同一规则（`startValues.<key>[i]`），扫描中可以发起；不合格返回 422 字段错误、不改状态；合格直接 `COMPLETED`，不写 `t_workflow_verification`。
- **锁定**：必选动作在节点 `APPROVING` 后不可再完成 / 修改（409）；可选动作到节点放行前可完成；放行后全部锁定（原规则）。
- **放行（A）**：必选全部 `COMPLETED` 才进入审批或自动放行（原逻辑，判断条件由 `VERIFIED` 改 `COMPLETED`）；审批「同意」时在决策处理里再查一次，有未完成必选动作返回 409 并列出动作名。
- **配置兼容**：
  - 表单字段：保留 `required`、类型、枚举选项；`maxLength` 等校验键在保存时忽略并不再写入，存量配置中出现时忽略。
  - 上传文件：新增 `required`（至少一个）；存量 `minFiles ≥ 1` 视为 `required=true`，`minFiles / maxFiles / mimeTypes` 不再校验、编辑器不再写入。
  - 人工确认：`noteRequired` 忽略（说明一律选填）。
  - 已发布版本的动作快照不改，按上述规则解释。
- **删除**：「重新验证」接口 #20（Platform API / Controller / `ReverifyWorkflowActionProcessor` / 请求类、BFF 转发、前端调用）；`VERIFICATION_FAILED` 的产生逻辑（枚举值保留以兼容已发布配置，草稿校验拒绝新配置使用）。块 127 删除路由 `900000000000127429` 及其 6 行 header、6 行 guard（与 4.1 合计 418 → 405 行），本机 e2e 与 mor-test 用增量 SQL 删除（另行授权）。
- **保留**：`t_workflow_verification` 表与历史行（不再写入）；实例详情 `verifications` 字段（历史数据，前端不展示）。
- **测试**：必填缺失 422 且状态不变；类型错误 422；扫描中文件可完成、可发起；未通过扫描的文件完成与发起均 422 且落在该文件路径；合格即 `COMPLETED` 并推进节点；`APPROVING` 后改必选动作 409；同意时有未完成必选 409（构造数据）；存量 `minFiles` 兼容；删除 #20 用例；BFF 边界用例去掉 #20。

## 7. 风险

- **流程卡片缩略图并发读取触发 429**（mor-test 2026-10-22 卡 BIN / 3DS 验收 S7-02 观察到：定义页并发读详情，2 次 429、2 张缩略图空白）：S3 改为经 `DetailQueue` 串行、进入可视区才读，失败时显示占位并可重试。
- **待办计数多 2 个请求**：串行节流；如仍触发 429，改为只在列表首屏加载时取计数。
- **本地问题检查与服务端不一致**：发布仍以服务端为准；本地检查只做提示，发布确认弹窗打开时先保存草稿取服务端问题。
- **就地新建动作与草稿保存的顺序**：先创建模板（独立事务），再把模板加入未保存的草稿；用户放弃草稿时模板保留在动作目录（可停用），在抽屉里提示这一点。
