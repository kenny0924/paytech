### 2. channel-connector 代码

- 表与 Java 改名：
  - 渠道身份 `t_channel` 归 protocol 模块（technique 第 2 节）。
  - core 中原 `PaymentChannel*` 的读写改为调用 protocol 公开的渠道服务，组合方式沿用 D1（`ChannelConfigTransactions`）。
  - 依赖方向仍是 `core → protocol`，架构测试同步。
- 渠道接口（`/channel-connector/v1/channels`）：
  - 创建必填 `channelType`，且不可修改；`UpdateChannel` 不接受类型。
  - 创建与更新可带 `description`。
  - 列表新增 `channelType` 过滤。
  - 详情与列表返回 `channelType`、`description`、`endpoints`、`version`；列表另加 `endpointCount`，服务渠道另加 `activeGrantCount`（支付渠道为 null）。
- 新接口 `PUT /channel-connector/v1/channels/{channelId}/endpoints`：
  - 请求 `{expectedVersion, endpoints:[{endpointCode, baseUrl, sandbox}]}`，写必带操作人，版本 CAS。
  - 校验规则沿用原接入方，并加出站地址保存校验（第 3 节）。
  - 原子 API 仍在引用的 `endpointCode` 不得删除，返回 409，原因写明被哪些原子 API 引用。
  - 同事务写变更记录。
- 状态变更：激活前置改为 `endpoints` 非空（两类渠道相同），拒绝文案"渠道未配置出站地址: {code}"。
- 服务渠道的规则（technique 第 5.3 节）：
  - 账号创建或更新时，`PAYMENT` 必须带 OE，`SERVICE` 必须不带。
  - `SERVICE` 激活第 2 个账号时返回 409。
  - MID、能力、成本方案的创建接口对 `SERVICE` 渠道返回 400。
  - Vault 负载 `entityNo` 改为可空：写入和读取校验同步调整，`schemaVersion` 不变。
- 删除接入方 5 个 CRUD（`/external-api-admin/v1/integrations` 的 list / get / create / update / delete）及其 DTO、Processor、测试。
  - 其余 `/external-api-admin/v1/integrations/{code}/…` 接口按渠道编码解析 `t_channel`。
  - 原子 API 编辑时，出站地址从 `t_channel.endpoints` 取。
- `ChannelConfigChangeApi` 的 `targetType` 白名单扩展到全部类型（P1 偏差 D9）。
- 通用执行入口 `POST /channel-connector/v1/service-executions`（technique 第 6.2 节）：
  - 请求 `{channelCode, standardApiCode, input}`，响应 `{executeStatus, outputs}`，结构沿用原 Platform 执行合同。
  - 校验顺序：
    1. 调用方身份。参照 `paytech/card/.../CardCallerResolver`：Token 优先；Header 与 Token 不一致返回 400；internal-auth OFF 时信任 `X-Caller-Service`；缺失返回 400。
    2. 渠道存在（否则 404）、类型为 `SERVICE`（否则 400）、状态 `ACTIVE`（否则 400）。
    3. 存在 ACTIVE 授权，否则 403 `CHANNEL_CALL_NOT_GRANTED`。
    4. 取唯一 ACTIVE 账号；没有就不提供账号材料。
    5. 在事务外执行。
  - 未发出类失败按原 NOT_SENT 集合返回 Problem（与第一段 D6 的类型化异常一致），其余失败为 `ERROR`。
  - 任一校验失败时外部请求数为 0。
- `ChannelOperationApi`（支付入口）对 `SERVICE` 渠道一律拒绝，不发出请求；结果口径与现有"配置无效"一致，在报告中写明。
- 隔离（technique 第 6.3 节）：
  - 按渠道类型分开两个执行舱，各有独立的 JDK `HttpClient` 实例和信号量。
  - 配置键 `channel-connector.protocol.execution.payment-max-concurrency`（默认 64）与 `service-max-concurrency`（默认 16）。
  - 拿不到许可时：通用入口返回 503 `CHANNEL_EXECUTION_BUSY`；支付入口结果为 NOT_SENT；沙箱验证的步骤结果记为 PROBLEM 503。全程不排队。
- 出站地址防护（technique 第 6.4 节）：
  - protocol `ext/outbound` 新增地址防护组件，参照 Platform `WebhookAddressGuard`（复制思路，不依赖 Platform）。
  - 执行时：先解析并固定地址再连接；拦截回环、私网、链路本地、保留与组播地址；不跟随重定向；`trusted-networks`（CIDR 列表，默认空）放行。被拦截时按配置无效处理，结果 NOT_SENT。
  - 保存出站地址时：拦截 IP 字面量落在被拦截网段的地址和 `localhost`，`trusted-networks` 放行；保存时不做 DNS 解析。
  - 本机与 mor-test 的 Mock 地址写入对应 profile 或 Nacos 配置样例，在报告中列出。
- 访问日志（technique 第 6.5 节）：
  - 每次原子 API HTTP 请求结束打一条 INFO，logger 名 `channel.outbound.access`。
  - 字段：`callerService`、`channelCode`、`channelType`、`standardApiCode`、`apiCode`、`executeStatus`、`httpStatus`、`elapsedMs`、`requestId`。
  - 不含 URL Query、请求头、报文与凭据。
  - 支付入口的 `callerService` 为 Payment 调用方，沙箱验证为 `VERIFY`。
- 授权接口（Owner）：
  - `GET /channel-connector/v1/channel-call-grants?channelId&callerService&standardApiCode&grantStatus&page&size`，分页，返回标准 API 编码与名称。
  - `POST /channel-connector/v1/channel-call-grants`：请求 `{channelId, callerService, standardApiCode}`，写必带操作人。
    - 渠道须为 `SERVICE`，否则 400；标准 API 须已被该渠道实现，否则 400。
    - 已存在同一组合返回 409，原因含现有状态与授权 ID。
  - `POST /channel-connector/v1/channel-call-grants/{id}/status`：请求 `{targetStatus, expectedVersion, reason?}`，版本 CAS。
  - 写入按新 Processor 规范使用 `AbstractLockProcessor` + TRY_LOCK，锁 `channel-call-grant:{channelId}`；同事务写变更记录。
  - 删除标准 API 实现前，若该渠道 × 标准 API 有 ACTIVE 授权，返回 409。
- 读卡：card 收回 `platform-support-service`，只允许 `channel-connector-service`（technique S6）。
