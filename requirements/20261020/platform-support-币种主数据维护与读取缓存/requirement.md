# platform-support：币种主数据维护与读取缓存

状态：**阶段 1—8 完成**（2026-10-21）：已部署 mor-test，已本地提交，未推送。确认记录见 [delivery.md](./delivery.md)，技术方案见 [technique.md](./technique.md)。

## 1. 背景

[目标架构 V2 决定 D41](../../../agent-docs/decisions/2026-10-17-target-architecture-v2.md) 规定 `t_currency_spec`（币种、小数位、舍入方式、状态）归 Platform 持有，ledger、billing 为“过账与舍入不依赖远程调用”各持一份同结构只读副本，同步机制留到后续切片。现状（mor-test，2026-10-20）：

- `mor_platform`、`mor_ledger`、`mor_billing` 三处各有一行 USD（2 位、HALF_UP、ACTIVE），由同一份 SQL 分别初始化，彼此没有同步；
- Platform 已有只读查询 `GET /platform/v1/currency-specs`、`/{currency}`（`CurrencySpecQueryApi`），没有维护接口、没有运营页面、没有调用方；
- ledger 9 处、billing 4 处读本库副本：账簿开立校验币种启用、人工调整 / 过账 / 试算 / 关账 / 计费事实的金额精度与舍入；其中过账的精度校验（`JournalPostingServiceImpl.checkBalanced`）在过账事务内。

用户 2026-10-20 决定：币种在 Platform 维护；ledger、billing 等不再持副本，改为读取 Platform 并用进程内缓存（Caffeine）加速。该决定取代 D41 中“各持只读副本”的部分，需另立决定记录。

## 2. 目标

1. 运营人员在 Operations 上维护币种：新增、编辑草稿、启用、停用，查看列表。
2. 币种只在 Platform 一处存放；ledger、billing 读 Platform 并缓存，不再有本地副本和同步问题。
3. 过账、计费的正确性不因缓存或 Platform 短暂不可用而改变，且遵守“事务内不调用外部服务”。

## 3. 本期范围（草案）

- **R1 Platform 维护接口：** 新增币种（草稿）、修改草稿、启用、停用；带操作人与变更记录；列表与详情沿用现有查询接口。
- **R2 Operations 页面：** 「平台配置」下新增「币种」页：列表（代码、小数位、舍入、状态）、新建 / 编辑草稿、启用 / 停用；需新增权限、路由与菜单注册。
- **R3 ledger、billing 读取 Platform：** 删除本地 `CurrencySpec` 仓储 / Mapper，改为经 `platform-support-api` 内部 HTTP 读取，进程内缓存（实现方式见技术方案 Q6）。
- **R4 缓存方式（满足事务公理）：** 服务内持有一份全量币种快照（数据量很小），启动时加载，之后定时刷新；业务代码（含事务内）只读内存快照，从不在事务内发起远程调用。查不到的币种按“币种不存在或未同步”拒绝，并触发一次事务外的异步刷新；被拒的过账批次由 ledger 既有重试机制恢复。
- **R5 删除副本：** `mor_ledger`、`mor_billing` 的 `t_currency_spec` 表、PDManer 模型、初始化数据随本需求删除。
- **R6 决定记录：** 新增决定记录，取代 D41 的副本部分；同步更新数据库文档与技术栈中受影响的描述。

## 4. 不做

- 不新增 USD 以外的实际币种数据（页面可以建，数据由运营自行维护）。
- 不改金额模型、不做汇率。
- tax、account、reconciliation、payout 当前不读币种，不改；以后需要时按 R3 同样方式读取。

## 5. 验收标准（草案）

| 编号 | 验收标准 |
|---|---|
| AC-01 | Operations「币种」页可新建草稿、编辑草稿、启用、停用；列表与 Platform 数据一致；无权限账号看不到维护按钮 |
| AC-02 | 已启用的币种不能修改小数位与舍入方式（Q1），页面不提供修改入口，接口拒绝 |
| AC-03 | ledger 开立账簿只接受 ACTIVE 币种；Platform 停用后，在刷新周期内新开账簿被拒绝 |
| AC-04 | ledger 过账、人工调整、试算、关账及 billing 计费事实的精度与舍入结果与改造前一致（现有测试全部通过） |
| AC-05 | 事务内代码路径不发起远程调用：缓存未命中时拒绝并异步刷新，不在事务内回源（测试可证） |
| AC-06 | Platform 不可用时，已加载的快照继续服务，过账不受影响；服务启动时 Platform 不可用则就绪探针失败（Q3） |
| AC-07 | `mor_ledger`、`mor_billing` 不再有 `t_currency_spec`，代码中无本地币种仓储 |
| AC-08 | 新增币种在一个刷新周期内被 ledger、billing 识别 |

视觉 / 交互：「币种」页沿用 Operations 现有配置列表页样式（筛选行 + 表格 + 抽屉 / 弹窗编辑），状态用标签显示，启用 / 停用二次确认。

## 6. 确认结果（2026-10-20，用户“继续”，按建议采纳）

| 编号 | 问题 | 结论 |
|---|---|---|
| Q1 | 小数位、舍入方式能否在启用后修改？改了会让已入账金额与新规则不一致，缓存也会出现新旧混用 | **启用后冻结**，只有草稿可改。币种代码唯一，启用后填错无法换一个代码重建，所以启用确认框要求再次核对小数位与舍入 |
| Q2 | 停用（INACTIVE）的影响范围 | **只拦新用途**：不能新开账簿、不能被新配置选用；已有账簿的过账、计费事实照常处理（经济事实不因状态被拒，与明细账决定第 12 条一致） |
| Q3 | 刷新周期与启动策略 | 每 60 秒全量刷新；启动时首次加载失败则服务不就绪（避免带空快照接流量）；Platform 暂时不可用时保留上次快照 |
| Q4 | 启用 / 停用是否需要双人复核 | **不需要**，单人操作 + 变更记录（与科目维护一致）；若要复核请说明 |
| Q5 | 阶段安排 | 跨 Platform、ops-bff、ops-web、ledger、billing 与三个库，建议走完整流程；阶段 2（现状差异）与 3（方案）合并为一次评审 |
