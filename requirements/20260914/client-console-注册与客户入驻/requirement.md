# Client Console 注册与客户入驻

> **2026-09-14 后继范围：** 本期仅邮箱密码登录，Google 与 OTP 延后；取消入驻资料版本，审核中只读、退回后可修改原申请、批准后不可修改；最终拒绝结束申请。同一账号的个人/组织 Client 入驻合计最多一份未完成申请。详细接口、字段投影、页面和实施顺序见[设计入口](./design.md)。下文已按简化决定修订，原编号保留用于关联。共享模型和 HTTP 合同尚待收口，不能据此直接进入研发。

本期目标是让新客户完成账号注册、入驻申请和最小人工审核闭环，审核批准后进入自己的客户工作区。团队邀请延后。用户已确认阶段 2，当前提供[阶段 3 完整设计评审稿](./design.md)；不表示完整接口、数据合同或研发已获批准。用户原意与确认范围见 [delivery.md](./delivery.md)。

关联：Client Console、E2E-01、CCT-01、CCT-I15/I16、RCO-01、PLT-I15/I16/I17、PLT-I04、PLT-I02/I21。阶段分析见 [technique.md](./technique.md)，实现、验证及部署状态只见 [当前台账](../../../agent-docs/CURRENT_IMPLEMENTATION.md#client-console-onboarding-20260914)。

## 1. 使用者与成功结果

- 新客户申请人：注册 CUSTOMER Account，申请成为 INDIVIDUAL 或 ORGANIZATION Client，保存资料、提交申请、响应补件并持续查询结果。
- 已有账号的申请人：复用自己的账号和正在处理的申请，避免因重复注册、刷新或超时创建重复业务对象。
- 获授权的 Operations 审核人员：查看被授权的申请与材料，核验要求、提出补件、形成有依据的审核结论。
- 已批准客户的负责人：在有效的 CLIENT Tenant 上获得自己的工作区；账号、成员、来源业务状态或安全状态不允许时不得进入。

成功结果是注册、验证、申请、审核、客户激活和工作区访问之间的真实状态能够衔接。进入工作区不表示合同已签署、技术接入已完成或已经具备收款能力。

## 2. 本期功能

| 编号 | 能力 | 本期边界 |
|---|---|---|
| F-01 | 邮箱注册 | 邮箱与密码创建 CUSTOMER Account；账号与 Client 分开建立，不为注册预创建业务客户或假 Tenant |
| F-02 | 邮箱验证与重发 | 验证、过期、已消费、被新邮件替代等结果清晰可见；重发不产生第二个账号，不泄露其他账号状态 |
| F-03 | 密码登录与找回 | 登录、退出、会话续期、找回并重置已有密码；重置后旧会话失效；本期仅邮箱密码，不改变其他已存在认证方式的恢复规则 |
| F-04 | 外部登录（延后） | Google、OTP、通用账号合并和登录方式管理本期不做；编号保留 |
| F-05 | 登录后的业务引导 | 区分未申请、申请草稿、已提交、审核中、补件待办、审核结果及已可进入的工作区；只查询当前账号有权看到的信息 |
| F-06 | 个人/组织入驻草稿 | 创建或恢复 Client Application，填写适用资料、保存草稿、再次登录继续；组织资料与相关自然人资料按 CCT/Risk 已有模型组织 |
| F-07 | 受控材料上传与提交 | 等待 PENDING Tenant 投影完成后上传，显示扫描状态；提交前校验必需资料，正式提交使当前资料与文件引用只读，建立稳定提交身份 |
| F-08 | 申请进度与补件 | 从 CCT/Risk 权威事实展示进度及客户可见原因；Risk 退回结束当前审核任务；客户在原申请修改后重提，新任务固定新受审事实 |
| F-09 | 最小人工审核 | Operations 申请/案件列表、详情、受控材料核验、行业/MCC 确认、退回修改和最终批准/拒绝；形成 Risk 正式资格决定，保留人员、理由与证据 |
| F-10 | 批准后的激活与工作区 | CCT 消费并校验 Risk 决定，推进 Client/Application，随后投影 Platform；撤销临时入驻角色、授予 Tenant Owner，按当前有效状态签发单一工作区上下文 |
| F-11 | 隔离、恢复与失败反馈 | 当前账号/申请/客户归属检查，防重复提交、并发覆盖及越权；外部依赖暂不可用时展示处理中或错误，不伪造成功或审核通过 |

## 3. 已确认的交付边界

本期包含注册入驻和最小人工审核闭环。人工审核使用 Risk 既有 Case、Requirement、Evidence、Check 与 Qualification Decision 语义；“人工”不能绕过有效程序中要求的材料、检查、关联人资格或筛查。

以下能力延后：团队邀请创建/接受/撤销、团队角色编辑与成员管理、Partner Console、OE/MID 申请、合同签署、API Credential/Webhook 自助、交易/退款、余额/Payout、通用审核工作流配置器、自动风控引擎和新增外部筛查产品接入。必要检查如依赖尚未具备的外部能力，只能保持未完成，不能默认通过。

注册/入驻需要的邮件、文件保存与扫描、CUSTOMER 密钥和 Vault 接入是本期依赖；具体实现与环境配置在详细设计中明确。用户选择延期邀请，取代前一轮讨论中“受邀用户路径也在第一期”的候选安排；现行全系统邀请设计和后续产品目标继续有效。

## 4. 业务不变量

1. Account 表达人类登录身份，Client 表达平台客户，Tenant Member 表达工作区授权。申请发起人不因此成为法定代表、UBO 或 Signatory。
2. 邮箱密码注册先验证邮箱，使用一次性邮件链接，不提供 OTP 或 Google 登录。
3. 注册、找回密码的公开响应不得成为账号/客户关系查询接口。已登录账号可以查询自己的申请和授权工作区。
4. `START_OR_RESUME` 按已认证 Account 恢复唯一未完成 Client 申请；个人/组织共用名额，DRAFT/SUBMITTED/UNDER_REVIEW/RETURNED 均占用。没有活动申请才建立下一份并登记 Platform 投影任务；正式 `SUBMIT` 后才登记 Risk 尽调。
5. 上传入驻材料时保留 Account Context。Platform 从可信账号及当前入驻授权解析 Tenant，浏览器不得提供一个 Tenant ID 来决定文件归属；歧义必须拒绝。
6. CCT Application 使用 `DRAFT/SUBMITTED/UNDER_REVIEW/RETURNED/APPROVED/REJECTED/WITHDRAWN`。RETURNED 经用户明确确认，结束旧审核任务后才能修改。
7. 提交及审核中当前资料只读；RETURNED 后修改同一份资料并重提，Risk 保留旧任务受审证据。批准后永久只读；最终拒绝不可改回草稿。取消 Profile 版本及版本对比。
8. Risk 的人工决定必须匹配申请、主角色/资格类型、Case 与提交身份；缺少必需证据或资格时不能批准。Organization 主 Case 与相关自然人 Case 的依赖由 Risk 管理。
9. 审核通过、CCT 激活、Platform 投影完成和当前工作区访问是不同事实。CCT 激活不能覆盖 Platform 的安全暂停；旧会话不能作为当前成员权限事实。
10. BFF 无业务数据库，不双写 CCT、Risk 或 Platform。事务内不调用外部服务；跨系统后续工作由各 Owner 的提交后执行及幂等恢复完成。

## 7. 详细设计需要闭合的问题

- 无 Tenant 的认证邮件已提出提交 Challenge 后直接投递、失败可重发新链接的最小方案，见数据设计；真实通道和环境尚待配置。
- 已确认每账号一份未完成 Client 入驻申请；准确状态、唯一索引和旧页面上传归属见[详细设计](./design.md#4-申请数量与恢复规则)，不限制多个已有工作区。
- 个人/组织必填字段、材料清单、相关人范围以及人工核验要求如何从已批准的 CCT/Risk 事实得到；技术设计不能自定某司法辖区的法定义务。
- 退回公开说明、原申请重提、新审核任务与旧结果隔离已在 API/数据稿定义；本次已按一份申请决定补齐上传目标核对和账号唯一索引。
- 既有 DD Program/Check/Screening 中哪些要求可由本期人工完成，哪些真实依赖未就绪会阻止批准；不虚构外部筛查成功。
- 注册声明/隐私说明所需文案与证据由其 Owner 确定，不能复用 Consumer Checkout 的三份法律接受事实。
