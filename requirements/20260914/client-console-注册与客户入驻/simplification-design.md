# Client 入驻简化方案：单页、运营分类、无资料版本、邮箱密码

日期：2026-09-14。阶段：3，供评审的设计修订。实现、模型、SQL 和环境状态统一见[当前台账](../../../agent-docs/CURRENT_IMPLEMENTATION.md#client-console-onboarding-20260914)。

本稿承接用户四点反馈及随后“可以，下一步”的确认：采用单页分区，运营在最终批准前确认行业/MCC，本期取消入驻资料版本，批准后只读，仅邮箱密码；退回修改和最终拒绝分开。方向已认可，详细接口和物理迁移仍是阶段 3 评审内容。后继详细工件统一从[design.md](./design.md)进入。

本稿优先于本需求旧稿中受影响的 Google 范围、分步页面、Profile 版本和冻结后只能另开申请更正的安排。共享 CCT、Risk、Platform 合同的迁移仍须逐项设计，不把本稿视为全平台版本字段批量删除授权。未涉及的 Owner、权限、库隔离、文件和真实审核门禁继续有效。

## 1. 页面与保存：推荐单页分区，允许不完整草稿

| 方案 | 页面与保存 | 取舍 |
|---|---|---|
| A，推荐 | 同一页放基础资料、经营资料、组织相关人员、材料；顶部页内定位，人员/关系用抽屉；保存草稿与正式提交分开 | 少跳转；支持中途离开和恢复。组织页较长，可折叠已填写分区 |
| B | 基础与经营资料一页，人员及材料一页 | 表单较短，但仍要解决不完整草稿的保存，合页本身不能解决数据库约束 |
| C | 全部填完才一次保存提交 | 表结构最容易要求完整，但无法可靠续填，上传及多人资料仍有独立生命周期；不建议本期采用 |

方案 A 的页面结构：顶部品牌/返回申请 → 标题与保存提示 → 页内定位 → 基础资料 → 经营资料 → 组织相关人员（个人不显示）→ 材料 → 保存草稿/核对并提交。核对使用同页只读预览或确认抽屉，不再要求跳到一个独立表单页。桌面双列、窄屏单列；设计长画板表示完整滚动内容，不是要求固定屏幕高度。

数据库约束可以修改，但应按真实用途区分：

- 草稿未填的姓名、出生日期、经营模式、金额、币种等列允许 NULL；缺值不写空字符串、虚构生日、0 金额或占位 Hash。
- ID、客户类型、申请归属、状态继续必填；主键、身份唯一性及必要的一对一唯一索引保留。项目本就不创建物理 CHECK 或 FOREIGN KEY，这次发现的阻塞主要是 NOT NULL 与 Profile 创建时机。
- 资料字段有值时执行类型、长度、格式和组合校验；正式提交做完整校验。运营分类不属于客户提交必填，属于最终批准门禁。
- 建议选定类型后由 CCT 创建稳定申请、PENDING Client、Party 及单份资料头；内容可空。前端只拿真实申请 ID，再开始受控上传。

同一页不等于一个巨大接口：基础/经营字段可使用一个申请草稿保存命令，按明确字段集合更新；人员、关系、材料仍按实际子对象保存。命令都由 CCT 校验归属和可编辑状态。文件二进制仍上传 Platform，CCT 只接收受控文件引用。BFF 不在多个数据库之间组织保存事务。

## 2. 客户提供业务事实，运营确认行业和 MCC

客户填写经营模式、网站、主要商品/服务说明、预计月交易额、预计客单价、币种和业务联系方式。Client 请求合同不接受 `industry_code`、`mcc_code`、主要分类或分类确认字段；不能只在页面隐藏而仍允许接口写入。

新增有实际消费者的 `business_description`：运营据此核对实际业务并选择分类，Risk 据此了解经营活动。拟为 CCT Business Profile 下的结构化文本列，VARCHAR(2000)，草稿可空、提交必填；不使用扩展 JSON。页面与接口同名同义。

行业与 MCC 是两个维度。既有 [Risk 合同](../../../agent-docs/database/RISK_COMPLIANCE_DATABASE.md)明确二者不得合并或互相推导；一个行业可能对应多种 MCC，不能选行业后静默生成 MCC。运营分别从受控目录选择，并确认该客户被批准的组合。

推荐顺序：客户提交 → 运营核对资料/材料 → 运营选择并确认行业与 MCC → 完成适用审核 → 最终批准 → 资料及分类锁定 → 开通工作区。这把运营配置放在批准动作前的最后阶段，与“批准后不能改”一致，也避免额外增加“已批准但分类未完成”的入驻分支。

若坚持先批准后配置：可以先完成身份核验，但最终业务批准与交易放行必须等分类确认及相关审核完成。工作区可展示等待配置；不能默认 MCC、自动取第一项或把身份核验结果当作全业务批准。该方案需要额外区分身份核验、经营分类和业务准入，不作为本轮推荐默认。

运营分类表单包含：行业、MCC、主要分类，以及系统生成的确认人/确认时间。沿用 Business Profile 1:N 分类、准确组合唯一、恰好一项主要分类的能力；不因 UI 只有一行而把多分类模型静默改成一对一。只有一项时自动标主要分类，多个分类时由运营明确选择。

正式行业/MCC 仍归 CCT，Risk 拥有审核决定。Operations Web/BFF 负责展示与转发，不成为分类 Owner。分类在审核任务中完成后保持固定；若必须改分类，结束该审核任务并重新核验，不让已经检查过的分类被另一个操作覆盖。

分类确认绑定当前审核任务，作为运营在审核过程中形成的核验事实，不修改客户最初提交的业务说明。Risk 最终批准必须取得并核验同一任务的已确认分类；CCT 激活也校验该任务绑定。两次本地写入通过任务身份及提交后恢复衔接；确认分类成功但 Risk 尚未接收时保持处理中，不能直接批准。需要更换分类时重新建立审核任务和确认，旧核验结果不能沿用。

## 3. 单份资料与审核状态

| 状态 | 客户可做什么 | 运营可做什么 |
|---|---|---|
| DRAFT 草稿 | 填写、保存、上传、提交 | 不能提前批准 |
| SUBMITTED 已提交 | 只读、查看进度 | 等待 Risk 审核任务登记，不能把登记失败当成待客户重提 |
| UNDER_REVIEW 审核中 | 只读 | 核验、确认分类、退回修改或最终批准/拒绝 |
| RETURNED 退回修改（本次新增） | 修改原申请、补充材料、重新提交 | 查看退回原因与待客户处理情况，不能批准旧任务 |
| APPROVED 已批准 | 只读 | 入驻资料、人员关系、材料集合和批准分类全部不可修改 |
| REJECTED 最终拒绝 | 查看结果 | 终态，不能改回草稿 |
| WITHDRAWN 已撤回 | 查看结果 | 终态；是否展示自助撤回不因保留状态自动纳入 UI |

采用用户确认的退回修改规则。初始草稿可以编辑；提交后客户不能边填边被审核。退回原因自动定位到分区，具体字段、人员或材料由客户可见说明指出；本期不建设通用字段级整改工作流。返回原单页表单，顶部展示原因，不要求客户重复填写所有内容。

取消资料多版本、前后版本对比、版本选择、版本生效期、批准后资料变更申请。本期也不给运营保留绕过审核的批准后编辑入口。账号密码与登录会话不是 Client 法律/经营资料，密码恢复不因 Client 已批准而禁用。

申请编号始终不变。每次正式重提创建新的真实审核任务，旧任务以“退回”结束；任务记录保留操作者、动作、原因、时间、证据及最终决定，不保留可供切换的 Profile 版本集合。审核任务 ID 是处理身份，不是资料版本号。

为隔离异步旧结果，CCT 保存当前提交命令 ID 和当前主审核任务 ID；Risk 以提交命令身份幂等登记主/关联人任务。仅当前任务允许改变本次申请。原申请退回后，上一任务的延迟批准必须拒绝；重复发送同次提交不得产生新任务。现有 Risk 按 Application/Role/Qualification 唯一的规则需要增加提交身份才能支持同一申请重提，不能原样复用并覆盖旧 Case。

退回时先让 Risk 任务结束，再由 CCT 确认同一任务并进入 RETURNED；投影未完成前仍只读。批准同理只消费准确当前任务的终态结果。所有远程调用均在本地事务外，后续可重试，BFF 不跨系统双写。

### 无版本号的并发边界

保存、提交、退回投影和批准投影按真实申请资源串行化，并在 CCT 本地事务中锁定同一申请行、重新检查状态后修改子对象。组织关联人编辑同时校验该 Party 是否被其他已批准资料引用；已有已批准 Party 只读复用，不能借新申请修改。

数据库行锁/状态条件保护“审核中或批准后不能写”，不解决两个旧浏览器草稿的所有覆盖问题。首期页面只提交用户实际修改的字段，同一页面保存单飞；同一字段在两个标签页编辑仍按最后成功保存结果保留。本稿不把时间戳、Hash 或隐藏计数器冒充“没有版本”的冲突令牌，也不声称无版本还能保留原先全部乐观冲突提示能力。

保存和提交竞争时，先完成的事务决定后续：先保存则提交读取保存后的内容；先提交则后续保存失败并刷新为只读。重复批准/拒绝使用命令幂等与状态门禁；不能仅凭 Redis 锁声称解决全部竞态。

## 4. 数据库目标差异：真实删除版本结构

下表是目标设计差异，精确 DDL 需结合共享消费者收口；不是已执行的迁移清单。

| 现有对象 | 本期目标 | 需要删除或调整的结构 |
|---|---|---|
| `t_party_profile` | 每个 Party 一份当前资料，`profile_id` 为稳定资料 ID | 删除 `version_no`、版本有效期、版本 active slot；以 `party_id` 唯一取代 `(party_id,version_no)` 和 ACTIVE 唯一定位。资料状态由申请/批准引用控制，取消 FROZEN→ACTIVE→SUPERSEDED 版本切换 |
| `t_individual_profile` / `t_organization_profile` | 仍按类型保存明确字段 | 保留稳定 `profile_id` 关联，未填写业务字段允许 NULL；提交检查类型与完整性 |
| `t_party_address` / `t_party_contact` / `t_party_profile_identifier` | 单份资料的地址、联系方式、法律标识 | 不为修改创建新 Profile 或子行版本；证件自身有效期仍是实际业务事实，不属于资料版本生效期 |
| `t_party_relation` | 一条组织与人员关系使用稳定关系 ID | `relation_version_id` 改为 `relation_id`，删除 `version_no` 与版本选择索引；关系自身实际起止日期与持股比例按真实业务保留，不与版本有效期混为一谈 |
| `t_client_business_profile` | 每个 Client 一份经营资料 | `client_id` 唯一；删除 `version_no`、版本生效期、版本 active slot；新增业务说明，草稿内容允许 NULL |
| `t_client_business_classification` | 运营确认的分类组合 | 保留行业/MCC/主要分类；增加确有审核消费者的确认人、确认时间与说明，客户端不可写；最终批准后不可改 |
| `t_client_application` | 入驻生命周期、当前提交及审核关联 | 本期仅 ONBOARDING；取消 Base/Target Party/Business Profile 四指针及版本切换，按 Client→Party→单份资料读取；增加 RETURNED、当前提交命令身份；保持原申请 ID |
| 本期入驻 BCR 接入 | 普通业务记录加真实审核动作记录 | 入驻保存不再依赖 BCR `current_version` 或新增 `business_change_version` 快照；不为新资料保存维护另一套版本历史 |
| Risk 本期审核来源 | 精确申请/提交/任务身份与受控审核证据 | 去除本期来源合同的 Profile Version No、Relation Version No、Submission Version 依赖；关系引用改稳定 ID，来源提交使用真实命令 ID；Case 证据保留其所属审核任务 |
| CCT/Risk 决定匹配 | 准确任务 + 不可变决定 ID | 本期不支持批准后决定修订；不再依赖本期决定版本号选“最新”。共享 Risk 决定更正/复审能力不能直接删除 |

单份资料的旧 `hash_schema_version`、`content_hash` 和 Submission Hash 不能只删除一半：它们现有消费者用于冻结和校验。新入驻合同以不可变审核任务输入和准确任务/决定 ID 关联；迁移时同步去掉本期旧 Version/Hash Tuple 依赖，旧历史 Reader 保留原合同，不重算历史。文件 `content_hash` 继续证明文件字节，是文件事实，不能因移除资料版本而删除。

共享影响已核实：Partner Application、Operating Entity Application、Agreement Party 引用 `party_profile_id`；Risk Case Subject 引用 Profile/Relation 版本；CCT 普通聚合 CAS 依赖 BCR；Platform 还有凭据/会话撤销、投影顺序及安全并发字段。这些不等同于客户资料版本。此次不能执行全库按字段名匹配 `version` 的删除；商业条款版本、Risk 规则/程序版本、密钥版本以及既有 Platform 安全字段属于其他用例。若用户要的是 CCT 乃至六系统所有版本一起移除，需要另列对应业务简化范围；本稿没有静默批准或执行它们。

如果既有库中同一 Party/Client 已有多份 Profile，不能任选最大版本覆盖。迁移前须盘点批准、合同及历史引用；确认保留对象与旧 Reader 后才能投影新结构。设计批准仍不等于数据库执行。

## 5. 字段一致性合同

页面与接口字段一致，数据库按 Owner 保存。系统生成字段不要求客户填写；密码、邮箱等敏感值也不要求与数据库原文同形。下表为精确的业务映射目标，界面文案不作为第二套字段 Schema。

| 字段/字段组 | 个人 | 组织 | 目标落点与处理 |
|---|---|---|---|
| 登录邮箱、密码 | 共用 | 共用 | Platform Account/Password Credential；密码只存 verifier，Client Profile 不保存密码 |
| 客户类型 | INDIVIDUAL | ORGANIZATION | CCT Party `party_type`，创建后不可改 |
| 名/中间名/姓 | 填写 | 相关人员填写 | `individual_profile.given_name/middle_name/family_name`；中间名可选，不合成一个不一致的姓名输入 |
| 出生日期/国籍/居住国 | 填写 | 相关人员填写 | `birth_date/nationality_country/residence_country`，日期与国家代码不混用展示文案 |
| 组织法定名称/简称 | 不显示 | 填写 | `organization_profile.legal_name/trade_name`；简称可选 |
| 注册国/组织类型/成立日期 | 不显示 | 填写 | `incorporation_country/organization_type/incorporation_date` |
| 证件类型/签发国/签发机构/号码 | 按适用证件填写 | 组织登记标识及人员适用证件 | `party_profile_identifier.identifier_type/issuing_country/issuer_scope_key/identifier_value` 保存草稿，完整校验后绑定永久 Identity Key；机构由受控目录解释，不能将国家机械等同机构作用域 |
| 规范化身份号码 | 不填写 | 不填写 | `normalized_identifier_value` 由 CCT 按证件/登记类型规范化；唯一性规则保持 |
| 证件生效/到期日期 | 按适用证件填写 | 相关人员按适用证件填写 | `party_profile_identifier.valid_from/valid_to`；长期有效映射无到期日，不填虚构远期日期 |
| 地址第一/第二行、城市、州省、邮编、国家 | 居住地址 | 注册地址；相关人员为居住地址 | `party_address` 同名字段；第二行可选，州省/邮编按地区要求；地址类型由分区和主体确定 |
| 经营模式 | 填写 | 填写 | `client_business_profile.business_model_code`，受控选项，非 industry/MCC |
| 网站地址 | 可选 | 可选 | `website_url`，未填为 NULL |
| 业务说明 | 填写 | 填写 | 新增 `business_description`，支持运营理解业务；提交必填 |
| 预计月交易额/预计客单价/币种 | 填写 | 填写 | `expected_volume/expected_ticket/currency`；本稿建议 volume 明确定义为月金额，金额接口用十进制字符串，不使用笔数或浮点；旧含混单位需迁移评审 |
| 业务邮箱/电话 | 填写 | 填写 | 主 Party 的 `party_contact` EMAIL/PHONE；通过 Vault 标量 Token 保存。可以与登录邮箱不同，不复制成账号绑定 |
| 相关人员身份 | 不显示 | 添加/编辑 | 同一套个人字段合同。添加人员不创建 Account，不发送邀请 |
| 关系类型/直接持股比例/关系起止 | 不显示 | 按适用关系填写 | `party_relation`；页面“%”与数据库比例单位必须统一，不擅自引入 UBO 阈值；日期控件到 UTC 时刻的边界在接口稿明确 |
| 行业/MCC/主要分类 | 客户不填写 | 客户不填写 | 运营专属 CCT Classification 命令；行业与 MCC 两项独立选择、组合批准 |
| 材料要求/对象/文件 | 按清单上传 | 按组织和人员清单上传 | CCT Application Document 与 Platform File 引用；要求来自 Risk 程序，不把稿中示例当成所有国家通用必填 |
| 保存时间/申请状态/审核原因 | 展示 | 展示 | 由 CCT/Risk/Platform 权威事实投影，不由客户输入 |

姓名、生日、地址、法律标识沿用 CCT 当前结构化保护边界；联系邮箱/电话使用 Vault 当前 V1。现有 Party Contact 的 Vault Record Version/Metadata Hash 是另一个已知适配缺口，不能伪造值填满 NOT NULL；本期接入须按真实 V1 返回的 Token/Mask 改正合同。

已建立身份标识的 Party 归属不得改绑。录入错误应在本次未批准申请范围内走明确的更正命令及重复身份核对；已有已批准 Party 只读复用。同一相关人参与多个组织时，组织自己的关系仍独立；资料归属不能取决于当前打开哪个抽屉。

## 6. 认证：仅邮箱密码

| 页面 | 输入与行为 |
|---|---|
| 注册 | 邮箱、密码、显示/隐藏密码、创建账号、已有账号登录 |
| 注册后验证 | 查收邮件，点击验证链接；提供重发、已验证、过期/失效反馈，不提供验证码输入框 |
| 登录 | 邮箱、密码、显示/隐藏密码、登录、忘记密码、注册入口 |
| 找回密码 | 填写邮箱，统一展示发送结果 |
| 重置密码 | 通过邮件中的一次性链接设置新密码，旧会话撤销，再用邮箱密码登录 |

不设计 Google、短信/邮箱 OTP 登录、TOTP/MFA、登录方式选择或绑定中心。本期不建设 Google Federated Identity/OTP 表和入口；它们在共享 Platform 设计中的其他用途不随此范围决定删除。

延续已确认的注册邮箱验证，通过高熵一次性链接完成；“不做 OTP 登录”不等于允许未验证邮箱入驻，也不等于取消找回密码。验证/重置链接不能直接变成日常免密登录，只有 EMAIL_VERIFICATION/PASSWORD_RESET 的指定用途。Authentication Challenge 仍有实际需要，Google 身份表不属于本期依赖。

首次登录成功按当前 Account 可见申请/工作区路由。未验证账号只进入验证引导；密码错误给统一提示；限流、禁用、退出和会话撤销沿用 Platform/Gateway 的真实能力。账号只保存密码校验材料，Token 和密码不写草稿、文件、普通日志或事件。
