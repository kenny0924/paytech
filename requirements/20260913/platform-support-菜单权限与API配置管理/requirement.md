# 菜单权限与 API 配置管理

阶段 1 范围已确认：用户选择将两项功能一起交付，并在澄清后明确 Target/Route 覆盖全部已有 Channel。确认记录见 [delivery.md](./delivery.md)，阶段 2 分析见 [technique.md](./technique.md)。关联现有需求 PLT-16、PLT-17、PLT-I02、PLT-I19、PLT-I20、PLT-I21；全局配置场景登记为 E2E-16，具体接口与实现仍按阶段评审。

**一句话总结：本需求合并 2 项能力，管理菜单/按钮、权限、Target、Route 共 4 类对象，预计涉及 Platform Support、Operations BFF、Operations Web 三个应用；Gateway 复用现有动态快照链，是否需要配套调整在阶段 2 核定；新增 API、表、字段及注册 DML 数量在阶段 3 定义，不预设新表。**

## 1. 使用者、目标与成功场景

使用者是获授权的 Operations 配置管理员；普通运营人员按既有角色使用配置后的菜单和操作。Platform 拥有配置及授权事实，Operations 提供管理页面。

现有人员、角色、审计以及 Target/Route 查询和启停继续复用。新增页面/API 的注册目前仍需 SQL，目标是通过管理页面完成受支持配置的新增、编辑、关联、启停和引用查看。

典型场景：某个业务页面和 API 已经研发部署，管理员登记权限，创建或复用 Target，登记 Route，配置菜单/按钮并关联权限，再通过已有角色管理授权。对应人员刷新导航后可访问页面并操作；未获授权的人员即使直接调用 API 也被拒绝。

本需求不是页面生成器或接口生成器。登记一个 component key、按钮或 Route，不会生成其尚未实现的页面、事件处理代码或后端 API。

## 2. 范围与已有约束

### 2.1 管理入口与渠道范围

- 管理入口只使用 Operations Web → Gateway → Operations BFF → Platform 的既有链路，不开放 Client/Partner 的管理写入口。
- 本期菜单/按钮维护先限定 OPERATIONS，复用现有人员和角色管理，不同时建设 Client/Partner Console。
- **Q1 已确认：Target/Route 新增编辑覆盖 OPERATIONS、CLIENT、PARTNER、CHECKOUT、CLIENT_API、CHANNEL_CALLBACK 六类已有入口。** 共用模型、管理 API 和页面，不分别建设六套功能；不新增 Channel 或认证算法，也不代表某个环境的六类真实业务入口均已接通。现有查询与启停范围保持。
- 各 Channel 分别遵守现有 HUMAN_PERMISSION、API_SCOPE、CHECKOUT_RESOURCE 等合同；不能把所有入口都改为 Operations 权限模式。管理这些配置始终使用 Operations 身份。
- 接口沿用已有版本，新增接口默认 v1；代码类名不增加 V1/V2。页面方案在阶段 3 使用现有 Operations Pencil 设计文件。

### 2.2 菜单与按钮资源

- 提供资源树、筛选、详情、新增、编辑和启停。
- 菜单可维护名称、父级、同级排序、前端相对路径、已支持页面组件和可见性权限；纯分组菜单与实际页面的组合规则在设计阶段明确。
- 按钮归属对应菜单，维护资源编码、名称、排序和权限；只配置已有功能使用的按钮身份，不生成新的业务操作。
- 支持调整父级和顺序；保存时拒绝树循环、错误父类型、跨渠道父子关系和不合法路径。
- 菜单路径和组件须能够被已部署前端识别。可调整的路径范围、组件目录来源及存量页面适配在阶段 2 核定；不能靠手工输入未知路径制造打不开的菜单。
- 停用父菜单后，其子项不再通过导航展示；子项自身状态保留，不批量改写角色授权。单独调用 API 仍按当前权限判断，不能将隐藏菜单当作撤权。

### 2.3 权限目录与资源关联

- 提供权限查询、详情、新增、编辑可变属性、启停和引用查看。复用现有权限身份及角色授权，不建设第二套角色体系。
- 权限可关联多个菜单/按钮，也可供多个 API Route 使用。资源和 HUMAN_PERMISSION Route 各自引用同一个权限，菜单/按钮不直接一对一绑定 API。
- 权限详情能够查看关联资源、Route 和角色，帮助管理员判断改动影响；按当前关系查询，不预建历史版本或复杂血缘图。
- 新增权限后，有资格的管理员能在已有角色管理中完成明确授权；不会自动赋予普通角色。现有系统管理员规则与“新权限如何进入可分配目录”的闭环必须在阶段 2 核对并于阶段 3 定稿，不通过默认给所有人权限解决。
- 停用权限后，相关资源在重新获取导航时隐藏，相关 API 在下一次权限判断时拒绝；角色原关联保留，重新启用时按原授权关系恢复。
- 权限编码及资源类型/动作所表达的身份不能通过编辑偷换已有授权含义；需要另一业务权限时新建身份。

### 2.4 Target 管理

- 在已有列表、详情和启停基础上，增加新建和编辑。
- 新建配置稳定 Target Code、所属 Channel 和服务发现名称；编辑可调整服务发现配置，展示受影响 Route。稳定编码及已建立的 Channel 身份不通过普通编辑改写。
- Target 从 Platform 数据库进入现有完整 Snapshot，Gateway 按同一快照中的 Target/Route 转发。新增支持范围内的 Target 不再要求向 Gateway 代码增加业务白名单或重启。
- 服务地址仍使用已有服务发现体系，不增加任意公网 URL、IP/Port、脚本或跨 Namespace 发现功能。
- 保留 Target 停用后其下路由退出有效快照、重新启用时整体校验的既有语义；不逐条改写 Route 状态。

### 2.5 Route 管理

- 在已有查询、详情和启停基础上，增加新建和编辑。
- 配置稳定 Route Code、Channel、HTTP Method、公共路径模板、下游路径模板、同 Channel Target、认证/授权模式、Permission 或既有 Scope，以及受支持的 Header、Query、Guard、Body、Cookie 和超时限制。
- 请求 Header、Query 和 Guard 子项作为一条 Route 的完整配置一起保存；不得出现主记录成功、子项只写一半的情况。
- 保存检查全局 Method/Path 冲突、目标引用、模板参数、认证与授权组合及既有容量上限，错误定位到相关字段或子项；无效配置不得破坏现有可用目录。阶段 3 依据当前全局唯一索引和编译器校正此处原“同 Channel”措辞，不能以不同 Channel 重复登记同一 Method/Path。
- 按当前授权模式呈现适用字段，Permission 与 Scope 不混填。阶段 2 核对发现当前没有独立 Scope 目录：requiredScopeCode 按既有 Client API 合同填写并做规范校验，可复用已有 Route 值作为提示，不将某个 Credential 的授权集当作全局目录；本期不同时交付 Client API 凭证及 Scope 全生命周期管理。
- 配置持久化成功与 Gateway 已加载是不同结果：保存后按现有快照刷新机制生效，不增加第二次发布操作；页面不能只凭保存成功声称所有 Gateway 已切换。

### 2.6 通用管理行为

- 本期采用新增、编辑、详情和启停，不增加物理删除；稳定编码不被复用。新建 Target、Route、菜单/按钮建议先保存为停用态，再明确启用；权限的初始状态与授权衔接在方案阶段一起确定。
- 修改使用既有并发版本保护，命令重试复用相同幂等身份，写操作记录操作者、对象及变更原因。版本冲突保留草稿，刷新后由操作者重新确认。
- 既有角色继续决定谁可查看、维护和授权。管理接口必须真实鉴权，新增权限不能被用于越权自授；管理入口、登录链及系统内置资源的可编辑边界在阶段 3 给出明确清单。
- 不引入新的审批、配置版本库、发布单、Snapshot 回执或通用回滚引擎。已有审计可用于追溯，修正配置通过现有编辑与启停完成。
- 不自动把现有全部注册记录改为启用，也不批量修改业务角色或删除既有配置。

## 3. 功能验收标准

| 编号 | 验收结果 |
|---|---|
| AC-01 | 已授权人员可进入资源与 API 配置页面；只读人员可查详情但不能写入，直接调用管理 API 也被拒绝 |
| AC-02 | 可创建并维护有效菜单/按钮，修改层级与排序后导航结果一致；循环、非法路径和非法父子关系被拒绝且原数据不变 |
| AC-03 | 已有页面可通过资源配置及角色授权被正确挂载；未实现的组件或按钮操作不能被配置成虚假的可用功能 |
| AC-04 | 新权限可经明确授权分配到既有角色，一个权限可关联多个资源及 API；普通角色不会因权限创建而自动获权 |
| AC-05 | 权限详情能查询关联菜单/按钮、Route 和角色，跳转到有权查看的对应详情 |
| AC-06 | 停用权限后新权限判断拒绝 API、重新加载导航后隐藏关联资源；仅隐藏菜单不替代 API 授权；重新启用按原关系恢复 |
| AC-07 | 六类 Channel 均可新增编辑 Target/Route 并通过匹配的配置校验及快照编译；在已接通的 Operations 链路证明此前 Gateway 代码中不存在的 Target/Route 经真实快照刷新后正确转发，无需修改业务名单或重启；其余入口配置验收不冒充业务认证已接通 |
| AC-08 | 调整 Target 服务发现配置后，新快照请求去新目标；单次请求不混用不同快照的 Route/Target；Target 启停保持原有整体语义 |
| AC-09 | 可完整新增、编辑 Route 及其 Header/Query/Guard 配置，保存失败不留下部分结果，详情与回读一致 |
| AC-10 | 路径冲突、目标或权限无效、不兼容认证/授权组合及超限配置均被拒绝，存量有效配置和业务访问保持 |
| AC-11 | 同命令重试不产生重复对象；并发编辑不覆盖他人改动，页面保留草稿并显示可理解的错误 |
| AC-12 | 新权限、Route、菜单/按钮、既有角色授权可完成一个从登记到人员访问的完整场景，写入有既有审计记录 |
| AC-13 | 沿用既有 v1 及动态快照，旧路由/角色/菜单/IAM/风控配置仍可用；Target/Route 覆盖全部六类入口，资源写入仍仅 OPERATIONS，Client/Partner/Checkout 等身份不能调用 Operations 管理写接口 |
| AC-14 | 保存提示准确区分数据库提交与快照加载；没有增加审批或发布步骤，也没有启动时建表/种数据 |

| UI-01 | 在现有 Operations 布局内提供清楚的资源管理与 API 配置入口，菜单/按钮层级及 Target/Route 关系可辨认；阶段 3 Pencil 评审后研发 |

## 5. 本期不包含

- 风控新增功能或真实执行；人员和角色体系重建。
- 新的认证方式、Client/Partner 前端、API Credential 生命周期、Scope 管理、文件、通知与 Webhook。
- 任意远程组件、低代码页面/接口生成、任意 URL 转发、脚本或 SQL 数据源。
- 物理删除、批量导入导出、配置审批/发布/回滚引擎、配置历史版本与 Gateway 实例回执系统。
- 通过本次需求评审直接执行 SQL、部署或 Git 提交；仍逐阶段交付与确认。
