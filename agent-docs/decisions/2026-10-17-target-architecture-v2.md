## 1. 决定

目标架构分四层：接入层、流程层（围绕一笔交易的生命周期：收单、支付执行、出款、争议、外汇）、领域层（主数据、规则与资金账）、平台支撑层。流程层可调领域层，领域层不得调流程层。24 个逻辑服务各自持库、各自独立部署（D09 修订）；api / core / app 结构与 ArchUnit 门禁保证边界。

跨服务一致性不依赖本地事务：计费是唯一经济事实来源，账户与会计只消费计费明细；跨服务写操作分四类，取消由下游资源 Owner 终态裁决；事件按聚合键分区有序并携带版本号。读模型由数据服务在近实时数仓上提供，经 CDC 同步白名单表。实例是数据隔离边界，模块按清单装卸，品牌是配置而非部署，多实例运维平面不接触实例业务数据。

| D01 | 客户术语 | 已定 | 继续使用 Client（含 INDIVIDUAL / ORGANIZATION），不改为商户。 |

| D03 | 税务与发票的归属 | 已定 | 属基座，所有实例必装；PSP 模式下仅功能降级，不卸载。 |
| D04 | Checkout 是否独立 BFF | 已定 | 不设。收银台前端经网关直达收单 checkout 模块与支付执行；PCI 路径不增加节点。 |
| D05 | 资金权威 | 已定（2026-10-18 修订） | 账户 = 可用额度实时权威（明细账，含余额桶）；会计 = 法定报表权威（总账，只记控制科目）；账户消费计费事实，会计消费账户入账（`AccountPosted`），一致性由构造保证，关账前做 billing → account、account → ledger 两段进度检查；余额成功 / 记账失败不回滚余额。见 [2026-10-18 决定](./2026-10-18-account-ledger-subledger-control-account.md)。 |
| D06 | 渠道职责边界 | 已定 | 渠道连接是支付渠道领域唯一 Owner（适配、验签、映射、恢复查询、健康）；Platform 集成仅做通用出站执行与凭据读取；支付执行不直连渠道、不持凭据。非支付外部方由各自 Owner 经 Platform 集成接入。 |
| D07 | Webhook 触发源 | 已定 | Platform 直接消费 Owner 事件触发 Webhook；数据服务不触发通知。 |
| D08 | 流程 / 领域分类标准 | 已定 | 是否围绕一笔交易的生命周期；领域层不得调流程层，只通过事件感知交易。合规案件留领域层。 |
| D09 | 能力边界与部署边界 | 已定（2026-10-17 修订） | 每个逻辑服务从第一天起就是独立部署单元：独立 `*-app` 模块、独立进程、独立数据库；不做组合部署。保留 api / core / app 结构与 ArchUnit 包边界门禁；服务间只经 `*-api` 的 HTTP 调用，进程内本地 Bean 绑定仅限测试。原「初期合并为约 13 个部署单元、按四个触发条件拆分」作废。资源后果已接受：测试环境单机 8 核 64 GB，生产单实例计算约增加四分之一。payment / 卡域 / Vault / 网关 / BFF 独立不变。 |
| D10 | 卡域独立服务的条件 | 待定 | 独立部署 + 独立网络区 + 独立密钥三条同时成立才拆；由谁承诺与审计未定。 |
| D11 | 数据库变更执行方式 | 已定 | 评审原则不变；执行改为评审后的版本化 SQL 由实例内迁移执行器按实例执行并记录；不引入 Flyway / Liquibase。属工程规范变更，需修订 DEVELOPMENT_CONVENTIONS 与 DATABASE_DESIGN_GUIDE。 |
| D12 | 能力阶段标签 | 已定 | 两档：已运行（有可运行实现且自动测试通过，不代表已部署）/ 已设计。2026-10-17 对照台账核对：下调 19、上调 12；阶段 2 盘点再下调 1（Direct Pay 受理仅为保留枚举，无入口）。现 119 / 76。 |
| D13 | 审批与业务裁决边界 | 已定 | 审批引擎只记录「人已同意」；业务服务执行时重新校验并记录最终决定；审批通过 ≠ 可执行。 |
| D14 | 消费者可变档案与交易快照 | 已定 | 交易侧保存不可变消费者快照与法律证据；删除只作用于消费者服务的可变档案。 |
| D15 | 迁移成熟度证据 | 待定 | Finance / Risk「已有事件边界」仅有设计证据；拆分成本需按运行证据重估。 |
| D16 | 资金三服务保持拆分 | 已定 | 计费 / 账户 / 会计独立服务、独立库，职责优先于本地事务。一致性用 Saga / TCC 式多段本地事务 + 补偿 + 周期核对，不用 XA；账户消费计费的不可变经济事实，会计消费账户入账并在事务外读取计费明细（2026-10-18 修订，见 [决定](./2026-10-18-account-ledger-subledger-control-account.md)）。 |
| D17 | 取消与执行的裁决权 | 已定 | 裁决权在资源 Owner：取消是下游命令，带同一幂等键；下游状态机只允许待定 → 执行 / 取消之一；不可逆外部操作无取消。 |
| D18 | 跨服务写操作分四类 | 已定 | 查询后冻结 / 可逆跨服务命令（五步）/ 不可逆外部命令 / 事件消费；不共用终止与反向语义。 |
| D19 | 迁移阶段措辞 | 已定 | 旧服务「不再接受新建」但在途可写；只读仅在归档阶段；新建归新 Owner、存量归原 Owner 到终态；回退 = 停止新建，不搬数据。 |
| D20 | 模块三态与缺席最小登记 | 已定 | 启用 / 停用（只读）/ 卸载；有在途禁止卸载；基座保留外部结算登记、争议结果事实登记等最小能力。 |
| D21 | 品牌拆分与来源规则 | 已定 | 品牌 = 展示配置 + 法律引用；入口域名定新会话品牌，交易创建时冻结，后台任务用冻结品牌，租户只能用被分配品牌。 |
| D22 | 多实例运维平面权限与版本兼容 | 已定 | 不持任何实例数据库凭据；下发版本与脚本、兼容预检；实例内迁移执行器执行 SQL 并回传日志；升级按实例原子执行，允许 N 与 N-1 并存。 |
| D23 | 站点归属与分站前置设计 | 待定 | 订单按 Client 归属站点落库；回调经 MID → OE → 站点；站点不可用失败关闭。快照下发 / 失效、中心限制下传、站点事件积压需单独设计后才允许分站。 |
| D24 | 事件顺序保证 | 已定 | 分区有序 + 版本号兜底：按聚合键投递同一分区，事件携带聚合版本号，消费者按版本判定乱序与重放。 |
| D25 | 读模型：数据服务替代交易中心 | 已定 | 近实时 OLAP 数仓上的数据服务（秒级）；CDC 同步各服务白名单表 DML，不经 MQ；白名单与 PII 屏蔽是公开契约；Client / Partner 只走查询模板 + 服务端租户过滤；每实例一套；详情与操作前校验实时读 Owner。 |
| D26 | 服务间调用身份 | 已定 | Platform 签发短期内部签名 Token（调用方、目标、实例 ID、Purpose）；替代 X-Caller-Service + 静态白名单；后续可叠加 mTLS。 |
| D27 | 合规限制传播范围 | 已定 | 出款拒绝新出款与待审批出款；账户停止该 Owner 的在途转可用；新收单不受影响。 |
| D28 | 平台法人的 Owner | 已定 | 所有法律主体含平台自身法人都是客户主档的 Party；会计只为账簿主体开账簿并引用其 ID。 |
| D29 | 消费者身份 | 已定 | 不引入消费者账号；买家门户由收单签发订单级一次性 / 短期 Token。 |
| D30 | 消费者数据删除编排 | 已定 | 消费者服务是编排 Owner，发布 ConsumerErasureRequested；各 Owner 按留存规则执行并回报；订单证据按法律保留。 |
| D31 | 服务命名与术语表 | 已定 | 收单 = acquiring-service（transaction / checkout / command / client-api 四模块共用一库；Checkout Session 为可选子聚合；Direct Pay 不经 Session）；商务 = commercial-service；Acquiring 仅指受理层；Order 不作为服务名。 |
| D32 | NFR 目标 | 已定 | 单实例收单峰值 100–500 TPS；RTO 1 小时 / RPO 接近 0。 |
| D33 | 支付执行与收单的关系 | 已定 | 支付执行保持独立服务与部署；Acquiring → Payment → Channel 三层；收单创建 Intent 为可逆跨服务命令，由支付执行终态裁决。 |
| D34 | 事件总线选型 | 已定 | 继续 RabbitMQ；分区有序用一致性哈希交换机按聚合键路由到固定队列组，每队列单活消费者；事件信封带聚合键、版本号、事件 ID、Schema 版本；落在 compensation-event 库与事件目录。不引入 Kafka。 |
| D35 | 数仓选型 | 已定 | 数据服务建在 Apache Doris 上，Flink CDC 同步白名单表 MySQL DML，每实例一套；阶段 0 只建本地容器骨架与白名单约定。 |
| D36 | 重构落地方式、分支策略与阶段 0 范围 | 已定（2026-10-17 修订） | 同仓新骨架：仓库顶层 `paytech/` 单一 reactor，下按 V2 服务分目录。逐模块 git mv 搬迁，顺序 Foundation → Platform / Gateway / BFF / Vault → Commerce / CCT / Payment / Risk / Finance；搬迁期间该系统其他会话暂停。分支：长期集成分支 `refactor-main`，每步短分支合入，不逐步合回 main；每步后合入 main 控制分叉；全部完成后在 refactor-main 全链路验证，验收后整体合并 main。阶段 0 范围：模块重组与每服务独立部署（D09 修订）、门禁、事件信封与目录 v1、数据服务与迁移执行器骨架、内部签名 Token，**以及两处事务逻辑重做**——Finance 账户与会计分库（`t_account` 拆为会计科目账户与账户余额账户，过账与余额更新改为最终一致，按 D16 / S1）、Payment 卡域独立进程与独立库（支付成功对卡表的写入改为事件驱动，读卡回调改为 payment 签发的一次性有范围授权，按 S3）。两处方案在阶段 3 设计、阶段 4 实现，其余搬迁不改业务行为。不另起项目，不原地改造。 |
| D37 | 经济事实唯一来源与账户消费口径（阶段 3 C1） | 已定（2026-10-17） | 计费是唯一经济事实来源；阶段 0 即引入最小计费能力（`t_transaction_economics` 三表更名为 `t_economic_fact*`，人工调整与成本调整经计费登记为经济事实，发布 `EconomicFactRecorded`）。账户从一开始只消费经济事实维护余额桶，不消费会计过账事件；会计消费同一事实自动过账（2026-10-18 修订为会计消费账户入账，见 [决定](./2026-10-18-account-ledger-subledger-control-account.md)）；影响 Owner 余额的人工调整不得直接在会计提交。方案见阶段 0 需求 design/04。 |
| D38 | 结算控制归属（阶段 3 C3） | 已定（2026-10-17） | `t_settlement_control`、`t_settlement_control_scope`、`t_settle_control_state_change` 归合规服务（`mor_compliance`）。风控决策 Action Effect 产生控制时经 compliance-api 创建（幂等键 `source_action_effect_id`），出款检查点评估在事务前经 compliance-api 读取 ACTIVE 控制集合并冻结 `control_set_hash`；合规不可用则评估失败关闭。变更经 `SettlementRestrictionChanged` 事件通知出款与账户。 |
| D39 | 消费者法律文档与卖方披露归属（阶段 3 C4） | 已定（2026-10-17） | `t_consumer_legal_document`、`t_seller_disclosure` 归客户主档（`mor_client_master`）。候选接口按消费者国家与语言随每个候选返回三份法律文档引用与卖方披露，商务两段式解析直接取候选自带值，不再读这两表。 |
| D40 | `risk-api` 拆分方式（阶段 3 C6） | 已定（2026-10-17） | `risk-api` 一次性拆为 `risk-decision-api` 与 `compliance-api`，不保留聚合坐标与兼容期；研发计划第 6 步在同一分支内同步修改五个消费方的坐标与 import，是阶段 0 唯一允许一步改多个系统的例外，排在收单、客户主档、支付三步之后执行。 |
| D41 | 全平台参考数据归属（阶段 3） | 已定（2026-10-17） | `t_currency_spec` 等全平台参考数据归平台支撑（Platform）持有并提供查询 API；会计与计费为保证过账与舍入不依赖远程调用，各持同结构只读副本，用同一份评审 SQL 初始化；副本同步机制在后续切片定义。 |
| D42 | 阶段 3 其余表归属与服务改名口径 | 已定（2026-10-17） | 尚无代码的渠道相关表按建议归属（路由策略、渠道交互与回调归渠道连接；渠道交易引用归支付；渠道争议归争议库）；现金账户三表归对账；订单法律文档快照与退款头寸归收单；`t_client_stored_card_setting` 为 Client 级配置归客户主档并随候选接口返回。改名服务不在 Nacos 保留旧名别名，改名步骤同分支改完全部调用方。 |

## 3. 取代范围

本决定当前**不取代**任何现行权威。`AGENTS.md`、`PROJECT_CONTEXT.md`、`APPLICATION_ARCHITECTURE.md`、`JAVA_PROJECT_STRUCTURE.md`、`database/` 文档与各专项决定继续描述并约束**运行中的系统**。本决定描述**重构目标**；每个切片落地时，由该切片的需求交付流程逐一提出对现行文档的精确取代范围并确认。

已知将被后续切片取代或修订的现行规则：D11（人工执行 SQL 的执行方式）、D26（`X-Caller-Service` + 静态白名单）、D09（模块与部署单元的组合方式）、D25（BFF 页面聚合与读模型分工）。
