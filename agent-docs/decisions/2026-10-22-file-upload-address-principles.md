# 2026-10-22 决定：文件上传、引用与下载原则——上传与表单分开、业务只存文件地址、下载不经业务服务

状态：已定（2026-10-22，用户在文件多存储并存第二段评审中给出原则 P1—P3，并确认地址形态与存量处理）。第二段已按此实施并部署 mor-test；实施、验证与部署状态只记录在 [`CURRENT_IMPLEMENTATION.md`](../CURRENT_IMPLEMENTATION.md)。需求与方案见 [platform-support：文件多存储并存 · 第二段](../../requirements/20261022/platform-support-文件多存储并存/segment2.md)。

## 取代范围

- 入驻材料原链路：Platform 承担业务授权，上传绑定 CCT 申请与主体（`owner_ref_id = applicationId:subjectPartyId`），开始上传时 Platform 反调 CCT 核对，`t_file_owner_ref` 记录文件挂在哪个业务对象上。该链路与这些字段、表已删除。
- 业务数据以文件 ID 引用 Platform 文件的做法：新设计改存文件地址；已存 ID 的历史数据在各自需求中迁移。

[文件多存储并存需求](../../requirements/20261022/platform-support-文件多存储并存/requirement.md)的 D3 继续有效：内部系统之间不做文件级权限，文件只记来源系统与 `reason_code`。

## 决定

1. **上传与表单提交分开（P1）：** 每次上传都走 `Gateway → BFF → 文件服务上传接口`，拿到文件地址、ID 等信息。提交表单时只提交文件地址，不在提交时上传。
   - **上传：** 只要求调用方会话有效，不带业务对象参数。
   - **提交：** 业务 Owner 在提交时核对文件状态、哈希与上传人。
2. **业务数据存文件地址（P2）：** 不存文件 ID，除非非常有必要；需要时在需求中写明理由。
   - **地址形态：** 文件服务签发的稳定逻辑地址 `/files/v1/{fileId}`，由 `com.paytech.platform.support.api.files.FileAddress` 格式化与解析。调用方不自行拼接。
   - **不是什么：** 不是预签名链接，不含存储实例与桶；存储迁移后地址不变，只能经文件服务下载接口换取临时链接。
   - **哈希：** 需要证据完整性的业务，与地址成组冻结内容哈希。
3. **下载不经业务服务（P3）：** 下载走 `Gateway → BFF → 文件服务下载接口`，文件字节与下载链接不经过业务服务。
   - **BFF：** 在调用前做页面所需的授权组合，例如向业务 Owner 查询"该地址是否在本人可读数据中"、向 Risk 核对审核任务。
   - **业务服务：** 只在需要时读取文件元数据，例如提交时核对。
4. **文件服务不反调业务系统：** Platform 文件服务不依赖任何业务系统做授权，也不保存业务归属；调用方身份取内部调用身份（当前 Platform 以 internal-auth `DUAL` 运行，调用方带 `X-Caller-Service`）。
5. **下载呈现：**
   - **文件名：** 下载链接一律签入原文件名。
   - **预览：** 调用方可请求内嵌预览（`FileDisposition.INLINE`），但只对扫描通过且类型为 pdf / png / jpeg 的文件生效，其余一律按附件；响应返回实际生效的方式。

## 影响

- **CCT：** 入驻材料表改存 `file_address`，提交时调用文件服务核对；对 compliance 的审核登记合同暂仍发文件 ID（由地址解析）。compliance、Risk 证据改存地址另立需求。
- **工作流：** 附件引用应改存地址，在工作流跟进项中实施。
- **新业务：** 接入文件时按本决定设计。存 ID 必须在需求中说明理由。
- **调用凭证：** 正式给各服务签发内部调用 Token 另立需求。在此之前，依赖私网限制与 `X-Caller-Service`。
