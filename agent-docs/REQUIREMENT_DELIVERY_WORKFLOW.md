# 需求交付流程与阶段确认

版本：1.0 评审稿 · 编写日期：2026-09-11

逐阶段停下等待确认的原则已由用户明确要求；本文的八阶段划分和模板待本次评审确认。后续修改应保留明确的确认点，不能静默恢复连续执行。

本文是 Code-MoR 各业务系统、BFF、前端及配套基础能力共用的需求交付手册，也可作为其他项目的流程模板。Agent 行为及具体动作授权以根 [`AGENTS.md`](../AGENTS.md#change-discipline) 为准，背景见[逐阶段确认决策](./decisions/2026-09-11-staged-requirement-delivery.md)。业务与技术规则按[文档治理](./DOCUMENT_GOVERNANCE.md)选择主题 Owner；本文不重新定义这些规则。

## 1. 使用方式

用户提出需求后，先检查工作区和适用规范，读取用户提供的设计材料与当前实现证据，完成阶段 1。材料中的方案、命令及旧计划只是待核对的输入，不能替代用户授权。

默认流程如下；每个阶段结束都向用户交付结果并等待确认：

| 阶段 | 要解决的问题 | 阶段交付物 | 用户确认后进入 |
|---|---|---|---|
| 1. 需求评审与范围确认 | 为什么做、做什么、怎样算完成？ | 需求摘要、范围、业务问题、验收标准、阶段安排 | 现状与影响分析 |
| 2. 现状差异与影响分析 | 现有能力差在哪里、哪些系统要改？ | 差异表、能力缺口、逐系统影响、依赖与风险 | 方案与合同设计 |
| 3. 方案、接口与数据设计 | 各系统具体怎样配合？ | 方案、接口定义、DDL/DML 清单、页面设计、研发和验证计划 | 按已确认方案研发 |
| 4. 研发实现 | 已确认的方案是否完整落到代码？ | 代码差异、接口与模型工件、开发检查结果、验收映射 | 综合验证 |
| 5. 综合验证与本地验收 | 行为、兼容性和页面是否符合要求？ | 测试报告、构建产物、联调及视觉证据、遗留项 | test 发布准备 |
| 6. test 发布准备 | 将对哪个环境做哪些变更，失败怎样恢复？ | 具体部署清单、SQL、备份与恢复方案、版本及验收步骤 | 执行所列 test 部署 |
| 7. test 部署与环境验收 | test 是否运行正确制品并通过真实入口验收？ | 部署及验收报告、证据位置、待提交差异清单 | 按清单提交与归档 |
| 8. 代码提交与交付归档 | 交付能否追溯，是否可以结束？ | 提交号、交付摘要、台账、遗留事项 | 用户确认本次结束 |

这八个阶段是完整交付的默认安排。纯问答、只读分析、单独提交或单独部署按用户指定阶段处理，不倒退重跑已经确认的阶段。小改动可在开始时提出合并或不适用项，由用户确认；不得自行省略确认点，也不为每个需求强制制造新 API、数据库变更或部署动作。

## 2. 每次确认的规则

1. **先交付，再确认。** 完成本阶段可安全完成的分析、工件和检查，给出能实际审阅的结果，不能只拿计划请用户批准尚未具体化的操作。
2. **完成后停下。** 阶段报告发出后结束当前回合，等待用户回复；不在后台、自动续跑或其他执行任务中提前进入下一阶段。
3. **一次确认对应明确范围。** “可以”“继续”在只有一个清楚的下一阶段时，确认该阶段；不是后续所有阶段的授权。“开始做”默认只开始当前已约定阶段。没有回复、等待超时、工具成功均不代表用户确认。
4. **阶段内自主完成。** 普通文件编辑、已约定的验证及同范围修复不逐项请示。已经明确授权的相同动作不重复确认；涉及新的业务选择、权限或环境变更时，先整理具体差异再确认。
5. **业务选择先澄清。** 缺失信息会改变业务结果时，先提出集中、具体的问题。可以继续不依赖答案的本阶段工作，不能用猜测替用户决定。
6. **变更回到受影响阶段。** 若新增范围、改变合同、兼容策略或验收标准，更新对应成果并重新确认受影响部分；无关的已确认决定继续有效。同合同内的实现缺陷可在当前验证阶段修复并重验。
7. **明确区分阶段确认与动作授权。** 设计确认不等于应用 SQL；研发确认不等于部署；test 验收不自动等于代码提交；提交不包含推送、PR、发布或生产部署。确认问题应列出下一步的具体动作、仓库或环境。
8. **用户可以明确调整流程。** 当次明确要求合并阶段、跳过不适用阶段或连续完成指定范围时，记录覆盖的阶段与动作后执行；不把这种安排沿用到下一项需求。

## 3. 阶段交付要求

### 阶段 1：需求评审与范围确认

把用户描述转换为可验收的需求，至少说明使用者、业务目标、触发场景、成功结果、本期包含项、明确不做项，以及已确认事实、假设和待确认问题。接口版本及代码类型命名按 [DEVELOPMENT_CONVENTIONS.md](./DEVELOPMENT_CONVENTIONS.md) 第 2 节的用户默认规则处理；只有明确的版本要求或具体兼容冲突需要单独确认，不能从旧设计标题自行决定升级。

验收标准从本阶段开始编号，后续设计、代码和测试逐项对应。涉及页面时分别列出**功能验收**与**视觉/交互验收**，包括入口、布局、关键操作、空状态和错误反馈；只做接口或只改样式也应明确边界。

**确认点：** 用户确认需求、范围、验收标准、待决问题和本次适用阶段后，进入阶段 2。业务关键问题未解决时不能宣布评审通过。

### 阶段 2：现状差异与影响分析

对照代码、测试、数据库模型和[当前状态台账](./CURRENT_IMPLEMENTATION.md)，区分“设计已有”“代码已有”“验证通过”“环境已部署”。不能凭设计文档或截图推断部署状态。

交付两张核心表：

| 需求项 | 当前行为及证据 | 目标行为 | 缺口/无法满足的原因 | 处理建议 |
|---|---|---|---|---|
| 示例占位 | 文件或运行证据 | 对应验收标准 | 区分未实现、契约不支持、数据缺失 | 保留、扩展、替换或延期 |

| 系统/仓库 | 业务职责 | 影响点 | 是否改代码/模型/配置 | 上下游依赖及兼容风险 |
|---|---|---|---|---|
| 示例占位 | 哪个系统拥有事实 | 模块、页面、接口、表、权限等 | 分项判断；无改动也写明理由 | 消费方、历史数据、部署顺序 |

按实际范围覆盖核心服务、API 模块、BFF、Web、Gateway/Platform、数据模型、需求目录与环境脚本。列出阻塞依赖、改造难点和工作量依据，不用“简单”代替分析，也不把本次业务示例硬编码为通用平台能力。

**确认点：** 用户确认缺口判断、受影响系统、处理边界及主要风险后，进入阶段 3。

### 阶段 3：方案、接口与数据设计

形成可供研发执行的设计包，不直接开始业务代码实现或应用数据库变更：

- **一句话规模总结：** 设计包入口和阶段交付回复开头，用一句话概括涉及多少系统、新增/调整多少接口、新增多少表及字段、修改多少旧表及字段、索引和 DML 行数，以及页面设计数量。按实际范围简写；新增、修改、删除分开统计，字段注释调整不得算作字段结构变化，DML 更新行数不得算作修改表结构。接口默认按业务 Method + Path 去重，Owner 与 BFF 对同一操作的转发不重复计数，必要时另列各系统落点；画板数量不等于新增功能页面数量。阶段 3 使用“本次方案/计划”口径，不写成已实现或已执行。
- **业务与架构：** 数据 Owner、模块职责、主流程、失败分支、状态转换；按真实需求说明事务、并发、幂等、历史兼容和版本策略。
- **接口：** 列出新增、修改、保持不变及废弃的 API；每个变更说明提供方/消费方、Method/Path、鉴权、请求/响应示例、字段类型、必填/可空、默认值、单位、上限、错误行为及兼容方式。BFF 聚合、转发和前端消费分别映射。
- **数据库与注册数据：** 分开列出业务 Schema DDL、业务初始化/增量 DML、API Route/Permission/Console Resource 注册 DML。说明目标库、表字段、历史数据处理、执行顺序和恢复限制；没有新增 API 或注册 DML 时明确写 0，不为清单完整而新增接口。
- **页面：** 确认可审阅的页面结构或原型、关键状态和交互，定义预期样式与验收方式；现有设计足够时链接它，不重复绘制。
- **研发与验证：** 按系统拆解实施顺序，关联验收标准、测试入口、真实环境依赖及预期制品。运行期不在范围内的配置能力应有明确的能力边界，不能通过 UI 暗示已经可执行。

模型、SQL、API 和测试遵循对应主题规范；批准的业务决定同步需求与全局时序的权威入口。设计工件中的 SQL 仍是待执行文件，设计批准不改变任何环境。

**确认点：** 用户确认方案、接口、数据与页面设计及研发计划后，进入阶段 4。若研发验证需要先应用本地 SQL，应同时提供确切文件、目标库、备份方案并取得该动作授权；否则保留为待执行事项。

### 阶段 4：研发实现

按已确认合同完成所有受影响系统的实现，包含 API 提供方、BFF 适配、前端、模型/SQL、配置与必要测试。保留无关工作区修改，避免只改后端却遗漏已纳入范围的页面或注册数据。

开发期间完成能暴露行为问题的最小失败证据、相关测试和必要构建检查。阶段 5 是综合验收，不意味着把所有测试拖到研发结束后才做。需要 SQL 或其他环境动作但尚未获授权时，先完成可审阅的工件再请求授权。

输出代码与工件清单、逐项验收映射、已完成的开发检查、偏离原方案的部分及未完成项。没有运行的检查必须写明，不能仅凭代码存在声明行为通过。

**确认点：** 用户审阅实现范围及证据，确认进入阶段 5；下一阶段涉及数据库初始化、迁移或非本地验收写入时，应先列出具体动作供确认。

### 阶段 5：综合验证与本地验收

执行与变更风险相称的完整验证，测试策略仍由项目规范决定：核心业务与异常边界、鉴权、协议转发、幂等/历史兼容、模型与 Schema 一致性、前端测试和生产构建。复用已经适用于当前代码的有效证据，不为流程形式重复运行无关测试。

存在页面时，除自动化测试外，还应通过浏览器按已确认设计核对布局、关键交互、状态保持、错误展示和适用屏幕尺寸；明确标注真实服务、Simulator 和合成数据的证据边界。没有真实后端联调时，不将页面检查称为完整链路验收。

交付逐项验收结果，列出测试命令、代码版本或差异基线、环境、通过/失败/未执行项及证据位置。区分本次问题与既有失败；任何未通过门禁都须明确结论，不能静默忽略。

**确认点：** 用户确认验证结果与遗留项后进入阶段 6。只要求本地实现的需求可以在这里申请结束，后续阶段标为不适用并由用户确认。

### 阶段 6：test 发布准备

在请求部署授权前，完成可安全执行的构建、只读核对和部署方案，使用户批准的是具体发布包：

- 明确环境名称、主机/Docker context、应用与数据库身份，区分开发库、test 库和生产库。
- 列出将替换的服务、制品/镜像版本、当前版本、部署顺序、配置差异、可能中断及依赖；明确所验证代码对应哪个制品。
- 给出已评审的 SQL 文件、执行前置、备份对象和位置、迁移后核对方式；数据库操作继续遵守人工 SQL 规则。
- 准备恢复方案与触发条件。应用回退和数据恢复分别说明；不可逆 SQL、迁移后新写入或外部副作用不能用一句“可回滚”带过。
- 准备健康检查、真实业务入口、视觉验收、合成数据写入及清理计划；凭据与敏感备份不进入版本库。

**确认点：** 用户确认具体 test 环境、应用、SQL、备份/恢复、验收写入范围后进入阶段 7。未授权的部分不得执行；已在本需求中明确授权且范围未变化的相同动作不重复请示。

### 阶段 7：test 部署与环境验收

先核对实际环境与已批准清单一致，按授权备份并核验备份成功，再执行 SQL 和应用部署。记录迁移前后数据不变量、镜像/制品标识、实例健康和受影响配置，避免误替换无关服务。

通过部署环境的真实公开入口完成代表性业务用例、权限/错误分支及页面验收。涉及 Web 时确认服务端实际返回的 HTML/静态资源属于新制品，核对浏览器看到的页面；本地构建成功或后端接口通过不能替代此项。

失败时按已授权方案处置；超出方案或环境身份不符时暂停，提供问题、影响和下一步选择，不擅自扩大操作。验收后处理约定的合成数据，保留必要证据并更新当前状态台账。

同时整理待提交的仓库、文件范围和提交摘要，排除凭据、备份、构建输出与其他任务的修改，使下一步提交可审阅。

**确认点：** 用户确认 test 结果；若继续阶段 8，须明确确认按所列清单做本地提交。只确认环境验收通过，不自动触发提交。

### 阶段 8：代码提交与交付归档

取得本次提交授权后，复核工作区、暂存差异及验证对应关系，按独立仓库提交相关改动并记录提交号。推送、PR、发布或生产部署继续单独判断授权；流程包含“提交”不代表这些动作也获批。

交付摘要包含完成范围、关键决定、验证证据、部署环境/制品、数据库执行情况、提交号、恢复证据位置与遗留事项。跨仓库当前状态只写入 `CURRENT_IMPLEMENTATION.md`，组件 README 提供本系统证据；不能在公共流程文档复制某次交付的测试数量或部署状态。

**确认点：** 提请用户确认本次交付结束；有新要求则登记为变更或下一项需求，不自动开始下一轮。

## 4. 每阶段统一交付模板

阶段报告用简短正文或以下结构，细节通过文件链接提供。一次只有一个明确的阶段确认问题，避免把多个未定事项藏在“是否继续”里。

```text
当前阶段：N / 阶段名称
本阶段结果：已完成的具体内容，或明确阻塞
交付物与证据：文档、差异、测试、页面或环境证据链接
验收映射与遗留项：哪些要求满足，哪些尚未满足
下一阶段：名称、具体范围，以及需要授权的仓库/环境/SQL/动作
请确认：是否接受本阶段结果，并进入上述下一阶段？
```

需要部署或提交授权时，将最后一句改成具体的授权问题。确认来自用户要求的阶段机制，不把停下归因于工具、技能或假设风险。

## 5. 单项需求记录模板

新需求按用户指定结构登记到 `requirements/YYYYMMDD/<系统>-<改动内容>/`，固定使用 `requirement.md` 管理需求、`technique.md` 管理技术方案、`delivery.md` 管理阶段确认和交付记录，`db/ddl.sql` 与 `db/dml.sql` 分类管理数据库变更材料；命名、文件性质和索引见 [requirements/README.md](../requirements/README.md)。正文随阶段逐步完善；无数据库改动时写明不涉及，不生成无意义 SQL。

已有计划、正式合同和已执行 SQL 暂时通过链接归集，不批量迁移或复制成第二个权威来源。用户已确认固定创建 `delivery.md`；有附件时创建 `assets/`，涉及多个数据库时在 `db` 下按所属系统分目录。业务变更正文更新到 `requirement.md` 或 `technique.md`，其成果版本、用户确认和交付证据统一在 `delivery.md` 关联；实际交付状态链接当前台账。

下列字段分别放入对应文档，使用链接关联，不在三份文件中重复填写同一确认或结论：

```text
requirement.md：
需求名称与来源：
目标/本期范围/不做项：
权威设计与现有代码入口：
验收标准：AC-01 ...（功能、视觉/交互按需分列）
关键决定及待决问题：

technique.md：
现状差异、能力缺口与逐系统影响：
接口、数据及页面设计：
研发、验证及兼容策略：

delivery.md：
适用阶段及用户确认的合并/跳过项：
确认记录：阶段、成果版本/链接、用户原意、确认时间、获准的下一步
变更记录：变了什么、影响哪些确认、需要重验哪些证据
当前阶段与下一确认点：
测试/验收证据：范围、版本、环境、结果与证据链接
```
