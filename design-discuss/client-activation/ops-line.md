## 1. 一句话

**每个 Client 有一位"上线负责人"对全程负责；每一步拆成有明确队列、明确完成标准、明确时限的任务；需要四眼的地方拆成两张任务、系统保证不是同一个人；任务做完系统自动把下一张卡推给下一个队列，并带上交接备注。**

## 2. 运营组织

### 2.1 角色与队列

| 队列编码 | 中文名 | 成员 | 负责的任务 | 首期人数建议 |
|---|---|---|---|---|
| `ONBOARDING_LEAD` | 上线主管 | 运营主管 / 合规组长 | 发起流程、指定上线负责人、终止、回退、超时升级的第二级 | 1–2 |
| `ONBOARDING_OWNER` | 上线负责人 | 运营专员 | 一个 Client 全程的单一联系人：跟进所有"等 Client"节点、提交上线复核 | 2+ |
| `COMPLIANCE_REVIEW` | 合规审核 | 合规专员 | 案件审核与推荐 | 2+ |
| `COMPLIANCE_DECIDER` | 合规决定 | 合规组长 / MLRO | 资格决定 | 1–2 |
| `RISK_UNDERWRITING` | 风控承保 | 风控专员 | 人工承保、LOW 级上线复核批准、观察期评估 | 1–2 |
| `RISK_LEAD` | 风控负责人 | 风控负责人 | HIGH 承保复核、MEDIUM / HIGH 上线复核批准 | 1 |
| `COMMERCIAL` | 商务 | 商务经理 | 起草合同与价格、发起签署、登记签署 | 1+ |
| `COMMERCIAL_APPROVER` | 价格审批 | 商务负责人 | 价格审批（已有规则：提交人不得审批） | 1 |
| `CHANNEL_OPS` | 渠道运营 | 渠道专员 | MID 录入、OE 扩 MCC、（M3）子商户与渠道登记 | 1 |
| `TECH_SUPPORT` | 技术支持 | 技术支持 | 跟进接入、生产交易验证 | 1 |
| `FINANCE_OPS` | 财务运营 | 财务专员（M4） | 收款账户核验（Maker / Checker）、保证金确认 | 2 |

一个人可以在多个队列；四眼约束按"任务"判断，不按"队列"判断（见 3.4）。

### 2.2 上线负责人（Onboarding Owner）

行业做法（Adyen、Checkout.com 的 Onboarding Manager）：每个新商户有一个人对上线结果负责，其他职能是"供给方"。

| 项 | 规则 |
|---|---|
| 何时指定 | 发起流程时必填，默认是发起人；上线主管可改派 |
| 职责 | ① 所有"等 Client"节点的跟进人；② Client 的唯一对外联系人（其他职能需要 Client 配合时，通过上线负责人或在卡片里 @ 他）；③ 提交上线复核；④ 每周检查自己名下 Client 是否有卡住的节点 |
| 不做 | 不替其他职能做专业判断（尽调决定、承保、价格审批） |
| 看到什么 | 待办第三页签"我负责的上线"：名下所有在途 Client，当前节点、卡在谁、已等多久 |
| 工作量 | 建议每人在途 ≤ 30 个 Client；看板显示每位负责人的在途数 |

## 3. 任务模型

### 3.1 任务类型

| 类型 | 说明 | 例 |
|---|---|---|
| **处理** | 队列成员认领后在 Owner 页面做事 | 审核材料、起草合同、录入 MID |
| **复核** | 四眼的第二人，必须不是"处理"任务的执行人 | 资格决定、价格审批、账户 Checker、上线复核批准 |
| **跟进** | 等 Client / 等外部；没有"做完"按钮，事实到了自动完成 | 等签署、等补件、等接入 |
| **异常** | 系统发现卡住时生成 | 开通项超过 1 个工作日未生效 |

### 3.2 任务生命周期

```
            认领                       提交 / 事实满足
 待认领 ───────────▶ 处理中 ─────────────────────────────▶ 已完成
   ▲  │                │ ▲                                  
   │  │ 直接指派        │ │ Client 补件回来 / 外部回执       
   │  └──────────────▶ │ │                                  
   │   放回队列         ▼ │                                  
   └──────────────── 等待中（SLA 暂停：等 Client / 等外部）  
 任意状态 ──流程终止 / 回退──▶ 已取消
```

| 状态 | 含义 | SLA |
|---|---|---|
| 待认领 | 在队列里，没人接 | 计时（认领也算在处理时限内） |
| 处理中 | 有执行人 | 计时 |
| 等待中 [M2+] | 处理任务内部要等 Client（如 N1 退回补件） | **暂停**；另有跟进时限。M1 不暂停，审核员把任务转交给上线负责人跟进，补件回来再转回 |
| 已完成 / 已取消 | 终态 | — |

### 3.3 分配规则

| 规则 | 内容 |
|---|---|
| 默认 | 进入队列，成员自行认领（按 SLA 剩余时间排序） |
| 粘性分配 [M2+] | 同一 Client 的后续同队列任务，默认直接指派给上次处理人（如 N1 补件回来仍是原审核员；N3 → N4 登记签署仍是原商务）。M1 靠队列成员自觉认领同一 Client |
| 认领上限 [M2+] | 每人处理中任务上限（默认 15），超过不能再认领 |
| 转交 | 执行人可转交给同队列成员，必填原因；保留历史（workflow 已有） |
| 请假 [M2+] | 成员标记不在岗时，其待认领粘性任务回到队列；处理中任务提醒组长改派。M1 由组长手工转交 |

### 3.4 四眼规则

需要两人的地方拆成"处理 + 复核"两张任务，复核任务的候选人**排除**处理任务的执行人（以及发起人，如适用）。系统在认领和提交两处都校验；Owner 系统仍保留自己的四眼校验（双保险）。

| 处理任务 | 复核任务 | 复核人 |
|---|---|---|
| T03 案件审核与推荐 | T04 资格决定 | `COMPLIANCE_DECIDER`，≠ T03 执行人 |
| T06 人工承保（HIGH） | T08 承保复核 | `RISK_LEAD`，≠ T06 |
| T09 起草合同与价格 | T10 价格审批 | `COMMERCIAL_APPROVER`，≠ T09（commercial 已有） |
| T21 账户核验 Maker | T22 账户核验 Checker | `FINANCE_OPS`，≠ T21 |
| T26 提交上线复核 | T27 批准上线复核 | LOW：`RISK_UNDERWRITING`；MEDIUM / HIGH：`RISK_LEAD`；≠ T26 |

### 3.5 时限（SLA）

| 项 | 规则 |
|---|---|
| 单位 | 工作小时 / 工作日，按**运营工作日历**（首期一份：周一至周五 09:00–18:00 GST，节假日可维护） |
| 计时 | 从任务生成开始；"等待中"暂停 [M2+]；整套 SLA 计时与升级属 REQ-09（M2），M1 只在卡片上显示生成时间与已等天数 |
| 预警 | 用掉 75% 时卡片变黄，通知执行人（未认领则通知队列） |
| 超时 | 100% 变红，通知执行人 + 上线负责人；超时 1 个工作日再升级到上线主管 |
| 跟进时限 | 等 Client：第 3 个工作日提醒跟进人催办，第 7 个工作日升级上线主管，第 15 个工作日提示"是否终止"；等外部：按节点 SLA |
| 全程目标 | C3 / C1 LOW：10 个工作日内收款上线（不含等 Client 时间） |

### 3.6 待办排序

1. 已超时 → 2. 预警 → 3. 复核任务（别人在等你） → 4. SLA 剩余时间升序 → 5. 生成时间。

### 3.7 交接备注

每张任务提交时可填"交接备注"（选填，≤ 500 字），自动显示在下一张任务卡片顶部。例：承保员写"预售型业务，已要求保证金 USD 20,000，合同 T+N 不得低于 7"，商务起草合同时第一眼就能看到。

## 5. 逐任务作业说明

每张卡片的固定结构：**谁 / 打开后看到 / 去哪做 / 逐项操作（☐ 人工判断，⚙ 系统已核对）/ 提交后系统做什么 / 常见情况**。以下只写 M1 必需的任务，M3 / M4 任务在对应需求阶段 1 补齐。

### T01 发起上线流程并指定负责人（上线主管）

- **打开后看到**：入驻审核列表"待发起"筛选；每行：Client 名、辖区、申请类型、PayFac、已提交天数、申请状态。
- **逐项操作**
  - ⚙ 申请状态 ∈ SUBMITTED / UNDER_REVIEW / RETURNED / APPROVED（否则按钮置灰并说明）
  - ⚙ 入驻码属于 AFFILIATED PayFac 或为 C3 直连（Q-10；否则提示"外部 PayFac 客户暂不支持"）
  - ☐ 选择上线负责人（默认自己；下拉显示每人在途数）
  - ☐ 点「发起上线流程」
- **系统做什么**：建实例；对 N1、N7 立即核对一次；T02 给技术支持（跟进），T03 进合规审核队列；通知上线负责人"你负责的新 Client"。
- **常见情况**：已有进行中实例 → 直接打开；误发起 → 上线主管终止并填原因。

### T03 案件审核与推荐（合规审核）

- **打开后看到**：Client、辖区、主体类型、档次（STANDARD / ENHANCED）、材料 x/y 已审、筛查命中 n 条未处理、关系人子案件 x/y、SLA。
- **去哪做**：审核工作台 `/client-onboarding/reviews/{caseId}`。
- **逐项操作**（工作台各页签，顺序固定）
  1. ☐ **申请**：核对法定名、注册号、注册地址与证件一致
  2. ☐ **材料**：逐件接受 / 拒绝（原因码）；过期证件必拒
  3. ⚙ **筛查**：机构与每位关系人已跑名单（制裁 / PEP / 负面）；☐ 每条命中判定为真命中 / 误报并写依据
  4. ☐ **人工检查**：网站审查（商品与申报一致、退款政策、联系方式、价格币种）；MATCH / VMSS；地址证明；银行证明户名
  5. ⚙ **关系人**：UBO（≥ 25%）、董事、签字人子案件全部有结论
  6. ☐ **分类**：确认行业与 MCC；⚙ 禁止行业自动拦截，限制行业提示加强尽调
  7. ☐ **风险**：给 CRR 与依据；HIGH 自动升 ENHANCED 并列出需补材料
  8. ☐ **推荐**：批准 / 拒绝 / 退回补件，写推荐意见
- **退回补件**：选择缺失项（需求级错误码）→ 案件 RETURNED → 任务进入"等待中"（SLA 暂停），T03w 给上线负责人跟进 → Client 重提后任务回到**原审核员**。
- **提交后**：T04 进合规决定队列（排除本人）；交接备注带给决定人。

### T04 资格决定（合规决定）

- **打开后看到**：推荐结论与意见、CRR、命中处理摘要、检查结果摘要；"推荐人：张三"。
- **逐项操作**：☐ 复核推荐依据（可抽查任一页签）→ ☐ 决定：批准（设定资格有效期与下次复审日）/ 拒绝（原因码）/ 退回审核员（回 T03，原审核员）。
- **系统做什么**：批准 → Client ACTIVE，发布资格事件；同时生成 N2（自动或 T06）与 T09；拒绝 → 流程结束，通知上线负责人，Client 收到结果邮件（已有）。

### T06 人工承保（风控承保）／ T08 承保复核

- **打开后看到**：CRR、MCC、预计月流水与客单价、交付方式、目标国家、网站；为什么没走自动承保（例："CRR = MEDIUM"）。
- **去哪做**：承保页 `/risk/underwriting/new?clientId=`（新）。
- **逐项操作**
  1. ☐ 交付周期与拒付暴露：即时交付 / 预售（天数）/ 订阅
  2. ☐ 三档额度：验证档（默认单笔 ≤ 50 USD、日 ≤ 5 笔）、观察档、标准档的单笔 / 日 / 月
  3. ☐ 观察期：天数或笔数（默认 30 天或 100 笔）
  4. ☐ 保证金：是否要求、金额、是否阻塞收款（默认否）
  5. ☐ 结算周期建议 T+N
  6. ☐ 是否高风险 MCC 需卡组织登记（⚙ 系统按清单预勾）
- **提交后**：MEDIUM / LOW → 承保 APPROVED，完成；HIGH → T08 给风控负责人（排除本人）；交接备注给商务（T09 卡片顶部可见）。

### T09 起草合同与价格并提交审批（商务）

- **打开后看到**：Client、CRR、MCC、承保结论（额度、保证金、T+N 建议）、Client 申请里的期望支付方式、承保员交接备注。
- **去哪做**：`/commercial/agreements/new?clientId=`。
- **逐项操作**
  1. ☐ 选模式（M1：C1 / C3）与 OE（⚙ 只列该 Client 可用的 OE 候选）
  2. ☐ 选产品与开通项（支付方式、币种；出款通道 M4 前可不选）
  3. ⚙ C1：系统提示 Client MCC 是否在 OE 范围内
  4. ☐ 从价目模板生成价格；改价处 ⚙ 自动标破标
  5. ☐ 条款：T+N（⚙ 低于承保建议标破标）、保证金（引用 Risk 要求，不手填金额）
  6. ☐ 提交价格审批（免审模板直接 APPROVED）
- **提交后**：T10 给价格审批人；开通项以 PENDING_PREREQUISITES 创建。

### T10 价格审批 → T11 发起签署 → T12 跟进签署 → T13 登记签署并生效

- **T10**（商务负责人）：看破标项与理由；批准 / 驳回（驳回回 T09 原商务）。
- **T11**（原商务）：☐ 生成合同正文与价格附件 → ☐ 提交签署；⚙ 合同 PENDING_SIGNATURE 后 T12 给上线负责人，同时 T14（C3 MID 录入）/ T15（C1 MCC 核对）给渠道运营。C2 的子商户报送（T17，M3）要等合同 ACTIVE 后才能提交，签署前只做资料预填（Q-4 修订）。
- **T12**（上线负责人，跟进）：卡片显示"等 Client 签署 · 已等 N 天 · 上次催办 …"；操作：催办（发邮件 + 门户站内信，模板化）、记录沟通（电话 / 邮件摘要）。
- **T13**（原商务，粘性，过渡期）：☐ 上传 Client 签署件 → ☐ 登记签署（签署人、日期）→ ☐ 排期生效；⚙ 合同 ACTIVE + 价格 ACTIVE。M2（自助签署）后，Client 在门户签完即自动完成，T13 不再生成。

### T14 录入 MID（渠道运营，C3）

- **打开后看到**：OE、合同开通的支付方式与币种清单，每项"已有 MID ✔ / 缺 ✘"。
- **去哪做**：`/channels/mids/new?operatingEntityNo=`。
- **逐项操作**：☐ 按收单行开户结果录入 MID、所属渠道账号、能力（方式 / 币种）→ ⚙ 系统逐项刷新覆盖情况。
- **常见情况**：Client 尚未拿到收单行 MID → 任务"等待中"（等外部），填预计日期；超 10 工作日升级。

### T23 开通项未生效处理（上线负责人，异常）

- **何时出现**：签署生效、渠道完成后 1 个工作日，仍有开通项不是 ENABLED。
- **打开后看到**：逐开通项列出未满足前置（例："④ MADA：OE AE001 无 ACTIVE MID"），每条带"去处理"链接和对应队列。
- **逐项操作**：☐ 按链接找到对应队列负责人（卡片里可 @）→ ☐ 修复后在合同页点"重新检查前置"。

### T24 生产交易验证（技术支持）

- **打开后看到**：开通项 ENABLED 清单、验证档额度、Client 开发者联系人、生产 API 凭据与 Webhook 状态。
- **逐项操作**
  1. ☐ 与 Client 约定时间，提供验证步骤（小额下单 → 支付 → 全额退款）
  2. ☐ 录入 Order ID、Payment ID、Refund ID
  3. ⚙ 系统核对：订单属于该 Client 且已支付、支付 SUCCEEDED、退款 SUCCEEDED、Webhook 投递 SUCCEEDED，逐项 ✔ / ✘，✘ 项给排查入口
- **常见情况**：3DS 失败 → 换卡或查 3DS 登记；Webhook 失败 → 引导 Client 查端点；C1 可用平台测试卡。

### T26 提交上线复核 → T27 批准上线复核

- **T26**（上线负责人）：去限额档位页；⚙ 页面自动带出复核清单（资格、CRR、承保、合同与价格、开通项、渠道、接入、生产验证、未结事项）；☐ 逐项勾确认 → ☐ 写上线说明 → 提交"VERIFICATION → OBSERVATION"。
- **T27**（按 CRR 分档，排除 T26 执行人）：☐ 复核清单与说明 → 批准 / 驳回（回 T26，写原因）。
- **系统做什么**：档位 OBSERVATION，发布档位事件；通知 Client"已上线"、通知商务与渠道；看板该 Client 移到"观察期"。

### T28 观察期结束评估（风控承保）

- **何时出现**：到期（天数或笔数，先到为准）。
- **打开后看到**：观察期交易笔数、金额、拒付率、退款率、欺诈命中、人工复核结果。
- **逐项操作**：☐ 选择：转标准档 / 延长观察（天数）/ 收紧为 RESTRICTED（原因）。
- **结束**：转标准档后，若出口 B 也已完成（或合同未开通出款），实例 COMPLETED；Client 进入持续监控。

## 6. 与 Client 的沟通规则

| 规则 | 内容 |
|---|---|
| 单一联系人 | 对 Client 的人工沟通由上线负责人发起；其他职能需要 Client 配合时在卡片里 @ 上线负责人 |
| 系统通知优先 | 补件、待签署、上线成功等由 Owner 事件自动发邮件 + 门户站内信；人工催办只用模板 |
| 催办节奏 | 第 3 个工作日首次催办；之后每 3 个工作日一次；最多 4 次，之后升级上线主管 |
| 记录 [M2+] | 电话 / 邮件沟通在卡片"沟通记录"里留摘要（不贴 PII）。M1 写在交接备注里 |
| 语言 | 模板按 Client 门户语言发送（Platform 多语言） |

## 7. 异常作业

| 情况 | 谁处理 | 怎么做 |
|---|---|---|
| Client 15 个工作日无响应 | 上线主管 | 决定终止（填原因）或继续等待；终止后 Client 可重新提交，需重新发起 |
| 资格被拒 | 系统 | 流程结束；上线负责人收到通知，不再生成后续任务 |
| 承保拒绝 | 上线主管 + 合规组长 | 决定终止或要求重新承保（附新条件） |
| 价格反复驳回（≥ 2 次） | 商务负责人 | 线下对齐后再提交；看板标记 |
| 换模式 / 换 OE | 上线主管 | 用"回退到节点"回到 T09（workflow 已有退回能力，REQ-09 补"跨分叉回退"） |
| 执行人离职 | 上线主管 | 批量转交其任务；上线负责人改派 |
| 上线后开通项被暂停 | 上线负责人 | 生成"开通项异常"任务，按 T23 方式处理 |
