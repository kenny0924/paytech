## 1. 定位与边界

**一句话：** workflow 用一条流水线把跨部门工作串起来。它记录每个节点**要做什么、做完没有、谁同意了**，但不替任何业务系统做事。

- **归属：** 不做独立服务。它是 Platform Support 的一个模块 `paytech-platform-support-workflow`，表放在 `mor_platform`，取代目标架构 V2 中规划的 `workflow-approval`（18121 / `mor_workflow_approval`）。
- **为什么放进 Platform：** 审批人身份与权限、文件、审计都在 Platform，放在一起不需要跨服务回调。
- **两种形态，同一模型：** 最简单的是纯审批流，节点只配审批人。复杂的是给节点挂动作，例如新渠道上线时，商务、风控、渠道三条线并行。

| workflow 拥有 | workflow 不拥有 |
|---|---|
| 流程定义、流程版本（流程图 + 启动表单） | 业务对象与业务数据（产品、规则、路由、MID 等，各归其 Owner） |
| 动作目录（动作模板的类型、输入、输出、验证方式） | 数据查询 SQL（由 data-service 维护，workflow 只引用其编码） |
| 流程实例、实例变量、节点与动作的运行记录 | 业务执行是否允许（Owner 执行时自己重新校验，D13） |
| 验证结果与证据、审批与转交记录 | 用户、权限（Platform Access Control）；文件存储（Platform file-document） |
| “我的待办”查询（本期） | 统一收件箱 mailbox（以后单独做） |

**三条红线（D13 的落地）：**

1. **不写业务数据。** 页面任务只把人引导到 Owner 的页面，跳转时带上参数，数据由 Owner 页面写入。workflow 不调用任何业务写接口，也不跨库写数据。
2. **不当执行开关。** 实例完成只说明大家都做完并同意了。业务系统是否以此为前提由 Owner 单独决定，而且执行时仍须自行校验。
3. **不复制业务对象。** 只保存动作输出（表单值、文件 ID、确认说明）和验证证据，证据只包含对象类型、ID、版本和状态。

## 2. 概念

```
流程定义 ──1:N── 流程版本（不可变：流程图 + 启动表单 + 动作模板配置快照）
                    │
                    └──1:N── 流程实例 ── 实例变量（启动表单值 + 各动作输出）
                                 │
                                 └── 节点运行 ──1:N── 动作运行 ──1:N── 验证结果
                                         └──1:N── 审批记录 / 转交记录
动作目录 ── 动作模板 ──（发布时复制配置进流程版本）
```

| 概念 | 说明 |
|---|---|
| 流程定义 | 一个流程模板（如“新渠道上线”）。有草稿，发布后生成新版本；可以停用，停用后不能再发起，在途实例照常走完 |
| 流程版本 | 发布时冻结的流程图、启动表单，以及所引用动作模板的**配置快照**。之后修改动作模板不影响已发布的版本和在途实例 |
| 节点 | 开始、结束、任务节点、排他网关、并行分叉、并行汇合 |
| 动作模板 | 可复用的动作配置，由有权限的人维护 |
| 节点动作 | 任务节点引用的动作模板，带 `MANDATORY` / `OPTIONAL`、默认执行人和输入参数映射 |
| 流程实例 | 一次运行，带标题、可选的业务关联键（如 `CHANNEL:GEIDEA-SA`，只用于检索）、启动表单值 |
| 实例变量 | 以 `<来源>.<字段>` 命名，例如 `start.channelCode`、`apply.contractFiles`。分支条件和下游输入都从这里取 |

## 3. 启动表单与字段

发起实例时填写启动表单，提交后成为这个流程的上下文。启动表单和 `FORM` 动作**共用一套字段定义**。

| 字段类型 | 说明 | 能否用于分支条件 |
|---|---|---|
| 单行文本 / 多行文本 | 可配置必填、长度 | 可以（等于、不等于、包含） |
| 数字 | 可配置范围、小数位 | 可以（比较） |
| 布尔 | — | 可以 |
| 枚举（单选） | 可选值在字段上配置 | 可以（等于、属于） |
| 日期 | — | 可以（比较） |
| 文件 | 经 Platform file-document 上传；**可以多份**，可限制类型与数量 | 只能判断“有 / 无” |

- 除文件以外，所有类型都是单值，不支持嵌套对象和列表。
- **启动表单提交后不能修改。** 要补充或更正，在后续节点放 `FORM` 或 `FILE_UPLOAD` 动作，每次修改都有记录可查。
- 实例详情顶部单独展示“启动信息”，文件可下载。

## 4. 节点与动作

### 4.1 节点类型

| 节点 | 配置 | 行为 |
|---|---|---|
| 开始 / 结束 | — | 实例从开始节点出发，到达任一结束节点即完成 |
| 任务节点 | 审批人（可多个，`ANY` / `ALL`）、节点动作列表 | 至少要有一个审批人或一个动作 |
| 排他网关 | 有序的条件列表，加一条默认分支 | 第一个满足条件的分支生效，都不满足走默认分支 |
| 并行分叉 / 汇合 | 成对出现 | 分叉时同时激活各分支，汇合处等全部分支完成 |

条件是结构化配置（变量、比较符、值），不支持脚本。

### 4.2 动作类型

| 类型 | 做什么 | 输入 | 输出 | 验证 |
|---|---|---|---|---|
| `FORM` 表单 | 按字段定义填写 | 字段默认值（可来自变量） | 各字段值 | 字段规则 |
| `FILE_UPLOAD` 上传文件 | 上传一份或多份文件 | — | 文件 ID 列表 | 文件存在，类型与数量符合配置 |
| `PAGE_TASK` 页面任务 | 打开某个 Operations 页面完成操作 | 页面路由，以及从变量映射出的参数 | 确认说明 | 本期人工确认；以后可换成数据查询验证 |
| `MANUAL_CONFIRM` 人工确认 | 执行人确认事情已完成 | 说明文字 | 确认说明 | 记录确认人与时间 |
| `DATA_QUERY` 数据查询（**预留**） | — | data-service 查询编码，以及从变量映射出的参数 | 查询结果中的指定列 | data-service 执行它自己维护的 SQL，按通过条件判断。本期只预留类型与配置结构 |

### 4.3 验证

- 执行人提交动作后触发验证。放行之前可以重复提交、重复验证，以最后一次的结果为准。
- 每次验证都保存结论（通过 / 未通过）、时间、证据和原因。
- 以后接入 `DATA_QUERY` 时：
  - 在事务外调用 data-service，结果另开短事务落库。
  - 调用失败或超时算“未通过”，可以重试。
  - CDC 有秒级延迟，刚配完查不到也只算“尚未通过”。
  - SQL 有问题时，到 data-service 修改，再重新触发验证即可。

## 5. 运行规则

### 5.1 状态

```
实例：     RUNNING ──▶ COMPLETED
              └──────▶ TERMINATED（发起人或有权限者终止，终止后只读）

节点运行： ACTIVE（做动作）──▶ APPROVING（必选动作全部通过，且节点有审批人）──▶ PASSED
              │                      └──▶ REJECTED（退回上一节点）
              └── 节点没有审批人时，必选动作全部通过即 PASSED
           WAITING：汇合点等待其他分支

动作运行： PENDING ──▶ SUBMITTED ──▶ VERIFIED / UNVERIFIED（可再次提交）
           节点 PASSED 后锁定；节点被退回重新激活时，生成新的一轮动作运行
```

### 5.2 放行与审批

- 必选动作全部验证通过后才开放审批，可选动作不阻塞。
- 审批方式：`ANY` 任一人同意即放行；`ALL` 需全部同意。任一人驳回即驳回。
- 同一人不能既执行该节点的动作又审批该节点。只有被指派的人能执行动作、审批节点。
- 执行人和审批人都可以转交给其他 Operations 用户，转交保留历史。

### 5.3 驳回

驳回只退回实例**实际走过**的上一个节点，不回退任何数据。被退回的节点再次提交时，其必选动作全部重新验证。

| 位置 | 能否驳回 | 行为 |
|---|---|---|
| 普通节点、并行分支内第 2 个及以后的节点 | 可以 | 退回上一节点；在分支内时只影响本分支 |
| 并行分支的第一个节点 | 不能 | 上一节点是并行分叉，退回会牵连其他分支 |
| 汇合后的第一个节点 | 可以 | 审批人指定退回哪一条分支的最后一个节点；其他分支保持已完成，汇合处重新等待这条分支 |
| 流程的第一个任务节点 | 不能 | 前面没有任务节点；发起人可以终止实例 |

### 5.4 人员

- 只能指定具体的 Operations Realm 用户，不按角色或部门分配。
- 流程版本里配置默认人选，发起时可以修改，运行中只能通过转交变更。
- 有“发起流程”权限的人可以发起实例。发起人或有“管理流程实例”权限的人可以终止实例。

### 5.5 发布校验

- 恰好一个开始节点、至少一个结束节点；所有节点从开始可达，且都能到达结束。
- 并行分叉与汇合成对，不能跨分支连线。
- 每个排他网关有且只有一条默认分支。
- 每个任务节点至少有一个审批人或一个动作。
- 引用的动作模板都处于启用状态，`DATA_QUERY` 本期不能被引用。
- 条件与参数映射引用的变量，必须是启动表单或上游动作的输出（并行分支之间的输出不能互相引用）。

## 6. 例子：新渠道上线

```
开始（启动表单：渠道、国家、支付方式[枚举]、渠道合同[文件]）
  │
  ▼
立项审批（审批人：业务负责人，ANY）
  │
  ▼
并行分叉 ─┬─ 商务：PAGE_TASK「配置产品与价目」→ 商务负责人审批
          ├─ 风控：PAGE_TASK「配置风控规则」+ FILE_UPLOAD「风控评估」→ 风控负责人审批
          └─ 渠道：PAGE_TASK「配置渠道账号与 MID」、PAGE_TASK「配置路由」
                   FORM「渠道商户号、联系人」（可选）
  │
  ▼
并行汇合
  │
  ▼
排他网关：start.paymentMethod == APPLE_PAY ？── 是 ──▶ FILE_UPLOAD「Apple Pay 证书」──┐
  │ 默认                                                                         │
  ▼◀─────────────────────────────────────────────────────────────────────────────┘
联调确认（MANUAL_CONFIRM + FILE_UPLOAD「联调报告」）
  │
  ▼
上线复核（审批人：两位负责人，ALL）──▶ 结束
```

**看板上能看到：**

- 当前停在“风控”和“渠道”两条分支。
- 商务分支已完成，证据是“产品配置已确认，确认人 X，时间 T”。
- 渠道分支的“配置路由”还没提交，已停留 2 天，执行人 Y。

**驳回示例：**

- 上线复核时发现路由配错了。审批人驳回并指定“渠道”分支，渠道分支最后一个节点被重新激活。
- 渠道负责人改完路由重新提交，相关动作重新验证。
- 汇合处等渠道分支再次完成后，流程重新走到上线复核。

## 7. 初步数据模型（草案，`mor_platform`）

| 表 | 内容 |
|---|---|
| `t_workflow_definition` | 流程编码、名称、状态（ACTIVE / INACTIVE）、当前发布版本 |
| `t_workflow_definition_version` | 版本号、状态（DRAFT / PUBLISHED）；流程图 JSON（节点、连线、节点配置）、启动表单 JSON、动作模板配置快照；发布人与时间 |
| `t_workflow_action_template` | 模板编码、名称、类型、配置 JSON（字段 / 输入 / 输出 / 验证）、状态、版本（乐观锁） |
| `t_workflow_instance` | 绑定的流程版本、标题、业务关联键、状态、发起人、启动与结束时间 |
| `t_workflow_variable` | 实例 ID、变量名、类型、值、来源（启动表单 / 哪个动作运行） |
| `t_workflow_node_run` | 实例 ID、节点键、轮次（被退回后再激活加 1）、所在分支、来源节点运行（用于驳回）、状态、激活 / 完成时间 |
| `t_workflow_action_run` | 节点运行 ID、动作键、必选 / 可选、执行人、状态、输出 JSON、最后一次验证结果 |
| `t_workflow_verification` | 动作运行 ID、结论、证据 JSON、原因、时间、操作人 |
| `t_workflow_approval` | 节点运行 ID、审批人、决定（同意 / 驳回）、意见、驳回目标分支 |
| `t_workflow_transfer` | 对象（动作运行 / 节点审批）、原人员、新人员、操作人、时间、原因 |

另外：

- 文件通过 `t_file_owner_ref` 挂到流程实例上。
- 所有写操作都在 Processor 中锁**流程实例**一个资源（`AbstractLockProcessor`）。事务内只写本库，外部调用（以后的 data-service 验证）放在事务外。

## 8. 接口与页面（草案）

**内部接口**（Platform 提供，经 operations-console-bff 转发；操作人取自登录身份）：

| 能力 | 接口方向 |
|---|---|
| 流程定义 | 列表、详情、新建、保存草稿、发布（含校验结果）、停用、版本列表 |
| 动作目录 | 列表、详情、新建、编辑、停用 |
| 实例 | 发起（启动表单 + 人员调整）、列表（按流程 / 状态 / 发起人 / 我参与的筛选）、详情（流程图 + 进度）、终止 |
| 动作 | 提交（表单值 / 文件 / 确认说明）、触发验证、转交 |
| 审批 | 同意、驳回（汇合后节点需指定分支）、转交 |
| 我的待办 | 当前用户待执行的动作与待审批的节点 |

**Operations 页面：**

- 流程定义：列表，加流程图编辑器（左侧节点面板、中间画布、右侧属性面板，发布校验错误标在节点上）。
- 动作目录：列表，加编辑抽屉。
- 流程实例：列表，加详情（上方是流程图进度，点节点在右侧展开动作、证据和审批记录）。
- 我的待办：表格，带跳转入口。

**事件：** 本期不发布 MQ 事件。以后 mailbox 上线时，再由 workflow 投递“待办产生 / 关闭”。

## 9. 本期不做

- 动作自动调用业务写接口。
- `DATA_QUERY` 的实现，以及 data-service 的查询能力。
- mailbox、邮件 / 站内通知。
- 子流程、定时器、超时处理、复杂会签、表达式编辑器、脚本条件。
- 按角色或部门分配人员。
- Client / Partner 使用。
- 迁移现有各服务的 Maker-Checker，以及业务系统把“实例完成”作为执行前提的接入。

| 编号 | 问题 | 倾向 |

| T1 | 引擎：自研，还是引入 Flowable 等 BPMN 引擎？ | 自研轻量引擎。BPMN 对“节点挂动作”的模型太重，而且会接管事务和表结构 |

| T4 | 实例变量：拆行还是整体 JSON？ | 拆行，便于分支判断、审计和检索 |
| T5 | Platform 注册块号 | 按 live `mor_platform` 选定 |
