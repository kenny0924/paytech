## Canonical terminology
- Client: platform customer, with `INDIVIDUAL` and `ORGANIZATION` types. Do not rename it Merchant or use both names for the same role.
- Operating Entity: legal seller that contracts with payment providers and owns MIDs.
- Finance Entity: Finance-internal accounting identity for a platform legal Party that may not own a MID or qualify as an Operating Entity. It is manually maintained in Finance and must not replace the CCT Party authority.
- Local Partner: external partner that supplies entity information and receives an independently configured revenue share.
- Consumer: final buyer using Hosted Checkout.
- Provider / Acquirer: NI, Geidea, or another external payment provider.

## Fixed architecture boundaries
- The six core systems are Client & Contract, Commerce, Payment Orchestration, Risk & Compliance, Finance, and Platform Support.
- Gateway and entry applications sit outside the six core systems and do not own core business facts.
- An entry application is a logical access channel, not automatically a Java service. Follow `agent-docs/APPLICATION_ARCHITECTURE.md` for the approved consolidation and exposure model.
- BFFs may aggregate authorized queries and adapt presentation responses, but must not own business facts or orchestrate cross-system business transactions.
- Platform owns global human Account, Realm exactly `{OPERATIONS, CUSTOMER}`, Channel exactly `{OPERATIONS, CLIENT, PARTNER}`, Sessions and Tenant membership/IAM. Operations maps to OPERATIONS Realm/Channel; Client and Partner map to CUSTOMER Realm with their respective CLIENT or PARTNER Channel. CCT owns Client/Partner pre-Tenant Applications; Risk owns the typed `source_namespace` Case boundary. BFFs are stateless channel adapters.
- Each system owns an independent database. Cross-database reads and writes are forbidden.
- Use synchronous interfaces for commands and queries; use MQ for internal callbacks and business facts.
- Internal synchronous service calls use HTTP contracts from lightweight `*-api` modules with Spring `@HttpExchange`; do not introduce new Dubbo or OpenFeign interfaces.
- Nginx terminates public TLS and overwrites one X-Real-IP. API Gateway consumes that value once for Guard and access logging, removes proxy headers before BFF forwarding, and is reachable only from the private Nginx network. Gateway, BFFs, Platform Support, Vault and core Java services communicate over private HTTP and do not own X.509 certificates.
- Gateway responsibilities are ingress, basic authentication, rate limiting, routing, request IDs, and access logs—not business orchestration.
- Platform owns the current public Target/Route/Guard/Console Resource configuration for all external HTTP APIs; internal service calls bypass Gateway. Gateway consumes a globally validated immutable Snapshot only after the future runtime cutover, retains its static Approved Target Registry, precompiled Security Profiles, trusted protocol and absolute safety ceilings, and keeps Bucket/Counter/Lease/TTL state in Redis. Gateway never executes PLT-I02 or core resource authorization; BFFs and core systems retain those decisions. Until cutover, the deployed static Operations Catalog remains a pre-cutover runtime fact.
- Partner transaction access is read-only. Partners cannot operate orders, payments, refunds, routing, MIDs, or ledger records.
- Operating Entity source values are `PLATFORM`, `CLIENT`, and `PARTNER`: platform-owned entities, an Organization Client's own or controlled entities, and Local Partner-supplied entities. Every Operating Entity is platform-managed after onboarding; one source role may supply multiple entities.
- Partner-source CCT-I13 V5 returns the Partner Share and Platform Service Charge scopes plus the Partner Agreement's unique `PLATFORM_SIGNATORY` Party. Commerce freezes the Service Charge Scope ID and Party ID but never a Finance Entity ID; non-Partner contexts keep all Partner/service-charge fields null.
- Finance maps that Party to one ACTIVE local `t_finance_entity`. A calculated `PLATFORM_SERVICE_CHARGE` produces one balanced Journal in the Partner OE Book (`Dr Service Fee Expense / Cr Payable`) and one balanced Journal in the Platform Finance Entity Book (`Dr Receivable / Cr Service Revenue`) in the same local transaction. Do not derive this charge as a residual or restore a generic intercompany-transfer table.
- Finance represents a Client's prepaid guarantee as the `CLIENT_SECURITY_DEPOSIT/NONE` liability Account and confirmed shortfall as the `CLIENT_RECOVERY_RECEIVABLE/NONE` asset Account. Deposit receipt/use/return and recovery creation/netting/receipt are immutable Journals; do not restore Reserve Case, Restricted Fund, Recovery Case/Application or another balance workflow. Risk owns the final minimum deposit requirement. Manual Payout must pass fresh Risk checks at `PAYOUT_CREATION`、`PAYOUT_FINAL_APPROVAL`、`PAYOUT_EXECUTION_CREATION` and `PAYOUT_EXTERNAL_SUBMISSION`; every distinct checkpoint uses a new `assessment_id + evaluation_id`, while the same command replay reuses its original pair. Each check freezes Owner/OE/currency/Beneficiary Account country and `owner_debit_amount`; Client requires zero Recovery Receivable and sufficient Security Deposit, while Local Partner requires zero `PARTNER_RECOVERY_RECEIVABLE` and never reads Client-deposit fields. Missing, stale or unavailable authority fails closed. `RefundSucceeded` does not consume the deposit. For `DisputeLost/DisputeOutcomeCorrected`, only `outcome=LOST + principal_bearer=CLIENT + security_deposit_use_allowed=1` may use it before creating any remaining receivable.
- CCT Entity Assignment uses only `entity_source_relation`, `client_entity_affiliation`, `entity_assignment_rule`, and `client_entity_assignment`. It is automatic, Client-specific, and exact on country/currency/industry/MCC. Do not restore Assignment Policy/Version/Binding, Assignment Root/Version, GLOBAL/wildcard/fallback/manual routing, `source_owner_key`, or Assignment scope/content hashes and revision fields without a new approved use case.
- An Assignment Rule target is eligible only when the Operating Entity is ACTIVE and has an exact ACTIVE Affiliation plus one unique ACTIVE Source Relation. The lowest eligible `priority_no` wins; no candidate or any ambiguity ends the old Assignment and fails closed. The CCT Processor handling a Rule/Affiliation/Source/OE/Business-Classification state change synchronously recomputes the exact affected assignments in the same local transaction before commit. Callers, CCT-I11/I13 queries, schedulers, and manual operations do not generate or repair assignments; do not add a workflow, scheduler, publication version, or extra event table for this MVP. CCT-I11/I13 are read-only and return `assignment_id`, `rule_id`, `affiliation_id`, `entity_source_relation_id`, `source_type`, and `operating_entity_id`; Commerce freezes these stable IDs and Payment freezes `assignment_id`.
- Client and Local Partner requests never select an Operating Entity or MID for a transaction. CCT resolves and freezes the Order's Operating Entity; Payment selects a MID under that same entity per Attempt. A later Attempt may change MID but must not switch Operating Entity.
- Payment Provider configuration uses `t_payment_provider -> t_provider_account -> t_provider_mid`. A Provider Account is a technical API account, not Finance's settlement/receivable account. Each MID belongs to one Provider and one current Provider Account; routing freezes Provider, Provider Account and MID per Action. Static typed Capability filters candidates before current-window Health State ranking. Do not restore Connection/Connection Version, MID Limit or MID Credential tables without a new approved use case.
- Payment Attempt freezes an exact Payment Method Catalog code. `t_payment_instrument` remains one optional wide table with `provider_instrument_ref` plus nullable approved card descriptors; do not add JSON, EAV/Key-Value, subtype tables or speculative Wallet/Bank/BNPL columns. If an APM has no stable Provider tool reference, omit the Instrument row. `t_payment_customer_action` expresses REDIRECT, THREE_DS_CHALLENGE, SDK, APP_SWITCH or QR_CODE and must not persist Redirect URLs, Client Secrets, SDK Tokens, QR Payloads or bearer-like parameters.
- `client_order_id` is permanently unique within one Client and is not a transport idempotency key. Command retries reuse their original idempotency key; reusing an existing `client_order_id` under a new key must not create another Order. The platform never creates an automatic replacement Order.
- Temporary Provider/MID/routing shortage keeps the existing Order and allows a later Attempt only under its frozen Operating Entity. If CCT publishes `OperatingEntityChanged` with `operating_entity_status=CLOSED`, Payment blocks new Attempts, waits for every active or `UNKNOWN` Attempt to resolve, then terminates the unsucceeded Intent; Commerce cancels the still-open Order/Session. Further payment requires a Client-created Order with a new `client_order_id`.
- Vault is an internal supporting security service, not a seventh core business system. It centrally stores approved recoverable non-card sensitive values but never owns their business meaning; no Gateway, BFF, browser, external Client or business service may access the Vault database directly.
- Vault is generic and must not gain Consumer, Customer, Order, Network Evidence or other business-specific tables. Never add a default Vault field bundle: Token, Blind Index/Key Version, Masked Value, Vault Record Version and Metadata Hash each require a demonstrated Reveal/Retire, equality-query, display, metadata-concurrency, integrity or rotation consumer. Omit fields with no current consumer.
- Payment Acceptance Readiness is always derived server-side by COM-I10 from exactly three immutable `CONSUMER_TERMS`, `REFUND_POLICY` and `PRIVACY_NOTICE` Acceptance records plus their same-Order/same-Session `LEGAL_ACCEPTANCE` Network Evidence. Return and freeze the three explicit Acceptance IDs, `acceptance_completed_at`, Order Version and expiry; do not restore Acceptance Summary, completion pointers or a collection Hash.
- `consumer_reference` is a structured, opaque, non-PII reference unique within a Client namespace. Reject Email, Phone, government identifier or any other personal raw value in this field.
- Commerce Consumer Email and Phone each use an approved stable Vault Value Token for equality/frequency correlation and authorized Reveal. The Consumer Profile Token contains only name and full billing address and must not duplicate Email/Phone. Equal normalized values for the same field return the same Token; key rotation leaves it stable; shared-token destruction waits for all references and Retention/Legal Hold rules.
- Commerce Checkout Network Evidence is not encrypted: store `client_ip_address`, `user_agent`, `trusted_proxy_chain` and approved derived dimensions in Commerce. Do not add a Vault Token, Blind Index/Key Version or device identifier. Apply minimum access, audit, Retention and no-external-disclosure controls.
- Commerce→Payment→Risk may pass stable Consumer Tokens, approved network originals and derived fields only through the internal synchronous minimum contract. Never expose these Tokens or network originals through an external API, ordinary logs, MQ or BCR.
- Commerce Refund uses only `t_order_refund_position` and `t_refund_request`. Commerce atomically reserves its local refundable amount and then calls PAY-I04 directly, storing only the stable Payment Channel Refund ID. Payment independently locks `t_payment_refund_position`, uses Version/CAS to reserve its refundable amount and creates the Channel Refund in one local transaction. Refund `UNKNOWN` stays inside Payment and is not published; Commerce remains `PROCESSING` with its local reserve unchanged. `RefundSucceeded` goes to Commerce and Finance, while `RefundFailed/RefundCancelled` go only to Commerce. Finance does not pre-reserve refund cash, never consumes `CLIENT_SECURITY_DEPOSIT` for a refund, and consumes only `RefundSucceeded` to create accounting and fiscal facts. Finance has no generic Funding tables: Manual Payout locks Owner `AVAILABLE → LOCKED` by `owner_debit_amount`, and each Execution creation/retry/failure/cancel/reconciliation path serializes `active_payout_cash` on the same `BANK_CASH` Account; `UNKNOWN` keeps that capacity occupied.
- Cancel is a Commerce-owned command for an unpaid Order: it may complete only when Payment confirms there is no successful `AUTHORIZE`, `CAPTURE` or `SALE` and no submitted/`UNKNOWN` Provider Action; Commerce closes the Order and Session only after definitive Payment Intent termination. Void is a Payment-internal full release of a successful uncaptured Authorization (`captured_amount=0`) and creates no Commerce Refund Request, Finance Journal, Fiscal Fact or Credit Note. Reversal is a Commerce-owned orchestration command whose Payment-side locked decision routes an uncaptured Authorization to Void and a captured/`SALE` payment to the existing full Refund chain; do not add a `REVERSAL` Payment Action or expose direct public Void.
- Dispute evidence is an on-demand RFI using Risk's existing dispute case/state-change/evidence-package/evidence-ref/submission-request records. Opening enters `EVIDENCE_REQUIRED` and publishes `DisputeEvidenceRequested`; the Client deadline precedes the Provider deadline, and no response may accept the loss. Outcome versions are append-only: `PROVIDER_ACTION` may produce Version 1 `WON/LOST`; `CLIENT_DISPOSITION` and `OPERATIONS_DISPOSITION` may produce Version 1 `LOST` only; Version 2+ is restricted to `OPERATIONS_CORRECTION`. Every result/correction state change binds `trigger_id=decision_source_id`. Liability authority is an XOR: the rule path freezes `decision_evaluation_id + action_effect_id` with null `decided_by`, while the manual path freezes non-null `decided_by` with both rule coordinates null. `DisputeOpened` only creates or updates Risk-owned settlement restrictions/minimum deposit requirements and does not post Finance entries. `DisputeLost` and `DisputeOutcomeCorrected` carry explicit `outcome_version`, `outcome`, `principal_bearer` and `security_deposit_use_allowed`; Finance may consume `CLIENT_SECURITY_DEPOSIT/NONE` only for `outcome=LOST + principal_bearer=CLIENT + security_deposit_use_allowed=1`, must not infer permission from reason/source/rule, and posts any remaining shortfall to `CLIENT_RECOVERY_RECEIVABLE/NONE`.
- PAN, CVV/CVC, full track data and PIN/PIN Block must never enter Code-MoR services, databases, events, logs, files or Vault. Card collection/tokenization remains Provider-hosted; Payment stores only a stable Provider instrument reference and approved card descriptors when such an Instrument exists.
- MVP reliable asynchronous work uses each service's local `compensation_event`, written with the business change in one transaction and executed only after commit. XXL-Job is the fallback wake-up/sharding mechanism, database Claim/Lease protects multiple instances, and consumers implement idempotency in business tables or projections. Do not add generic Inbox/Outbox or a central compensation database without a new approved decision.
- MVP does not implement generic automated Retention, Legal Hold, archive, anonymization or destruction infrastructure. Business and technical data is preserved by default and is not automatically destroyed. Before processing real regulated production data, complete a dedicated data-classification, jurisdictional retention, Legal Hold, backup, Vault lifecycle, controlled-destruction and audit design with legal/compliance review.

## Confirmed product constraints
- Checkout is hosted and redirect-based.
- Offering is optional; checkout data is supplied at order creation and stored on the Order plus its one immutable Order Context.
- Start with USD and one-time payments, while keeping the money model multi-currency capable.
- Client pricing supports percentage plus fixed fees; each partner's share is configured independently.
- Manual Payout amounts and fees are calculated by the system; payout initially uses fixed dual approval, a pre-created Execution, manual bank submission, payment evidence, and complete `CONFIRMED` debit reconciliation before `PAID`. Provider Settlement remains a separate reconciliation concept.
- Clients and internal operations can initiate full or partial refunds.
- Industry eligibility is configuration-driven; never hard-code games or another industry.
- Keep the site local. Do not publish externally unless explicitly requested.

## Change discipline
- Use applicable Superpowers skills for architecture exploration and implementation planning when the user requests Superpowers-assisted planning.
- During code implementation, do not use Superpowers implementation/execution skills unless the user explicitly asks for them. Follow a lightweight TDD loop instead: write one meaningful failing test, confirm the expected failure, implement the minimum production behavior, make the test pass, then refactor and rerun the relevant suite.
- Treat mature open-source projects as engineering-quality references for naming, module boundaries, configuration, testing and operability when useful, but adapt their practices to Code-MoR rather than copying code or overriding this repository's authoritative decisions.
- Preserve existing user changes and inspect `git status`; a dirty working tree may be intentional.
- Keep requirements, functional use cases, interface use cases, and global sequences consistent when changing a business decision.
- Do not collapse distinct lifecycle concepts for convenience.
- Run `npm --prefix requirements-site test`; lint touched code when relevant and report unrelated pre-existing failures separately.
- Do not commit, create branches, deploy, or provision external resources unless asked.

## Automated test boundaries
- Java `auto` tests must complete within the current service using its real production chain. They must not connect to real business environments, Nacos, configuration centers, other services, providers, or team-shared infrastructure outside the repository-owned Loopback environment.
- Database, Redis, and MQ behavior needed by a test must use the manually started repository-owned `local-environment`; tests do not create, stop or rebuild its containers. External HTTP/MQ dependencies use stateful Simulators over the real protocol.
- Do not use `when(...).thenReturn(...)`, `@MockBean`, `@MockitoBean`, spies, or equivalent method-level behavior stubs to replace the production chain. Builders construct data, Mockers prepare state, and Checkers/Probes only observe and assert.
- Prefer a small set of business-level tests from the public entry through the real Controller, optional Processor, Domain Service, Repository/Mapper and local database. Do not create one test per internal method or class merely to raise coverage; add focused unit tests for pure algorithms, state machines or converters when they materially improve failure localization.
- Default Maven tests run `auto` only. `manual` tests require an explicit profile and never run in normal CI.
- A new outbound client, provider adapter, Redis capability, or MQ producer/consumer is incomplete until its isolated `auto` path, Simulator/test infrastructure, unexpected-call failure, and state reset are covered as defined in `agent-docs/UNIT_TEST_GUIDE.md`.

## Database design boundaries
- Every project that owns a database must design it in PDManer from `agent-docs/templates/pdmaner/template.pdma.json` and keep its model under `<project-root>/docs/database/`.
- Physical table names must use lowercase `snake_case` with the `t_` prefix; unique indexes use `uk_`, and non-unique indexes use `idx_`. Chinese display names and logical catalog names do not receive the technical table prefix.
- Once database implementation is explicitly authorized, keep the PDManer model, manually applied schema SQL, initialization DML, DataObject/Mapper/Repository mappings, and local-infrastructure-backed tests consistent in the same change. Do not add Flyway, Liquibase, Testcontainers or application-startup schema/data initialization. DataObject types use business entity names without a `DO` suffix. The current Client & Contract and Commerce PDManer-only phases end at their validated design artifacts and do not create those implementation artifacts.
- Never store real database connections or credentials in a PDManer model, create cross-database foreign keys, or restore removed template content such as `PARTNER_ID`, legacy transaction domains, unrelated database targets, or generic Java CRUD generators.
- PDManer is the design source and the reviewed current Schema DDL is the executable database definition. Record each manual SQL change, execution order and rollback plan; never let generated DDL or an application mutate a shared environment automatically.
